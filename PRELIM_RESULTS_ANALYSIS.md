# KIRBy preliminary results — per-experiment walkthrough

Read-only analysis of the analysis script's output (`~/Downloads/prelimResults`,
produced by `tests/analysis/firstpass_notready.py`) for every experiment past c02.
Generated 2026-07-07. No code was changed to produce this document.

Each experiment is written in four parts: **what the experiment is asking** (the
hypothesis in plain English), **what the table shows** (every column explained,
with a verbatim row or two), **what it is actually telling us and whether to trust
it** (interpreting the real numbers, flagging noise / saturation / degenerate values
/ hidden max-median-mean selections), and **what is wrong and whose fault**
(experiment bug vs analysis-reader shortcoming vs a design decision for you).

A reminder of the setup being judged: KIRBy tests whether a *hybrid* (a
feature-selected combination of many representations) beats the best single
representation. Metric direction is per-domain — molecular/reaction regression use
an error where lower is better; antibody regression uses R2/Spearman where higher is
better; classification uses AUROC/F1. Wins/losses are reported as counts, never as an
average of a metric across datasets.

(The blueprint trace — the winning hybrid recipe per dataset — is NOT included here;
it runs separately as its own SLURM job.)

# COMPLEXITY

## c01 — profiling each representation on its own, before any hybrid

**What the experiment is asking.** This one is deliberately descriptive: it does not build a hybrid or test the hybrid hypothesis at all. For every dataset it takes each candidate representation one at a time and measures three things about it. First, how well that single representation predicts the label on its own, using a plain cross-validated baseline with several ordinary models. Second, its "effective rank," which is a measure of how many directions the representation genuinely spreads its information across (a compact representation concentrates in a few directions, a rich one spreads across many). Third, its "mutual information" with the label, which is an estimate of how much the representation tells you about the answer. The question the report is trying to answer with these three numbers is simply: "when a representation turns out to be the strongest predictor on a dataset, is it strong because it is intrinsically rich and high-dimensional, or because it is compact and focused?" There is no notion of the hybrid "working" here, because the hybrid is never run in c01. It is a characterisation step that feeds intuition for the experiments that do test hybrids.

**What the table shows.** Each row is one dataset. The "#reps" column is how many representations were profiled on that dataset. The "best rep" column is the single representation that scored best as a solo predictor, where "best" respects the metric direction for that domain — for antibody and genomic tasks a higher score is better, and for the molecular datasets the score is an error where lower is better. The "score" column is that winning representation's baseline number. Crucially, that score is the best result across the several models tried for that representation, so it hides a maximum taken over the models and never tells you which model produced it. The "erank" and "MI" columns are the effective rank and the mutual information of that same winning representation, not of whichever representation happened to have the highest rank or the highest information. So the three number columns all describe one chosen representation. One representative row is "abagym_EGFR 26 saprot 0.322 259.399 0.858", meaning 26 representations were profiled, saprot won as a solo predictor with a score of 0.322, and that saprot embedding has an effective rank of about 259 and an estimated mutual information of 0.858. Another is "humanness_therapeutic 26 igt5 0.920 245.642 1.442", where the igt5 representation is a very strong solo predictor at 0.920.

**What it is actually telling us, and why I do or do not trust it.** Read narrowly, the numbers are plausible and internally consistent: the strongest representations on the big classification-flavoured tasks (humanness_therapeutic at 0.920, tcga_luad_vs_lusc at 0.949, tcga_brca_pam50 at 0.882) also carry high effective rank and real mutual information, which is the "rich, not compact" story. But there are three things to be careful about. First, the mutual-information column collapses to exactly 0.000 on a whole cluster of antibody and Ginkgo datasets — ginkgo_aggregation, ginkgo_purity, ginkgo_titer, flab_aggregation_jain, flab_immunogenicity_marks are all 0.000. That is not a coincidence or a missing value: the estimator subtracts a label-permutation null and floors the result at zero, so 0.000 means "no information detectable above the noise floor at this sample size," and on flab_aggregation_jain the local result files show every single one of the 23 representations flooring to zero. On those datasets the MI column is genuinely uninformative rather than genuinely zero. Second, the score column silently mixes different metrics and different directions with no unit label. The antibody 0.322 for abagym_EGFR is a higher-is-better correlation-style score, while the molecular row "caco2 12 pdv 0.293 76.248 0.901" is a lower-is-better error, so 0.293 there is a good result, not a worse one than 0.322 — but nothing in the table tells you that, and the two numbers are simply not comparable side by side. Third, the score itself is a hidden maximum over roughly six models, and the winner can be a single lucky model: in the local abagym_EGFR file saprot only reaches 0.322 through the SVM, while its random forest and MLP baselines sit near zero or negative. I want to flag a data-freshness caveat too: my local result files predate the report — for abagym_EGFR the report prints saprot MI as 0.858, but the local file for the same dataset and representation shows 0.000, which means the report was generated from a newer server run and the exact MI values there are from the run I cannot see. The mechanics I describe above come from reading the code and the older local files, not from the exact numbers in the report.

**So what is wrong, and whose fault.** Nothing here is a crash or a divide-by-zero, and for a descriptive profiling step the core computation is behaving as designed. The real issues are on the reader side and in how the table is meant to be interpreted. The reader, in the read_c01 function of tests/analysis/firstpass_notready.py, prints only the winning representation's own erank and MI, which cannot actually answer the stated question "is the best rep rich or compact?" — to answer that you would need to see where the best representation sits relative to the others on that dataset (for instance the highest and lowest effective rank across all its representations), and the reader throws all of that context away. The reader also prints the score with no metric name and no direction marker, and it hides both the max-over-models and the identity of the winning model, so a reader cannot tell that caco2's 0.293 is an error while EGFR's 0.322 is a correlation, nor that saprot only won through one model. There is also a small latent mismatch worth fixing in the same reader: the experiment source, tests/experiments/complexity/c01_rep_characterization.py, deliberately writes the metric name and its direction into a "_meta" block (its own comment cites this as a fix so the bare scores stay interpretable), but the reader looks for a "lower_is_better" flag at the top level of the file rather than inside "_meta", so it never actually reads what the experiment saved and instead falls back to a hard-coded registry. That happens to give the right direction for the registered molecular and antibody cases here, so it is not currently corrupting results, but it means the experiment's own recorded direction is being ignored. The genuine design question for you is whether the mutual-information column earns its place at all: on the antibody and Ginkgo datasets it floors to zero across the board at these sample sizes, so as printed it adds a column of zeros that looks like a measurement but is really just "too little data to tell." I would either annotate those zeros as floored-at-null or drop MI from the c01 table for the small antibody tasks. All of these are reader and presentation fixes; the experiment itself is doing roughly what a characterisation step should do.


## c02 — the core claim: does the hybrid beat the best single representation on the same model?

**What the experiment is asking.** This is the headline experiment for the whole project. For each dataset it takes every downstream model (ridge, random forest, xgboost, lightgbm, svm, mlp, and so on) and asks a very direct question: if you give that model the single best individual representation it could have used, and then instead give the same model a feature-selected hybrid built from many representations, does the hybrid score better? The hybrid is not a different model and not a different metric; it is the identical model fed a smarter set of input features. The hybrid would count as "working" here if, holding the model fixed, the hybrid's cross-validated score comes out ahead of that model's own best single-representation score, and ideally by enough that the gap is larger than the fold-to-fold noise.

**What the table shows.** For each dataset the reader prints the three strongest existing (model, representation) pairs, one row each, ranked by how good that model's best single representation was. The rank-1 row is marked with a star and is treated as the "deployed" combination — the strongest baseline anyone would actually have picked. Reading across a row: the number is the rank; "model" is the downstream model; "existing rep" is that model's best single representation; "base" is that representation's cross-validated score; "hybrid" is the same model's best hybrid score; "±95CI" is a 95 percent confidence half-width computed from the five cross-validation folds of the hybrid (a t-value for four degrees of freedom, times the fold standard deviation, divided by the square root of five); "Δ" is the direction-corrected improvement, where positive always means the hybrid is better (for antibody R-squared or Spearman that is hybrid minus base, for molecular error metrics it is base minus hybrid); "verdict" is WIN, WIN\*, tie, or LOSS, where a bare WIN just means Δ beats the 0.01 tie threshold and a starred WIN\* means the base score fell entirely outside the hybrid's confidence band, i.e. "probably real"; "repdim" is the native width of the existing representation; "hybdim" is how many features the hybrid actually used; and "smaller?" is yes when the hybrid won using fewer features than the single representation it beat. Below each dataset a BEST-ANY line asks a looser question — the single best hybrid across any model versus the number-one existing combo. Two representative rows quoted verbatim: "abagym_EGFR 1\*svm saprot 0.324 0.358 0.091 +0.034 WIN 2560 250 yes" and "adme_hlm 1\*svm pdv 0.454 0.421 0.005 +0.033 WIN\* 200 1032 no".

**What it is actually telling us, and why I do or do not trust it.** The direction of the result is genuinely encouraging: the per-domain tallies at the bottom read "[antibody] deployed model: +19 hybrid-better =5 tie -6 worse (30 datasets)", "[molecular] +4 =0 -0 (4)", "[genomic] +2 =0 -0 (2)", and "[tcga] +0 =2 -0 (2)". So on the rank-1 deployed model the hybrid wins far more than it loses, and it essentially never loses in molecular, genomic, or tcga. But I trust these two groups very differently. The molecular wins are the solid ones: "adme_hlm ... 0.454 0.421 0.005 +0.033 WIN\*" has a confidence half-width of only 0.005, because those datasets have a couple of thousand samples and a tight error metric, so a +0.033 improvement that clears its own confidence band is real. The tz_her2 classification rows are similar — "tz_her2_binary 1\*lightgbm blosum 0.865 0.915 0.041 +0.051 WIN\*" is a five-thousand-sample dataset with a believable, band-clearing gain. The antibody wins, which drive most of the +19 count, are much shakier. Look at the EGFR row I quoted: the Δ is +0.034 but the confidence half-width is 0.091, nearly three times the improvement, so that "WIN" is nowhere near statistically distinguishable from noise. That pattern repeats across the antibody block, where datasets have only 50 to 240 samples split into five folds; several ostensible wins (for example "abagym_Ang2 ... +0.068 WIN" with a 0.401 band, or "flab_thermo_jain ... +0.101 WIN" with a 0.180 band) sit deep inside their own error bars. There is also a real hidden-maximisation concern that inflates these deltas: both sides are argmax picks on the same cross-validation folds, but the hybrid side is the best of roughly 4,445 configurations (I confirmed the config count in the EGFR result file), while the baseline side is only the best over a few dozen representations. A search over thousands of noisy fold-means will find a lucky high value more often, so some of the small positive deltas are winner's-curse rather than signal. The saturated datasets tell the honest opposite story — "humanness_therapeutic ... 0.969 0.969 0.010 -0.000 tie" and "tcga_luad_vs_lusc ... 0.991 0.996 0.004 tie" are already at the ceiling, so the hybrid correctly has nothing to add and lands as a tie. One genuinely missing cell is worth naming: "ginkgo_aggregation 1\*svm ablang2 0.163 -- -- -- --", where the svm hybrid produced no finite score, so that dataset's deployed-model verdict is blank; I would need the server run's logs to say why svm failed there. I should also flag that the report was clearly generated from fresh server results, not the copies in my local tree — my local files carry an older schema (no stored metric direction, a flat rep-dims field instead of the nested one the reader reads), so the repdim column would be blank locally even though it is populated in the report.

**So what is wrong, and whose fault.** The experiment logic itself is basically sound; the comparison it makes is the right one and the numbers are internally consistent, so I would not call this broken. The one experiment-side item to chase is the blank svm hybrid on ginkgo_aggregation, which lives in the search, not the reader. The deeper issue is a design question for you, and it is baked into the experiment rather than the analysis: the hybrid is selected as the argmax over roughly four thousand configurations on the same folds it is then scored on, with no held-out or nested validation, so on the tiny antibody datasets a +0.03 "win" inside a ±0.09 band is not really a win, and the honest headline is closer to "hybrid clearly helps on the larger molecular and classification datasets, and is within noise on small antibody ones." If you want the antibody claim to stand up you need either more folds or an outer held-out split to de-bias the selection. The reader has three fixable shortcomings, all in read_c02 in tests/analysis/firstpass_notready.py rather than in the experiment. First, the confidence test is asymmetric: it puts a band on the hybrid but treats the baseline as a point with no uncertainty, so WIN\* is more generous than it looks; it should either band both sides or say plainly that only the hybrid is banded. Second, the rank-2 and rank-3 rows quietly compare each weaker model's hybrid against that same weaker model's own single representation, which is a different and much less interesting question than the rank-1 deployed comparison, yet they sit in the same table where they are easy to misread as three independent wins — and the domain tally at the bottom silently keeps only the rank-1 delta and throws the other two away. Third, the fixed 0.01 tie threshold is applied identically to R-squared, RMSE-style error, and AUROC even though those live on different scales, so "tie" means something different in each domain. None of these need code shown here; they need the reader to stop presenting a noise-dominated small-n win with the same visual weight as a tight, band-clearing large-n one.


## c03 — cross-dataset transfer: does complexity predict the optimal hybrid?

**What the experiment is asking.** c03 is not a per-dataset experiment like most of the others. It runs once over a whole collection of datasets at the same time, and for each one it does two things. First, it finds the single best hybrid configuration native to that dataset — which downstream model won, which importance method was used to rank features, how big the feature budget was, and what score that combination reached. Second, it lines all of those datasets up side by side and asks whether the "shape" of a dataset predicts the size of its best hybrid. Concretely it computes complexity numbers for each dataset (things like the effective rank of its representation matrix, its participation ratio, and a handful of Lorena-style difficulty measures), and then measures the correlation between each of those complexity numbers and the winning feature budget. The hypothesis that would count as this "working" is a clean, positive correlation: datasets whose features live in a higher-dimensional, richer space should want a larger hybrid, and simpler datasets should want a smaller one. It is explicitly a co-variation study, not a true transfer study — the source file itself says real source-to-target blueprint transfer lives in c24, and c03 only looks at whether the optimal configurations move together in interpretable ways.

**What the table shows.** In principle the report table would print, one row per dataset, the best downstream model, the best importance method, the winning budget, the resulting feature dimension, and the best score, followed by a short list of Spearman correlations between each complexity metric and the optimal budget. In practice there is no table at all. The entire c03 block in prelimResults is two lines:

```
[c03]  cross-dataset transfer — native-optimal config + does complexity predict budget? (combined file)
  (no c03 file — single combined job, depends on c02)
```

That second line is not a computed result. It is a hardcoded fallback the reader prints when it cannot find any c03 output file to open at all.

**What it is actually telling us, and why I do or do not trust it.** The block is empty because the experiment's output simply is not present in the results that were synced. I checked every results directory under the analysis root, and there are folders for c01, c02, c04, c05, c11, c12, c13 and the similarity experiments, but there is no c03_cross_dataset_transfer folder anywhere, and no c03 JSON on the local disk either. The reader works by looking up a directory whose name matches the experiment, grabbing the first JSON inside it, and reading from that; when the directory does not exist the lookup returns nothing and the reader falls straight through to its "no c03 file" message. So the empty block is a data-availability fact, not a signal about the science. The most likely reason it is missing is exactly what the fallback line hints at: c03 is a single combined job that leans on c02. It reuses the same cached hybrid searches that c02 populates for each dataset, and it only becomes worth running once c02 has finished across the datasets you want to compare. c02 did run — its folder is present — but the combined c03 job that consumes those searches either was never launched in this wave or has not been synced back from the server. I cannot tell which from here, because there is no file and no error to inspect; confirming it needs a look at the server job list. What I can say is that nothing here is crashed or degenerate — there is genuinely no c03 result to interpret yet. It is also worth flagging, for when the data does arrive, that the headline correlation is fragile by construction: it is a Spearman correlation computed across however many datasets happen to be in that one combined job, and if that is only a few datasets the correlation will swing to plus or minus one almost trivially and mean very little.

**So what is wrong, and whose fault.** There is no experiment bug visible here, because the experiment did not produce anything to be wrong. The immediate cause is a missing-data problem: the combined c03 job has not landed in the synced results, and that is an operational thing to chase on the server, not a code defect. There is, however, a real analysis-reader shortcoming worth fixing in the reader function in tests/analysis/firstpass_notready.py. The reader cannot tell the difference between "this combined job was never run or never synced" and "the job ran but crashed" — both collapse into the same bland "no c03 file" line — so it quietly hides the distinction that actually matters to you. On top of that, even when the c03 file does exist, the reader is a very thin view of it: it prints only the per-dataset best model, importance, budget, dimension and score, plus two correlation numbers, and throws away almost everything the experiment computes underneath — the budget variance decomposition that splits budget spread into model effect versus dataset effect versus interaction, the per-model optimal budgets across datasets, and the novel SVR and ElasticNet regressor results that c03 goes to the trouble of fitting. Finally there is one design question for you that only bites once the data is back: a correlation between complexity and budget taken over a small handful of datasets is barely answerable, and c03's own "KEY FINDING" line reduces the whole thing to a single erank-versus-budget rho, which will be noisy unless the combined job spans a genuinely large set of datasets. So: the empty block itself is a sync/run issue, the reader deserves a clearer "missing versus failed" message and a richer c03 view, and the small-sample correlation is a methodology point to settle before you read too much into the eventual numbers.


## c04 — importance scores used as a distance metric

**What the experiment is asking.** This one is not about the hybrid-versus-best-single-rep question at all. It takes every representation for a dataset, glues them into one long concatenated feature vector, and then asks a narrower question: if we score how important each feature is (using a tree or attribution method), can those importance scores be reused as a distance metric? Concretely, it runs a nearest-neighbour regressor two ways. The unweighted way treats all concatenated features as equally important and measures plain Euclidean distance. The weighted way rescales each feature by the square root of its importance before measuring distance, so unimportant features count for less. It does the same thing for a similarity-retrieval predictor. The hoped-for result is that importance-weighting the feature space makes the neighbour predictions better, which would mean "feature importance doubles as a learned similarity metric." A positive delta is a point in favour of that claim.

**What the table shows.** For each dataset the table prints four things: the name of the importance method that gave the best weighted-versus-unweighted improvement for the k-nearest-neighbour predictor ("knn method"), that improvement in R2 ("knnΔ"), and then separately the best method and improvement for the similarity-retrieval predictor ("sim method" and "simΔ"). The delta is defined as weighted minus unweighted, so a plus sign means importance-weighting helped. Classification datasets are skipped outright and print "(clf skipped)". Representative rows: "abagym_lysozyme  lightgbm_gain  +0.470  lightgbm_gain  +0.371" and "abagym_VEGF  deeplift  +0.009  deeplift  +0.001". At the bottom the reader prints a tally: "importance-weighted kNN helps: +31  hurts: -0".

**What it is actually telling us, and why I do or do not trust it.** I do not trust the headline "+31 helps, -0 hurts," and I can show why from the real result files. The number the table prints per dataset is not "does importance weighting help" — it is the best-case improvement picked across the several importance methods that were tried. The experiment itself computes a field called best_knn_method by taking the method with the largest delta, and the reader simply prints that winner. So the column is a maximum over methods, which is structurally biased to look positive. Look at abagym_VEGF: the table reports deeplift at +0.009, essentially a tie. But in the actual JSON the other two methods on that same dataset gave lightgbm_gain at -0.229 and treeshap at -0.195 — both substantial losses. Two of the three methods hurt badly, and the table shows none of that; it shows the single least-bad method. So "hurts: -0" really means "for no dataset did even the best-of-several methods come out negative," which is almost guaranteed by construction and tells us very little.

The magnitudes are also misleading about what "help" means. For abagym_lysozyme the +0.470 improvement decomposes, in the raw file, into an unweighted R2 of -0.40 and a weighted R2 of +0.07. The unweighted baseline is worse than just predicting the average label; weighting only claws it back to barely above zero. So a big delta here is measuring how broken the unweighted baseline was, not how good the weighted metric is. That is exactly what you would expect: plain Euclidean distance over a few hundred concatenated dimensions, most of them irrelevant, is a known-bad baseline, and any supervised down-weighting of noise features will beat it. The experiment is essentially re-discovering the curse of dimensionality, then reporting the fix as a positive finding. Each delta is also a mean of R2 over five folds, and R2 on nearest-neighbour regression swings wildly, so the per-dataset numbers are noisy on top of everything else. The importance is computed per-fold on training data only, so there is no gross label leakage into the validation fold, which is the one thing here I am comfortable with.

**So what is wrong, and whose fault.** Three separate things. First, an analysis-reader shortcoming that is the most important to fix: the reader in read_c04 in tests/analysis/firstpass_notready.py prints only the best-of-methods delta and tallies wins off that single cherry-picked method, so the "+31 helps, -0 hurts" line is not an honest count. It should show the median or the full spread across the importance methods, or at minimum count a dataset as a "help" only if most methods help, not if the best one does. Second, the reader silently throws away two whole sections the experiment computed and saved — the cross-test matrix (select features by method A, weight by method B) and the low-dimensional budget-25 analysis — so the actual "is importance a transferable metric" story never reaches the page. Third, on the experiment side in tests/experiments/complexity/c04_importance_as_metric.py, the design question for you is whether the unweighted all-features Euclidean baseline is a fair comparator at all; beating it is close to automatic, so the experiment as framed cannot really falsify its own hypothesis. Classification being skipped is deliberate and documented in the source (the retrieval predictor averages continuous labels, which has no class-vote equivalent yet), so the "(clf skipped)" rows are honest and fine. One caution worth stating plainly: the single c04 file that synced back into results_server locally (logd.json) has an empty methods list, so if a future report is generated only against the server-synced tree it will show nothing for c04 — the numbers above come from the fuller local complexity results directory, and the server run of this experiment should be re-confirmed as actually populated before anyone trusts a fresh report.


## c05 — learning curves: does the hybrid's advantage grow or shrink as you add data?

**What the experiment is asking.** The intuition being tested is sample efficiency: a hybrid stitches together several representations and then feature-selects among them, so it has more knobs than any single representation. Extra knobs usually help most when data is scarce and can wash out once you have enough rows that even a plain single representation has seen everything it needs. So the question is directional. For each dataset the experiment retrains everything at a ladder of sample sizes — for a small antibody set that ladder is 10, 25, 50, 75 and 100 percent of the rows, for a big one it is capped absolute sizes like 250, 500, 1000, 2000 — and at each rung it runs the full hybrid search and also measures the best single representation. The hybrid would count as "working" here if its advantage over the best single representation is real at small n and, ideally, holds up rather than collapsing as n grows. A hybrid that only ever wins on tiny samples and ties once data is plentiful is a much weaker story than one whose lead is stable.

**What the table shows.** Each row is one dataset. The "model" column is the model the reader decided you would actually deploy, which it defines as whichever model had the best single-representation score at the largest sample size. It then follows that one model down the ladder and reports two endpoints: n_small with its Δsmall, and n_large with its Δlarge, where Δ is hybrid minus best-single after direction correction so that a positive number always means the hybrid is better. "Trend" compares the two endpoints — "grows" if the large-n advantage is bigger than the small-n one by more than 0.01, "shrinks" if it is smaller by more than 0.01, "flat" otherwise. "win@large" is just whether Δlarge itself is positive beyond that same 0.01 band. A representative reaction row reads "buchwald_hartwig  rf  395  +1.176  3955  +0.077  shrinks  yes": at 395 rows the hybrid beat the best single representation by 1.18 RMSE units and at 3955 rows it still won but only by 0.08, so a large early lead that nearly vanished. A representative antibody row reads "abcov_kd  ridge  50  +0.003  141  -0.060  shrinks  no": a tiny positive at 50 rows turning slightly negative at 141. The block footer summarizes the whole set as "advantage grows with n: 3   shrinks: 15   hybrid wins at largest n: 9/22".

**What it is actually telling us, and why I do or do not trust it.** Taken at face value the story is "the hybrid's edge mostly shrinks as data grows, and it still wins at the largest size on 9 of 22 datasets." I believe the direction of that story but I do not trust most of the individual rows, for three concrete reasons. First, the endpoints are frequently within noise. abcov_kd's small-n Δ of +0.003 is well inside the 0.01 tie band — it is effectively zero — so calling that a "shrink" to -0.060 is dressing up a coin-flip small-n value as a starting point. Several antibody rows behave the same way: flab_aggregation_jain goes +0.068 to +0.002, ginkgo_pr_cho +0.097 to -0.005, all "shrinks" whose large-n endpoint is essentially a tie. Second, and worse, there is an outright degenerate row: "abagym_HER2  lightgbm  146  -0.092  146  -0.092  flat  no". The small and large sample sizes are the identical 146, and the two deltas are identical. That is not a learning curve at all — it is a single point printed twice. It happens because the reader locks onto lightgbm (lightgbm had the best single score at the largest n), but lightgbm needs a minimum number of rows before its hybrid value is finite, so at every smaller rung on the server run its hybrid came back as not-a-number and got filtered out, leaving exactly one usable paired point. The "flat" verdict there is an artifact of the model-selection rule, not a finding. Third, every printed number hides an average the reader never shows: each hybrid and each best-single value is itself the mean across subsampling repeat seeds (three seeds at the partial rungs, collapsed to one at the full-data rung by design), and the "best single" is re-chosen from all representations independently at every rung, so the single-representation baseline is an oracle that can be a different representation at each sample size. That oracle re-selection makes the baseline stronger than any fixed representation you would really deploy, which if anything makes the hybrid's job harder — so the wins that survive are at least not flattered. The one row I trust most is buchwald_hartwig, because it is the only reaction set with a genuine multi-rung ladder (395 up to 3955) and real RMSE separation, and it tells a clean, believable story of a big small-data lead decaying toward parity. I cannot reproduce the exact printed numbers locally: this repository's copy of the c05 output only contains a handful of antibody datasets plus a lone molecular logd file, whereas the report shows 22 rows including tz_her2 and several ginkgo tasks that only exist in the server run, so the prelimResults block was generated against the fuller server results directory.

**So what is wrong, and whose fault.** These are mostly analysis-reader problems, one arguable experiment gap, and one design question. The reader shortcoming I would fix first is the collapsed single-point curve: when the deployed model has only one finite paired point after not-a-number filtering, the reader still prints it as a small-and-large pair with a "flat" trend, which is misleading. The reader (read_c05 in tests/analysis/firstpass_notready.py) should either refuse to emit a trend when fewer than, say, three finite rungs survive, or fall back to a model that actually has a full curve rather than blindly taking the best-single-at-largest-n. Relatedly, the reader throws away the middle of the curve entirely — it only ever compares the two endpoints, so a non-monotonic curve that dips and recovers is invisible, and it never prints how many rungs backed the "grows/shrinks" call. The experiment source (tests/experiments/complexity/c05_learning_curves.py) is largely sound and has clearly been hardened already — it caps budgets to the training partition to avoid the old all-NaN-at-small-n failure, samples whole scaffold groups so subsampling does not shatter groups, and re-resolves the model gates at each subsample size — but the genuine gap it leaves is that a model whose hybrid is NaN at the low rungs still gets treated by the reader as a valid deployed model; the experiment could help by recording, per model, how many rungs were finite so the reader can prefer a model with a complete curve. The design question for you is the one the tie-band numbers keep exposing: with small antibody sets the small-n Δ is routinely inside noise, so "advantage shrinks with n" is being inferred from a starting point that is statistically zero. It may be that these tiny datasets simply cannot answer the sample-efficiency question and should be reported as "inconclusive" rather than folded into the 3-grows/15-shrinks tally. That is a judgment call about what counts as an answerable curve, not something the code should decide on its own.


## c06 — within-family capacity gradient

**What the experiment is asking.** Take one model type and build a ladder of it from low capacity to high capacity: random forests at depth 3, 5, 10, and unlimited; ridge from heavily regularised to barely regularised; and so on, seven such families in all. For each rung of the ladder the experiment runs the full hybrid search and records the feature budget that gave the best validation score for that specific model. The hypothesis is that a higher-capacity model should be able to digest more features before it overfits, so as you climb the ladder the winning budget should climb too. The experiment measures that coupling as a Spearman correlation (called rho) between the capacity level and the winning budget, computed separately for each family. A positive rho means "more capacity wanted more features," which is the effect the experiment is looking for. This is a regression-only experiment, because the capacity ladders are hardcoded for regressors, so all the classification datasets are deliberately skipped.

**What the table shows.** Each row is one dataset. The "#fam" column is how many model families the experiment set up for that dataset, which is 7 for most datasets and 6 for the reaction dataset buchwald_hartwig because one family was dropped by the model-gating rules. The "#measured" column is how many of those families actually produced a usable correlation, meaning the family had at least three surviving capacity rungs and its winning budgets took at least two distinct values so the correlation was not mathematically undefined. The "rho range" column shows the smallest and largest of those per-family correlations, printed as a bracketed pair. A representative row reads "abagym_EGFR 7 5 [-0.775,+0.738]", meaning five of the seven families gave a correlation and they ranged from strongly negative to strongly positive. Another reads "buchwald_hartwig 6 5 [-0.894,+1.000]". Many rows instead read like "ginkgo_hic 7 0 --", meaning all seven families were set up but not one produced a usable correlation, so there is no range to print.

**What it is actually telling us, and why I do or do not trust it.** The signal is noise, and I can show why from the source. Each family has exactly four capacity rungs (for random forest they are depth 3, depth 5, depth 10, and depth None), so every rho printed here is a Spearman correlation over just four points. A correlation over four points can only land on a short list of discrete values, and it swings to plus or minus 0.7 or higher on pure chance constantly. The value -0.775 that appears again and again is literally the four-point correlation you get from one swapped pair; it is not a finding, it is an artifact of the arithmetic. This is why a single dataset like abagym_EGFR shows five families spread across the entire range from -0.775 to +0.738 at once: some families say more capacity wanted fewer features, others say the exact opposite, equally strongly, which is what randomness looks like. The experiment does store a p-value for each correlation, and in the underlying data every one of them is far from significant (values around 0.22, 0.37, and 0.74 are typical), but the report never prints the p-value, so a reader would not see how weak these are. The many "0 measured" rows are the small antibody-developability datasets (the Ginkgo panels have on the order of 94 to 242 samples, the flab panels similar), where every capacity rung ends up choosing the same single budget, so the correlation is genuinely undefined and the experiment honestly reports nothing rather than a fake number. There is one important caveat I have to be blunt about: the result JSON files sitting in the local results directory are stale. They use an older schema that has no "status" field on the correlation and only four capacity rungs, and the reader only counts a family when its status equals "measured". Run against the local files the reader would show zero measured everywhere, yet the report shows nonzero counts, so the numbers in this report were produced from newer server-side runs that I cannot open here. I verified the mechanism and the shape of the data from the local files and the source, but the exact rho values in the report I cannot independently reproduce without the server JSONs.

**So what is wrong, and whose fault.** There is no crash and no reader bug producing wrong arithmetic; the pieces do what they claim. The problems are two, of different kinds. The first is a design question for you, and it is the serious one: a Spearman correlation over four capacity rungs is very close to unanswerable, and the experiment's own guard for reporting one is weak (three points and two distinct budgets is enough to print a number that is still essentially noise). Either the capacity ladders in the experiment source, tests/experiments/complexity/c06_within_family_gradient.py, need many more rungs so the correlation has something to bite on, or this experiment should stop reporting a per-family correlation at all and instead just show the budget-versus-capacity curve and let a human eyeball a trend. The second is a smaller analysis-reader shortcoming in read_c06 in tests/analysis/firstpass_notready.py: it computes a median across the families and then throws it away, printing only the outer min and max, and it never surfaces the per-family rho, the number of points behind each rho, or the p-values that would immediately reveal none of these are significant. So even in the unlikely event that one family carried a real effect, the current table would bury it inside a wide range dominated by the noisy families. Before drawing anything from this section at all, the local staleness needs resolving too: the report is running on server data, and the checked-in local JSONs predate the current schema, so anyone re-running the analysis locally would get a misleadingly empty table.


## c07 — best hybrid on easy versus hard slices of the same dataset

**What the experiment is asking.** Take one dataset and cut it into two subpopulations: an "easy" half and a "hard" half. The cut can be made three ways — by how common a scaffold is (frequent scaffolds versus rare ones), by molecular size (small molecules versus large), or by how spread-out the labels are within a scaffold (low target variance versus high). On each half separately, the experiment runs the full hybrid search from scratch and finds the single best-performing hybrid configuration for that half — which downstream model, which feature budget, which importance method. The hypothesis is that the best configuration should depend on how hard the subpopulation is: a harder slice ought to want a different, usually bigger, recipe than an easy slice. The experiment counts the hybrid as "working" here if the tuned configuration genuinely changes between the easy and hard halves, which it records in a flag called config_differs.

**What the table shows.** Each row is one dataset paired with one partition method. The "easy" and "hard" columns are the raw score of the best hybrid found on that half, and the direction of that score depends on the dataset's domain: for the antibody rows (everything starting abagym, plus ginkgo and the tz_her2 rows) higher is better because it is an R-squared or a classification score, while for the reaction row buchwald_hartwig it is an error where lower is better. A cell reads "--" when that half produced no usable best hybrid at all. The last column, cfg_differs, is True when the winning configuration changed between the two halves, and None when one of the halves was missing so no comparison could be made. Two representative rows: "abagym_Ang2  target_variance  0.400  0.684  True" means both halves ran, the easy half scored 0.400 and the hard half 0.684, and the recipes differed; "abagym_Ang2  scaffold_frequency  --  0.485  None" means the easy half produced nothing, only the hard half scored (0.485), and with one side missing there was nothing to compare.

**What it is actually telling us, and why I do or do not trust it.** Three things undermine this table, and I verified all of them against the source and a local result file. First, the score printed is not a plain measurement — it is the maximum over every downstream model, budget, and importance method the search tried on that half, with the experiment picking the single best and discarding the rest. So the easy and hard numbers are each already the top of an independent noisy search, and comparing them tells you very little. Second, and more damaging, the central claim rests on config_differs, and that flag is almost always True whenever both halves exist (abagym_Ang2, abagym_EGFR, abagym_HER2, abagym_VEGF, ginkgo_pr_cho, and tz_her2_multiclass all show True). That is exactly what you would expect from noise: when you take the argmax over dozens of representations crossed with several models, budgets, and importance methods, the winning recipe will differ between any two different data halves almost every time, even if there is no real complexity effect at all. A near-universal "True" is not evidence for the hypothesis; it is what a coin that always lands heads looks like. Third, the scaffold_frequency partition is structurally broken on these datasets: in every antibody row its easy side is "--", and I confirmed why in the local abagym_Ang2 file — the "easy" (frequent-scaffold) half collapses to fewer than two distinct groups, so grouped cross-validation is impossible and the experiment skips it, leaving an empty half and cfg_differs=None. For buchwald_hartwig the same collapse hits the other side (hard is "--"). So scaffold_frequency almost never delivers both halves, which is why nearly all the informative rows come from target_variance instead. On top of that, the target_variance comparison has a confound worth naming: the "hard" half is by construction the high-label-variance scaffolds, and R-squared mechanically rises when the labels spread wider, so hard scoring higher than easy (0.684 versus 0.400 on abagym_Ang2, 11.677 versus 17.227 on buchwald) may be a property of the metric and the split rather than any real behaviour of the hybrid. Finally, the third designed partition, molecular_complexity, never appears in the report at all, because the antibody datasets have no SMILES and the reaction strings do not parse as molecules, so only two of the three intended cuts ever run and one of those two is usually half-empty.

**So what is wrong, and whose fault.** There is a real experiment-level problem in the scaffold_frequency partition: on grouped antibody and reaction data it routinely degenerates to a single dominant group on one side and gets silently skipped, so it produces almost no comparable pairs; this lives in the partitioning logic in tests/experiments/complexity/c07_data_complexity_partitions.py, where the frequency cut needs a guard that it actually leaves two usable, group-diverse halves before it bothers searching. There is also a design question for you that no amount of code will fix: proving that "the optimal config differs" using an argmax over a large, noisy search grid is close to guaranteed to say True, so the config_differs signal as currently defined is not trustworthy evidence — a defensible version would need to show the same model family shifting its budget in a consistent direction, or a stability check across resamples, not just "the single winner changed." Separately, the analysis reader in read_c07 is thin in ways that hide whatever real signal might exist: it prints only one maximized score and a boolean per half, and throws away everything richer the experiment already computed — the per-model best table, the top-3 base reps, the delta_budget it calculates, and the full-data blueprint re-fit scores — and it prints no direction marker, so the easy-versus-hard numbers sit in one column with mixed units and no way to tell which way is better. It also silently drops every dataset whose partitions came back empty (abcov_kd, ginkgo_heparin, the flab rows, humanness_therapeutic all have empty partition dicts because their halves fell below the 50-sample floor), so the table quietly hides how many datasets c07 could not run on at all. None of this needs the server to confirm; the pattern is visible in the local result files and the source.


## c08 — does the winning hybrid give honest uncertainty estimates?

**What the experiment is asking.** When we pick the "optimal" hybrid feature set for a dataset, we usually only judge it on accuracy. This experiment asks a different question: does that optimal hybrid also produce trustworthy uncertainty? It wraps the model in conformal prediction, which builds a prediction interval (for regression) or a set of candidate labels (for classification) that is supposed to contain the true answer 90% of the time. It then measures the actual hit rate, called PICP (prediction-interval coverage probability). If the intervals are honest, PICP should land right on 0.90. The experiment does this not just for the optimal hybrid but also for deliberately bad "underfit," "overfit," and "mismatched" versions, because the underlying hypothesis of the whole complexity paper is that matching model capacity to the data should give the best-calibrated uncertainty. The hybrid "works" here if the optimal condition sits closest to the 0.90 target while the crippled conditions drift away from it.

**What the table shows.** The report table is stripped down to four columns per dataset. PICP is the measured 90% coverage of the optimal hybrid, averaged across the five cross-validation folds. cal_err is the calibration error, defined in the header as the distance from the target, and it is the average across folds of each fold's own gap from 0.90 (lower is better, zero is perfect). The "distinct?" column is a True/False flag that says whether the optimal, underfit, and overfit conditions actually ended up using different feature budgets; when it is False the header warns that "budgets collapsed, contrast meaningless." A representative well-behaved row is "abcov_kd 0.950 0.053 True," meaning the intervals covered the truth 95% of the time instead of the intended 90%, so they are slightly too wide. A representative broken row is "abagym_VEGF 0.692 0.208 True," where the intervals only caught the truth 69% of the time, badly under the 90% they promised.

**What it is actually telling us, and why I do or do not trust it.** Two things stand out. First, the coverage numbers are all over the place, from 0.692 on abagym_VEGF up to 0.950 on abcov_kd, when conformal prediction is mathematically designed to hit 0.90 automatically. The reason it misses is that the guarantee only holds when the calibration data and the test data are interchangeable, and this pipeline uses grouped, leave-cluster-out cross-validation on small antibody datasets, which deliberately makes the test fold come from a different region than the calibration fold. So the numbers in this table are mostly measuring how badly grouped splitting breaks the conformal assumption, not whether the hybrid representation itself is well or poorly calibrated. That is a real and interesting finding, but it is not the finding the column headers imply.

Second, the two number columns are not consistent with each other, and this is easy to misread. PICP is the average of the per-fold coverages, while cal_err is the average of the per-fold distances from 0.90. Because folds bounce above and below 0.90 and then average out, a dataset can show a PICP that looks perfect while cal_err reveals real per-fold wobble. The report's "humanness_therapeutic 0.899 0.024 True" is exactly this trap: the coverage looks flawless at 0.899, but cal_err of 0.024 tells you each individual fold was still off by a couple of points on average. I confirmed the mechanism on the local copy of this dataset, where the five folds ran 0.764, 0.857, 0.943, 0.867, 0.895 — averaging to a tidy 0.865 while every fold individually missed. So cal_err is the more honest column and PICP alone can flatter a dataset.

I have to flag a data-provenance caveat. The local result files under tests/results/c08_calibration are stale: they carry only the older three conditions, their conditions_distinct and total_dim fields are still null, and their optimal-condition numbers do not match the report (local abagym_EGFR optimal PICP is 0.771, the report prints 0.868). The report clearly came from a fresher, server-synced run with sixteen datasets and populated distinct flags. So I verified the schema, the averaging, and the reader logic against source and the local files, but the exact printed values come from data I cannot open here.

**So what is wrong, and whose fault.** The experiment code itself is not crashing — the old NameError bugs on the regression path and the classification-without-probabilities path are fixed and commented as such. The real problem is a design one for you to weigh: conformal prediction on top of grouped cross-validation cannot deliver its coverage guarantee, so PICP here is confounded by distribution shift and the small calibration sets (as few as 20 points), which makes the quantile noisy. That belongs in the experiment source, tests/experiments/complexity/c08_calibration.py, if you decide the calibration claim needs to hold under leave-cluster-out splits.

The bigger complaint is with the reader, read_c08 in tests/analysis/firstpass_notready.py. The experiment computes four conditions specifically to test "optimal calibrates best," but the reader prints only the optimal condition and throws the underfit, overfit, and mismatched numbers on the floor. That means the table cannot answer the question the experiment was built to answer — and the source comment even notes that on EGFR the underfit condition calibrated best, the opposite of the hypothesis, which no reader column would ever reveal. On top of that, the "distinct?" flag is dead weight as printed, because it only matters for the optimal-versus-suboptimal contrast that the reader does not show. I would change the reader to print all the conditions side by side, or at least optimal versus overfit, and to carry the fold count and per-fold spread so the PICP-versus-cal_err inconsistency is visible rather than hidden. As it stands this table shows that our winning hybrids are roughly but not reliably calibrated, and it silently withholds the actual complexity-matching comparison.


## c09 — where does the hybrid's score come from: the model, the feature budget, or their interaction?

**What the experiment is asking.** This experiment does not test whether the hybrid wins. It takes the full grid of results that experiment c02 already produced — every downstream model crossed with every feature budget — and asks a bookkeeping question about that grid: of all the variation you see in the scores, how much is explained by which model you picked, how much by how many features you allowed, and how much by the two of them interacting (some models only doing well at some budgets). It reports each of those three as a percentage of total score variance, a statistic called eta-squared. The intended story, written into the source file's own header, was "model explains 50 percent or more, budget 25 percent or more, interaction 10 percent or more." So "working" here would mean the choice of model and budget clearly dominates the outcome. Nothing about this sub-analysis is about the hybrid beating the best single representation; it is a variance-accounting exercise on top of c02's numbers.

**What the table shows.** The report prints one row per dataset with three columns: eta_model, the percentage of score variance attributable to the choice of downstream model; eta_budget, the percentage attributable to the feature budget; and eta_inter, the percentage attributable to the model-by-budget interaction. Two representative rows, quoted verbatim: "abagym_EGFR  7.1  2.1  2.7" and "flab_polyreact_jain_cic  21.6  5.5  1.4". Some rows carry no numbers at all — "buchwald_hartwig  (no anova)" — which the reader prints whenever the stored result has no usable ANOVA block.

**What it is actually telling us, and why I do or do not trust it.** The numbers land nowhere near the story the experiment set out to tell. On abagym_EGFR the three factors add up to about twelve percent (7.1 plus 2.1 plus 2.7); on the strongest row, flab_polyreact_jain_cic, model reaches only 21.6 percent and the three together are under thirty. The reason is a column the reader silently drops: residual variance. I opened the stored JSON for abagym_EGFR and the residual is 88.1 percent — the vast majority of the variation is "none of the above." That residual is not a mystery, it is a construction artifact. The ANOVA has only two factors, model and budget, but the c02 grid it is fed varies far more than that: allocation method, importance method, internal evaluator, the general-versus-top tier, and the augmentation condition, each measured over five folds. In this dataset that is roughly 397 separate measurements crammed into each of the 56 model-by-budget cells (22,225 observations over 8 models times 7 budgets). All the variation driven by those un-modelled knobs, plus fold-to-fold noise, gets swept into the within-cell "residual" bucket, which is why residual swallows almost everything and the two named factors look tiny. So eta_model of 7.1 does not mean "the model barely matters"; it means "the model explains 7 percent of a pie that is dominated by hyperparameters this two-factor model never named." Separately, the significance test is meaningless here: because there are twenty-thousand-plus observations, every F-statistic is enormous and every p-value in the JSON is pinned at machine-epsilon (1.1e-16) for model, budget and interaction alike — everything is "significant" and the p-values carry no information. The "(no anova)" rows are a different phenomenon: the ANOVA exists only when c02's grid was handed to c09 as a dependency, so a blank row means c02's output was not available for that dataset when c09 ran, not that the analysis was attempted and failed. One more caveat on trust: the local copies of these JSONs are from May and store the grand mean under the old key name "grand_mean_r2", whereas the current source writes "grand_mean_score"; the eta-squared values themselves are unaffected, but it confirms these files predate the current code and the report was generated against a fuller results tree than exists on this machine (twelve datasets in the report, nine locally).

**So what is wrong, and whose fault.** The core problem is an experiment-design issue, and it sits in the source file tests/experiments/complexity/c09_formal_analysis.py, in _run_anova_decomposition. It pours the entire multi-knob c02 grid into a two-factor model and treats every allocation, importance, evaluator, tier and augmentation variant as an interchangeable replicate of the same model-by-budget cell. That guarantees a huge residual and shrinks the two reported effects toward zero, so the printed eta-squared numbers cannot be read the way the header promises. Either the extra knobs need to be named factors in the decomposition, or the grid needs to be reduced to one blueprint per cell before the variance is split — that is a design decision for you, not something I would change unilaterally. The p-values are a second experiment-level issue: at this sample size they are structurally always zero, so they should not be leaned on at all. There is also a real analysis-reader shortcoming, in read_c09 in tests/analysis/firstpass_notready.py: it prints model, budget and interaction but hides the residual, which is by far the largest term and the one that actually explains why the other three look small. Anyone reading the report sees "7.1, 2.1, 2.7" and has no way to know 88 percent is unaccounted for. The reader should show the residual (or at least the row total) so the three percentages are interpretable, and it could distinguish a genuinely absent dependency from an errored one rather than printing a bare "(no anova)". None of this is a crash or a divide-by-zero; the pipeline runs and the arithmetic is correct. The issue is that the thing being measured is not the thing the header claims, and the reader omits the one number that would make that obvious.


## c10 — noise robustness: does the hybrid degrade more gracefully as we corrupt the labels?

**What the experiment is asking.** Take a regression dataset and deliberately add noise to the training labels at increasing strengths (sigma running from 0.0 up to 0.6), using a few different noise recipes. Retrain and watch how the test score falls off as the noise gets worse. Each rep, and each hybrid, therefore has a whole degradation curve rather than a single score. The experiment boils each curve down to one number called auc_norm, which is essentially the area under the retention curve, normalised so that higher always means "held up better as the noise got worse" regardless of whether the underlying metric is higher-better or lower-better. The hypothesis is that a hybrid, because it draws on many representations rather than one, should be more resilient to garbage in the labels. The hybrid would count as "working" here if its best auc_norm came out meaningfully above the best single rep's auc_norm.

**What the table shows.** The intended columns are: rep_auc, the robustness score of the best single representation; hyb_auc, the robustness score of the best hybrid; the difference between them (a positive difference means the hybrid was tougher); and a plain "more robust?" verdict of yes, no, or roughly tied. In practice the whole table is blank. Every row reads the same. Quoting verbatim: "abagym_Ang2  --  --  --  ~" and "flab_polyreact_jain_bvp  --  --  --  ~", and the footer says "hybrid more robust: +0  ~0  -0  (8 datasets)". Only eight datasets appear at all, all in the antibody section, and not one of them produced a number.

**What it is actually telling us, and why I do or do not trust it.** This experiment never ran. I opened the actual result files, and every single one is a tiny stub containing an error and nothing else: for example abagym_Ang2 holds only a timestamp and the message "noiseInject not installed". That same message is in all eight files in the local results folder, dated across early-to-mid May, and it is also in the June copies under the complexity results folder. The reason is right at the top of the experiment source: c10 needs an optional third-party package called noiseInject to generate the corrupted labels, and if that package is not importable the whole run bails out immediately before computing anything. So the blanks are not a divide-by-zero or a saturation problem in the science; they are simply the absence of a dependency on whatever machine produced these files. On top of that, only eight or nine datasets even have a c10 file at all, versus roughly forty that show up in other experiments, so most of the survey never so much as attempted this experiment. There is nothing here to trust or distrust numerically, because there are no numbers.

There is a second, quieter problem I want to flag even though it does not change today's blank result. When c10 does run, the reader computes each side of the comparison by taking the maximum auc_norm over every configuration on that side: the "best single rep" is the most robust rep across all three noise recipes, and the "best hybrid" is the most robust hybrid across all feature-budgets and all three recipes. That is a maximum-of-a-maximum on both sides. Picking the single luckiest curve on each side inflates both scores and quietly cherry-picks the noise recipe, so even once the data exists this particular head-to-head will read more favourably than a like-for-like comparison would. Worth knowing before anyone reads a future filled-in version of this table.

**So what is wrong, and whose fault.** The headline issue is an environment and operations problem, not a bug in the experiment logic or the reader: the noiseInject package was never installed on the machines that ran c10, so every result is an error stub, and the survey needs a re-run with that dependency present before this row means anything. There is also a staleness issue worth naming precisely. The current experiment source, when the package is missing, returns a clean "skipped" record with the reason "noiseInject_unavailable"; the files on disk instead carry an older "error" wording. And the current reader, when I run it against these files, actually prints "(0 datasets)" and no rows at all, because it skips any file whose representation and hybrid blocks are empty. The report in prelimResults, by contrast, shows eight dashed rows and "(8 datasets)". In other words the report was generated by an earlier version of the reader than the one in the file today, so this block is doubly out of date: both the stored results and the reader that printed them have since moved on. The concrete fixes live in two separate places. Installing noiseInject and re-running is an operations task on the server, not a code change. Separately, in the reader function read_c10 in tests/analysis/firstpass_notready.py, I would have it explicitly recognise and surface these dependency-missing files as "skipped: noiseInject unavailable" so the table plainly says why it is empty instead of showing mute dashes, and I would reconsider the maximum-over-all-recipes-and-budgets comparison before anyone reports real c10 numbers. The experiment source itself, tests/experiments/complexity/c10_noise_robustness.py, is fine as written and does not need changing for this.


## c11 — one model on the fused hybrid, versus that same model on its best single representation and on a PCA-squeezed concatenation

**What the experiment is asking.** Pick one downstream model at a time. Give it three different feature inputs and see which wins. The first input is the single best representation on its own: train the model on every representation separately and keep the best score. The second is a dimension-matched control: glue all the representations together into one wide block, use PCA to squeeze that block down to a fixed number of components, and train on that. The third is the hybrid: the feature-selected mixture of representations that KIRBy actually builds. The hypothesis KIRBy is defending is that the hybrid beats both the best single representation and the PCA control, using the same model, so that the win comes from KIRBy's feature selection rather than from just having more model or more raw dimensions. (An older fourth arm that averaged predictions across per-representation models was deliberately deleted, because the group does not allow averaged baselines as a comparator; the experiment name still says "ensemble" for continuity only.)

**What the table shows.** The report prints one row per dataset. The "model" column is the model that was deployed, and it is chosen as the model with the best single-representation score, not the model with the best hybrid. The "single" column is that model's best score over all representations. The "pca_cat" column is that model's best score from the glue-everything-then-PCA control. The "hybrid" column is that model's best hybrid score. The "Δvs_single" column is hybrid minus single, corrected for metric direction, and since every dataset here is antibody where higher is better, a positive delta means the hybrid scored higher. The "verdict" applies a plus-or-minus 0.01 dead-band: above it is WIN, below it is LOSS, inside it is tie. Two rows read verbatim: "abagym_Ang2  svm  0.380  0.339  0.428  +0.048  WIN" and "flab_pk_jain_fcrnrt  ridge  0.595  0.450  0.421  -0.174  LOSS". The saturated case reads "humanness_therapeutic  svm  0.911  0.901  0.914  +0.003  tie", and the bottom line is "hybrid vs best single rep: +2 better  =1 tie  -8 worse (11 datasets)".

**What it is actually telling us, and why I do or do not trust it.** Every dataset in this section is antibody, so what we are really reading is "on antibody regression and a couple of antibody classification tasks, does the hybrid help?" and the answer here is mostly no: the hybrid loses on eight of eleven, ties on one, and wins on only two, and the two wins (abagym_Ang2 at +0.048 and abagym_EGFR at +0.015) are small while some losses are large (flab_pk_jain_fcrnrt at -0.174, abcov_kd at -0.135, flab_polyreact_jain_cic at -0.103). That looks like a real negative lean for the hybrid on antibody, and it is made more damning by the fact that the hybrid is being handed a quiet advantage: the reader does not print a single hybrid number, it prints the best hybrid over all the searched feature budgets, and likewise the best PCA over all budgets. So the hybrid gets to cherry-pick its best budget and still loses most of the time. That said, I do not trust the individual row verdicts, because these are R2 scores averaged over grouped cross-validation folds on very small antibody datasets, and the fold-to-fold scatter is enormous. In the local result files the per-fold standard deviations on these hybrid scores routinely sit between about 0.15 and 0.26, which on five folds is a confidence interval wider than almost every delta in the table. A 0.01 tie band against roughly 0.2 of fold noise means the WIN/LOSS labels are essentially coin flips; the aggregate lean (hybrid rarely helps antibody) is more believable than any single row. The humanness_therapeutic row is a different story: single is already 0.911, so the task is near its ceiling and there is simply no headroom for the hybrid to move, which is why it ties. One honest caveat: the report I am reading was generated from a fuller, server-synced result set of eleven datasets that includes ginkgo_heparin and flab_pk_jain_fcrnrt, and those files are not present locally. The two local copies of this experiment's output hold only nine datasets and carry different hybrid numbers (local abagym_Ang2 svm hybrid comes out at 0.497, not the report's 0.428), so I cannot reproduce the exact printed figures here, and confirming them needs the server data.

**So what is wrong, and whose fault.** On the experiment side there is nothing broken in the logic; the budget list is now aligned to the precompute budgets, the PCA control is honestly built, and the only smell is minor (one representation, "structural", silently returns a not-a-number score for at least one dataset, which just drops a dead representation from the single-rep pool). On the reader side there are three real gripes. First, the hybrid and PCA columns are each a hidden maximum over feature budgets, and the header only discloses the model-selection rule, not this max, so a reader thinks they are looking at one hybrid when they are looking at the best of several; I would either print the winning budget or drop the max, in the read_c11 function. Second, the reader throws away everything the experiment actually measured beyond the score: the standard deviations, the fit and inference times, the dimensionality, the model counts, and the top-3 base representations. Printing at least the fold standard deviation or a confidence interval would make the noise visible instead of hiding it, and that is the single most useful change, again in read_c11. Third, the reader locates the results directory by first-match on the folder basename, and there are two local folders with the same name but different contents, so which one is read depends on filesystem walk order, which is a reproducibility hazard worth pinning down. The genuine design questions for you are: this experiment only ever produces antibody rows, so is c11 intended to be antibody-only or are the molecular, reaction, and tcga runs simply missing and never synced; the deployed model is chosen by its single-representation score and the hybrid is then constrained to that same model, which is a defensible "deploy the model that already won on your reps" story but it hides whether the hybrid would have helped a different model; and given fold noise near 0.2 on datasets this small, a 0.01 tie band and per-row WIN/LOSS verdicts are probably not answerable without more folds or a paired test.


## c12 — modality ablation on TCGA (does stacking omics layers beat the best single omics layer?)

**What the experiment is asking.** This experiment only makes sense for the cancer-genomics (TCGA) datasets, where a single sample has several completely different measurement types, called modalities: gene expression, DNA mutations, DNA methylation, and so on. The question is whether combining modalities helps. The experiment first finds the single best representation inside each modality, then glues pairs of those best-per-modality representations together side by side, and finally glues all of them together at once. For each combination it records how much the score moved relative to the best single modality on its own. The hybrid "works" here if concatenating modalities lands above the best individual modality, meaning the extra measurement types genuinely added signal rather than just noise and width. Note that the score used is always the higher-is-better kind (R-squared for regression, AUROC or F1 for classification), and the experiment refuses to run on anything that is not a TCGA dataset — the source file raises an error the moment it sees a non-TCGA domain.

**What the table shows.** When results exist, the reader is designed to print one row per TCGA dataset with three things: "all_comb Δ", which is the change in score from throwing every modality together versus the best single modality; "best_pair Δ", which is the best change found across all two-modality pairings; and a "helps?" flag that reads "yes" if the all-combined change clears a small tie threshold, "no" if it falls below the negative of that threshold, and "~" if it is essentially a wash. In this run, though, none of that prints. The entire c12 block in the report is a single line quoted verbatim: "(no c12 files)". There are no rows, no columns, no numbers at all.

**What it is actually telling us, and why I do or do not trust it.** The empty block is not a bug in the reader and it is not a blown-up number — it is honest. The reader looks for an output directory named exactly `c12_modality_ablation`, and there is no such directory anywhere in the results tree it was pointed at; I confirmed that by walking the whole repository. What does exist on disk is a directory called `c12_adaptive_pruning`, holding just two files (`logd.json` and `tcga_brca_pam50.json`) dated back in February, and their contents are a completely different experiment: they store fields like `full_search_n_results`, `pruning_analysis`, and `thresholds_tested`, which are about pruning weak models during a search, not about combining omics modalities. In other words the "c12" slot was repurposed. It used to be an adaptive-pruning experiment, those stale February files are the leftover, and the slot was later rewritten into the modality-ablation experiment that lives in the source today. That new modality-ablation code has never been run, or at least its output was never synced back here, so there is simply nothing under the name the reader now expects. I trust the emptiness completely; there is no signal hiding behind it. It is also worth flagging, for whenever this does get run, that the printed delta is doubly optimistic: behind each single number the experiment already takes the best score across all models, and the reader's "best_pair Δ" additionally takes the largest delta across every pairing, so a positive value there could be the luckiest of many comparisons rather than a stable effect.

**So what is wrong, and whose fault.** Nothing is broken in the analysis reader — showing "(no c12 files)" for a missing directory is the correct behavior. The real issue is an experiment and bookkeeping problem: the c12 name was reused for two different experiments, the old adaptive-pruning output was never cleared out, and the current modality-ablation experiment has not produced any fresh output under its own name. So the fix is operational rather than in code: this experiment needs to actually be run on the TCGA multi-omics datasets and the results synced back, and the stale `c12_adaptive_pruning` directory should be removed so it stops being a red herring. There is one design point worth raising with you, though not a defect: because c12 is explicitly TCGA-only and refuses every other domain, it will never contribute rows for the molecular, reaction, or antibody datasets that dominate the rest of this report, so even a fully successful run will light up only a handful of cancer-genomics rows. That is by design, but it is worth knowing before treating an empty c12 as a failure of the wider sweep.


## c13 — forward compatibility: does a brand-new representation earn its place in the hybrid?

**What the experiment is asking.** This is the experiment that speaks directly to the core thesis. The claim KIRBy wants to make is that when a new representation appears — a fresh protein language model, a new structural embedding — you can drop it into the hybrid and the hybrid gets better, without having to redesign anything. The honest difficulty is that adding any extra column of numbers, even pure noise, lets the feature-selection search cheat a little and look better on the same data it was tuned on. So c13 does not just compare "hybrid with the new rep" against "hybrid without it." For each new representation it builds a fifth condition: the same hybrid but with a random-Gaussian matrix of exactly the same width standing in for the new rep. The new rep only gets credit when the real hybrid beats that random-matrix hybrid. That debiased gain — the score with the real rep minus the score with the same-sized noise matrix — is the number that would count as the hybrid genuinely "working." A second number, the hybrid-with-the-new-rep score minus the new rep's own best single-model score, asks the companion question of whether hybridising actually helps the new rep rather than dragging it down.

**What the table shows.** The report is meant to print, per dataset and per new representation, two columns: "D-Drandom", the debiased gain just described, and "D-B", whether the hybrid beats the new rep on its own, plus a "helps?" verdict of yes, no, or a tilde for undecided. Underneath each dataset it prints two win-rate summaries, and at the very bottom a tally of how many new reps showed a real debiased gain. In practice every single cell is blank. A representative dataset block reads, verbatim:

```
  --- abagym_EGFR (antibody) ---
                        ablang2                      --       --  ~
```

and closes with:

```
                        win_rate D>Drandom=None  D>B=None
```

Every listed representation — ablang2, esm3, saprot, the esm2 variants, and the rest — shows the same two dashes and a tilde, across all ten datasets that are present locally (nine antibody datasets plus buchwald_hartwig on the reaction side). The final line of the whole section reads "new reps with a real (debiased) gain: 0/0."

**What it is actually telling us, and why I do or do not trust it.** The dashes are not telling us the new reps failed. They are telling us the report is reading result files that were written by an older version of the experiment. I opened one of the local JSON files, abagym_EGFR, and it was produced on the 17th of May. Inside, each representation genuinely has numbers — for example ablang2 records a real "D_minus_C" gain of about +0.004 — but they live under the old naming. That old file has five conditions labelled A through E, and its deltas are called "D_minus_C" and "E_minus_B", with a summary that reports "win_rate_D_vs_C" and "win_rate_E_vs_B". Since then the experiment was rewritten: condition E was deleted as redundant, the random-Gaussian null was added as the new fifth condition, and the deltas were renamed to "D_minus_D_random" and "D_minus_B". The reader was updated to the new scheme and now asks each file for "D_minus_D_random" and "D_minus_B". Those keys simply do not exist in the May files, so every lookup returns nothing and prints a dash, and the summary lookup for "win_rate_D_vs_D_random" returns nothing and prints None. The 0/0 at the bottom is the same story: the reader only counts a rep when the debiased delta is a finite number, and since none are, the denominator never leaves zero. So the emptiness is fully explained by a schema change that the local files predate — it is not a divide-by-zero, not a domain that c13 skips, and not a crash in the experiment. There is nothing here to trust or distrust numerically yet, because none of the current experiment's numbers have been computed and synced. It is also worth noting that even the old data that does exist would be partly hidden on purpose: the redesign deliberately stopped showing "D minus C" because that comparison is biased upward by construction, so the reader would refuse to display the one delta these old files actually contain.

**So what is wrong, and whose fault.** Nothing here is a live bug in either the experiment or the reader; they are simply out of sync with the data on disk. The fix is operational, not a code change: c13 needs to be re-run on the server with the current source so it emits files carrying the "D_minus_D_random" and "D_minus_B" fields, and those files need to be synced down before this section can say anything. There is one small robustness gap worth naming, and it lives in the reader function read_c13 in tests/analysis/firstpass_notready.py: when it meets a file whose per-rep entries exist but whose delta keys are all missing, it silently prints a wall of dashes and a 0/0, which reads exactly like "we ran it and nothing helped" rather than "these files are stale." A one-line guard that recognises the old key names, or that notices per-rep is populated while every delta is absent, and prints "stale schema, re-run needed," would stop this from being mistaken for a real null result. That is a reporting nicety, not a correctness problem. There is also a genuine design question for you buried underneath, but it cannot be judged until fresh data lands: whether the random-Gaussian null, evaluated over only a handful of non-independent cross-validation folds, is a stable enough baseline that a small debiased gain means anything. Hold that thought until the server files come back.


## c15 — machine-learning-theory depth: the "double descent" stability probe

**What the experiment is asking.** There is a well-known result in machine-learning theory (double descent) that says a model gets *most* unstable exactly when the number of features it is given is roughly equal to the number of training examples it has. Below that point and well above it, performance is calm; right at the crossover it can swing wildly. The c15 experiment asks whether KIRBy's hybrid feature-selection suffers from this instability more or less than a plain PCA baseline. Concretely, for each dataset it sweeps the hybrid's feature budget across the danger zone where the number of features is near the number of samples, records the cross-validated score at each budget, and measures how much the score bounces around. It does this for the hybrid and for PCA and reports a single "instability ratio" for each. The hybrid would count as "working" here if it were no more jumpy near that crossover than PCA is, ideally calmer. The experiment header even says "lower is better" for this ratio, meaning less bounce is the good outcome. The whole thing is gated to regression datasets only, which is why every dataset listed is an antibody or reaction task and there are no classification datasets in the block.

**What the table shows.** The report prints one row per dataset with three visible pieces of information. The column "inst_hybrid" is the instability ratio for the KIRBy hybrid; "inst_pca" is the same ratio for the PCA baseline. Under the hood each ratio is defined as the variance of the scores at budgets *near* the sample count, divided by the variance of the scores at budgets *far* from the sample count, so a big number is supposed to mean "much more jittery near the crossover than elsewhere." The last column, "sub-analyses," just lists which of four theory sub-probes were present in the file (distance concentration, kernel analysis, double descent, approximation theory); it is a presence check, not a result. Two representative rows read: "abagym_HER2  24340436.265  604514.127  distance_concentration,kernel_analysis,double_descent,approximation_theory" and "abagym_EGFR  0.040  0.012  distance_concentration,kernel_analysis,double_descent,approximation_theory". Two rows show nothing at all: "buchwald_hartwig  --  --" (with all four sub-analyses present) and "humanness_therapeutic  --  --" (with no sub-analyses listed).

**What it is actually telling us, and why I do not trust it.** These numbers are not measuring instability; they are an artifact of a divide-by-almost-zero. I traced the arithmetic against the real result files. The experiment now chooses its sweep budgets at exactly 0.8, 0.9, 1.0, 1.1 and 1.2 times the sample count. The instability formula then splits those budgets into a "near" bucket (between 0.7 and 1.3 times the sample count) and a "far" bucket, and divides the near-bucket variance by the far-bucket variance. But every one of the five chosen budgets lands inside the 0.7-to-1.3 window, so the "far" bucket is always empty. When the far bucket is empty the code substitutes a floor value of one ten-billionth for the missing variance, and the ratio becomes the near-bucket variance multiplied by roughly five billion. I reproduced this exactly on the local copy of abagym_HER2: the five budgets are 116, 131, 146, 160, 175 against 146 samples, all five sit in the near window, zero land in the far window, the near-bucket score variance is about 0.0002, and dividing it by the tiny floor yields 1021046, which is the same scale as the report's HER2 value and whose PCA companion (604514.127) matches the report to the digit. So the enormous numbers like abagym_HER2's 24340436.265, flab_polyreact_jain_cic's 8316387.872, and abagym_Ang2's 1372983.914 are not signal; they are a fixed constant times a very small variance. The apparently reassuring small numbers are the same artifact seen from the other side: abcov_kd's inst_pca of 0.000 and flab_immunogenicity_marks's inst_pca of 0.000 do not mean "perfectly stable and good," they mean the PCA scores were literally identical at all five near-crossover budgets, which is itself a saturation artifact because PCA runs out of components once the budget exceeds the feature-pool width. The one genuinely sane-looking row, abagym_EGFR at 0.040 and 0.012, appears to be a leftover from an older wider-budget version of the experiment that still had a populated far bucket; I cannot fully confirm that split of old-versus-new files without the server's copies, but the mechanism itself is proven locally. The one thing that is faintly usable is the *comparison between the two columns* on a blown-up row, since both share the same five-billion multiplier and it cancels: HER2's hybrid being about forty times its PCA figure does say the hybrid's score wobbled more than PCA's across those five budgets. But the absolute magnitudes, and the experiment's own "greater than 2 means UNSTABLE" verdict, are meaningless because that threshold now fires on essentially everything. The two blank rows have separate causes. buchwald_hartwig ran the double-descent probe (all four sub-analyses are present) but never wrote an instability ratio, which happens when fewer than two budgets survive into the near window after the budget-versus-feature-width clamp trims them, plausible for a reaction dataset with narrow feature pools. humanness_therapeutic shows blanks *and* no sub-analyses at all, so its file is a partial or stale one that never wrote the theory blocks; the local copy of that dataset does contain them, so the server file differs and I would want to see the server copy to say more.

**So what is wrong, and whose fault.** The primary problem is an experiment bug, not an analysis bug, and it lives in the double-descent routine in tests/experiments/complexity/c15_ml_theory_depth.py. The budget grid was narrowed to only 0.8 through 1.2 times the sample count, but the instability formula it feeds still assumes there are budgets both near and far from the crossover to compare. With no far-away budgets the ratio degenerates into a tiny variance divided by a floor constant, and every large value in this table is that division. This needs the two pieces made consistent again: either the sweep has to include budgets well below and well above the crossover so the "far" bucket is genuinely populated, or the instability measure has to be redefined so it does not depend on an empty bucket and does not fall back to a ten-billionth denominator that manufactures million-fold outputs. That is a real design decision for you, because it is a question of how the double-descent claim should actually be quantified, and it should not be patched silently. There are also two analysis-reader shortcomings in read_c15 in tests/analysis/firstpass_notready.py. First, the reader prints the raw ratio with no sanity guard, so a value of twenty-four million is shown with the same calm formatting as 0.040 and reads as if it were a legitimate quantity; it should at minimum flag when the far bucket was empty. Second, the reader throws away almost everything the experiment computed and reduces a four-part theory experiment to two numbers: it shows only the names of the sub-analyses, never their contents, and it completely ignores the ridge-regression double-descent probe (the ridge-on-hybrid versus ridge-on-PCA curves) that is the actual Bartlett-Belkin interpolation test the experiment was built around. So even once the instability formula is fixed, the reader would still be hiding the most theory-relevant output. My recommendation is to treat the whole c15 block as not-yet-trustworthy: the experiment's headline metric is broken by construction, and the reader is not surfacing the parts that might still be salvageable.


## c16 — is the hybrid's edge just a feature cap in disguise?

**What the experiment is asking.** The suspicion behind this experiment is uncomfortable but fair: maybe the hybrid does not win because it picks a *smart* subset of features, but simply because it uses *fewer* features, and using fewer features is itself a crude form of regularization. Any model can be regularized directly — you can crank up ridge regression's L2 penalty, or cap a random forest's depth, or lower an SVM's C — so the honest question is whether feature selection buys you anything that you could not already get for free by dialing up regularization on the full feature set. For each model family (Ridge, Random Forest, SVM, and Logistic Regression for classification) the experiment compares two things: a "simple hybrid," which is the model at its default middle-of-the-road regularization but allowed to pick its best small feature budget, versus a "best tuned full-dim" model, which keeps the large feature budget but is allowed to pick its best regularization strength. If the small-budget hybrid still wins, the claim is that selection adds something beyond what regularization alone could do. If it loses or ties, the skeptic is right.

**What the table shows.** The table lists, per dataset and per model family, three columns: `hybrid` is the score of the simple-hybrid (default regularization, best small budget), `tuned_full` is the score of the tuned full-budget model (best regularization, largest budget), and `wins?` is True when the hybrid beat the tuned full model in the correct direction for that domain (higher is better for antibody Spearman and classification AUROC, lower is better for the reaction error metric). One representative antibody row reads "abagym_HER2 Ridge 0.169 0.004 True," meaning the small-budget ridge hybrid scored 0.169 Spearman while the best-regularized full-budget ridge scored essentially zero at 0.004, so the hybrid won. A representative reaction row reads "buchwald_hartwig Ridge 19.081 19.750 True," where the numbers are an error metric so the smaller 19.081 wins. The classification dataset is a special case: "humanness_therapeutic LogReg 0.948 -- None" shows the hybrid AUROC of 0.948 but a blank tuned-full column and no win verdict, because the full-budget comparison score was never produced. The block closes with a raw tally: "selection beats regularization-only (hybrid_wins): 12/27 family-cases."

**What it is actually telling us, and why I do or do not trust it.** The headline number is that selection beats regularization in only 12 of 27 family-cases, which is below half, so on this evidence the skeptic is largely right — for most model/dataset pairs, letting the model pick its best regularization on a large budget matches or beats the small-budget hybrid. But I do not trust the comparison as framed, for three concrete reasons. First and most serious, the "full-dim" baseline is not actually full-dimensional. The code sets the largest budget to the smaller of the true dimensionality, twice the sample count, or a hard 2048 cap, and for these datasets the true dimensionality is enormous — abagym_HER2 has a total of 11,704 features and humanness_therapeutic has 48,288 — so the "no selection" baseline is in fact a hybrid that already selected down to 2048 features. The experiment is therefore comparing aggressive selection against mild selection, not selection against no-selection, which guts the premise. The source code even flags this itself in an "OTHER-27" comment and records a `budget` and `is_capped` field, but that caveat never reaches the printed table. Second, many of the numbers are simply too small and too noisy to carry weight: abagym_HER2's tuned-full ridge score of 0.004 is a Spearman correlation indistinguishable from zero on a small antibody dataset, so a "win" of 0.169 over 0.004 is a win over noise, and abcov_kd loses on all three families with scores clustered in the 0.3–0.4 band that these small antibody sets swing through by chance. Third, both sides of each comparison are quietly cherry-picked in asymmetric ways — the hybrid score is the best over roughly six feature budgets while holding regularization fixed at the middle value, and the tuned-full score is the best over four-to-six regularization levels while holding the budget fixed at the cap — so each column is a max over a different axis, which biases both upward and makes a one-versus-one "wins?" flag a coin-flippy readout. Two further honesty notes: the coverage is thin and lopsided (nine antibody datasets plus one reaction dataset, with no molecular, TCGA, or genomic datasets present at all), and the local result JSONs I inspected disagree slightly with the report's numbers (locally HER2 ridge reads 0.160 versus 0.017, and humanness's tuned-full is filled in rather than blank), which tells me the report was generated from a newer server-side run than the JSONs on disk; confirming the exact provenance and the blank classification cell needs the server files.

**So what is wrong, and whose fault.** These separate into three buckets. The experiment bug worth chasing is the blank classification column on humanness_therapeutic: the tuned-full score came back as not-a-number, which happens in the source when the blueprint at the top budget was never built, and the code has an explicit `capped_full_error` field precisely to make that diagnosable — someone should read that field from the server JSON to see whether the fast search at the capped budget failed, rather than silently printing a dash. The reader shortcomings live in the analysis function `read_c16` in `tests/analysis/firstpass_notready.py`: it labels the second column "tuned_full" and never prints the `budget` or `is_capped` fields that the experiment already stores, so the reader actively hides the fact that "full" is capped at 2048 out of tens of thousands of features; it also throws away the two other analyses the experiment computes and saves — the regularization-sensitivity-versus-budget curve and the L2-equivalence estimate — which are arguably the more interesting outputs, and surfaces only the single binary win. The design questions for you are the deeper ones and belong in the experiment source `tests/experiments/complexity/c16_feature_selection_as_regularization.py`: whether a comparison against a 2048-feature "full" baseline can answer the question at all when the real feature space is 12k–48k wide, whether the asymmetric best-over-budget-versus-best-over-regularization framing should be replaced by something symmetric, and whether family-case counting on ten datasets (nine of them antibody) is enough coverage to say anything. As it stands the experiment is not fine — the numbers are real but the baseline does not mean what its name says, so the 12/27 tally should not be quoted as evidence either way until the "full-dim" baseline is genuinely full-dim or explicitly relabeled as a mild-selection control.


## c17 — information density: does the hybrid pack in more information or just more columns?

**What the experiment is asking.** When the hybrid stacks many representations together and then feature-selects a budget of columns out of that pile, is it genuinely picking columns that carry information about the target, or is it just grabbing a lot of columns and looking impressive because there are more of them? To test this, c17 takes the same feature budget (10, 25, 50, 100 columns) and fills it five different ways: the hybrid's own selection, PCA, mRMR, RFE, and a random draw. For each one it estimates the mutual information between the selected columns and the label using a k-nearest-neighbour estimator, then divides that by the number of columns to get an "information density" — information per feature. The hybrid would count as "working" here if its density sits well above the random draw's density, meaning its columns actually earn their place rather than diluting the set. This experiment only runs on regression datasets; classification datasets are deliberately skipped.

**What the table shows.** Each row is one dataset. The `best_strat` column names whichever of the five strategies had the highest information density averaged over the four budgets. The `hyb_dens` and `rnd_dens` columns are the hybrid's and the random draw's information densities. The header text claims these are "averaged over budgets," but that is not what the reader actually prints: the function `read_c17` in `firstpass_notready.py` collects the density at each budget and then calls `med_range`, which returns the median, and prints only that single median value — there is no averaging and no range, despite the header promising both. Two representative rows quoted verbatim from the report: "abagym_HER2 mrmr 0.213 0.034", where the hybrid's density is roughly six times the random draw's, and "abagym_VEGF mrmr 0.105 0.135", the one row where the random draw actually beats the hybrid.

**What it is actually telling us, and why I do or do not trust it.** Read at face value, the hybrid looks good: it beats random on eight of the nine listed datasets, sometimes by a wide margin, for example "flab_polyreact_jain_bvp mrmr 0.031 0.001" where random is essentially at the noise floor. But two things hold me back. First, the `best_strat` column is close to meaningless as a headline, because it says "mrmr" almost everywhere, and mrmr is the one strategy whose entire job is to maximise exactly this label-mutual-information quantity. Reporting that the information-maximising method has the most information is nearly tautological; it tells us nothing about whether the hybrid is good. The column that matters is the hybrid-versus-random pair, not the winner. Second, and more worrying, the numbers printed in the report are not reproducible from anything I have locally. The local result files for these datasets carry an entirely different scale: abagym_HER2 locally shows a hybrid density around 0.006 and a best strategy of "rfe," not the 0.213 and "mrmr" in the report, and several local datasets (both flab_polyreact files, abcov_kd, abagym_VEGF) collapse to 0.0000 for both hybrid and random once you round, because the estimated mutual information is tiny and it is being divided by up to 100 or 200 columns. Two of the datasets in the report, abagym_EGFR and buchwald_hartwig, have no local file at all, and humanness_therapeutic, which does exist locally, is correctly absent from the report because it is a classification task. So the report was generated against a server-side results directory that was never synced back to this machine, and the local copies I can inspect are an older, largely degenerate run. I can describe the mechanism confidently, but I cannot vouch for the specific printed values without the server data. The degeneracy in the local copies is itself a red flag: the k-nearest-neighbour mutual-information estimator, run on standardised high-dimensional antibody representations (total dimensions of 60,000 to 80,000 before selection), is sitting near its noise floor, and when both hybrid and random densities are effectively zero, a claim that one beats the other is fragile.

**So what is wrong, and whose fault.** There are three separable problems. As an experiment issue, the information-density metric divides mutual information by the raw feature count, which mechanically shrinks as the budget grows, so any aggregation across budgets is dominated by the smallest budget and the metric confounds "information" with "column count" in a way the experiment is supposedly trying to disentangle; on top of that the estimator visibly collapses to near-zero on the wide antibody representations, which is a real degeneracy worth investigating in `c17_information_theoretic_decomposition.py` rather than papering over. As an analysis-reader issue, `read_c17` prints a median while its own header claims an average and a range, throws away the two most useful numbers the experiment computed — the downstream random-forest R2 and the effective rank, which together would tell us whether denser information actually predicts better — and leads with the near-tautological `best_strat` column instead of an explicit hybrid-versus-random win or loss with the number of budgets behind each median; I would change the reader to surface downstream R2 and to state the hybrid-minus-random comparison directly. As a design question for you: mutual-information density is only a proxy for the thing the thesis cares about, which is downstream predictive performance, and asking whether the hybrid's selection beats a random draw on that proxy is a low bar that any non-random selector clears — it may be worth deciding whether c17 should be reframed around the downstream R2 it already computes, or retired in favour of the experiments that measure prediction directly.


## c18 — diversity versus depth: spread the budget wide, or concentrate it

**What the experiment is asking.** You have a fixed number of features you are allowed to keep — a budget of, say, 50 or 100. The question is where to spend it. Do you get a better model by pulling those features from many different representations at once (diversity), or by pouring the whole budget into just the one, two, or three strongest representations (depth)? The experiment builds five competing feature sets at each budget and scores each one with the same random forest: "depth_1" takes all its features from the single best-ranked representation, "depth_2" splits the budget across the top two, "depth_3" across the top three, "uniform_all" spreads the budget evenly across every representation available, and "natural" lets the actual KIRBy hybrid search allocate the budget freely however it wants. All the ranking and feature selection is done on training folds only, using LightGBM gain importance, which is the methodologically careful thing to do. The hybrid would count as "working" here if spreading wide, or letting the search allocate freely, genuinely beats just concentrating on the best single representation.

**What the table shows.** Each row is one dataset. The "depth_best" column is the best score achieved by any of the three depth conditions — that is, the reader takes depth_1, depth_2, and depth_3, and for each budget picks whichever depth arm did best, then reports the single best of those. "uniform" is the even-spread condition's best score across budgets, and "natural" is the free-allocation hybrid's best score across budgets. Direction is per-domain: for reaction the score is an error so lower is better, and for antibody the score is Spearman rho or an AUROC so higher is better, and the reader flips the arithmetic accordingly. The "Δdiv-depth" column is uniform minus depth (direction-corrected), so a positive number means the even-spread beat the concentrated one, and the "winner" column labels it diverse, depth, or tie against a fixed threshold of 0.01. Two real rows: "buchwald_hartwig  15.255  15.179  15.065  +0.076  diverse" (a reaction dataset, where all three numbers are large errors and lower is better), and "abagym_HER2  0.294  0.216  0.316  -0.078  depth" (an antibody dataset scored by a correlation, higher is better).

**What it is actually telling us, and why I do or do not trust it.** The headline at the bottom, "diversity wins: 6   depth wins: 2", is not answering the question you probably think it is answering. The winner column is computed purely from uniform versus depth. The "natural" column — the free-allocation hybrid, which is the thing KIRBy actually ships — is printed but plays no part in deciding the winner. So "diversity wins 6" really means "spreading the budget evenly across all representations beat concentrating it, on 6 of 10 datasets," and it says nothing about whether the real greedy hybrid won. That matters, because when you look at the natural column it is frequently the best cell in the row: buchwald_hartwig's natural error of 15.065 is lower than both its depth (15.255) and its uniform (15.179), and abagym_HER2's natural of 0.316 is higher than both its depth (0.294) and uniform (0.216). On the datasets shown, the free hybrid quietly tends to win even where the printed verdict says "depth." The verdict is measuring the wrong contestant.

The magnitudes are also small and the scale is inconsistent across domains. The antibody deltas run from +0.033 to +0.084 of Spearman rho, computed over roughly five grouped folds, which is comfortably inside the range that noise alone produces. humanness_therapeutic sits at 0.960 versus 0.957 versus 0.958 — that is a saturated classification score near the ceiling with a delta of -0.003, correctly called a tie. The reaction row is the clearest scale problem: a delta of +0.076 on an error metric whose values are around 15 is a relative change of half a percent, yet it clears the same absolute 0.01 threshold used to declare a "win" on a Spearman rho that only ranges from zero to one. The reader applies one fixed tie-band of 0.01 to a 0-to-1 correlation and to a ~15-unit error in the same breath, so the reaction "diverse win" is essentially meaningless as stated.

I want to be plain that the report was not generated from the JSON files sitting in this repository. The local copies are stale, and they disagree with the report, not just in decimals but in the actual winner. The local abcov_kd file gives a best depth score of about 0.412 against a uniform of about 0.365, which would make depth the winner, whereas the report prints abcov_kd as "diverse  +0.076." The local abagym_Ang2 file only sweeps budgets 50 and 100 and uses the older "n_features" field name, and its numbers do not match the report's either. So the numbers I am reading in prelimResults come from a fresher server run that has not been synced down here. The report is internally consistent and readable, but I cannot re-derive any single number from local data — that would need the server results.

**So what is wrong, and whose fault.** There is no experiment bug. The source file computes exactly the five conditions it describes, ranks and selects on training data only, and aggregates cleanly across folds; the "natural" arm is honestly restricted to base representations so it is a fair comparison. The problems are in the reader, in `tests/analysis/firstpass_notready.py`, in `read_c18`. First and most important, the win/loss count is decided from uniform-versus-depth and completely ignores the natural hybrid, even though natural is often the best cell in the row — so the summary line understates, or simply mislabels, whether KIRBy's real allocation works. It should be scoring natural against the best depth, or at least reporting both contests separately. Second, the reader silently takes the best budget per condition, independently for each arm, before comparing them, which is an optimistic max that lets each contestant cherry-pick its own budget; that hidden selection is invisible in the printed number. Third, the fixed 0.01 tie-band is applied across metrics on wildly different scales, which makes the reaction "diverse" verdict spurious. Those are all analysis-reader fixes, not experiment fixes. The one thing genuinely for you to decide is a design question: on antibody datasets these deltas are a few hundredths of a correlation over five folds, and I do not think that is a resolvable signal without either more folds or a confidence interval — the reader currently prints a point estimate with no spread at all.


## c19 — should we let importance scores steer the training, not just the feature selection?

**What the experiment is asking.** Once the hybrid has been built (the feature-selected combination of many representations), every feature in it carries an importance score. c19 asks whether we can squeeze more accuracy out of that hybrid by actually using those importance scores during training, instead of treating all the selected features as equal. It tries five ways of training on the same hybrid feature set: plain unweighted training as the baseline; "feature_weighted," which multiplies each standardized feature column by the square root of its importance so important features are literally bigger; "sample_weighted," which scores each training molecule for how well its label agrees with its neighbours and passes that reliability in as a per-sample weight; "combined," which does both at once; and "importance_pruned," which throws away every feature whose importance is below the median. For each model, it picks whichever of the five scored best, and the hybrid "works" here if some weighting scheme consistently and meaningfully beats plain unweighted training.

**What the table shows.** The report prints one row per dataset with two columns. "most_winning" is the single weighting condition that won the most model cells for that dataset — the experiment runs several models, each model votes for its own best condition, and this column reports the plurality winner (read from the summary field `most_winning_condition`). "models_weighted_wins" is a fraction: how many of the models preferred any weighted scheme over plain unweighted, out of the total number of models run. So the row "abagym_Ang2  feature_weighted  3/3" means feature-weighting was the plurality winner and all three models preferred some weighted scheme over unweighted, while "abagym_HER2  unweighted  1/3" means plain unweighted training was the plurality winner and only one of the three models wanted weighting at all. Note the denominator is 3 on every row, so these runs used three models.

**What it is actually telling us, and why I do or do not trust it.** The honest read is that the winning margins are tiny and the "wins" are mostly noise. In the real result files the differences between conditions are in the second or third decimal place of the metric. On the humanness_therapeutic run the best weighted scheme beats unweighted by roughly 0.002 to 0.015 of AUROC across models; on abagym_Ang2 the top gain is about +0.038 of Spearman rho for one model, but on that same dataset the ridge model swings by -0.178 rho under feature-weighting. That last number is the tell: multiplying standardized columns by importance badly distorts a linear model's geometry, which is why feature-weighting produces big negative swings on ridge and near-zero swings on the tree models. And there is a structural problem hiding in the three-model denominator. The current model filter (`WEIGHTED_MODELS = {'rf', 'lightgbm', 'xgboost'}` in the experiment source) keeps only tree-based models, and tree splits are essentially scale-invariant, so "feature_weighted" and "importance_pruned" barely move them at all — the per-model "best condition" is then being decided by hundredths-of-a-point wobble between near-identical scores. A column that reads "3/3" therefore looks decisive but can be three models each preferring a weighted scheme by a margin smaller than fold-to-fold noise. Two further reader mechanics matter. The "most_winning" column is a plurality over only three votes, and ties are broken by condition order so plain unweighted quietly wins ties; and the "models_weighted_wins" count treats a 0.002 win exactly like a 0.05 win, because it looks only at the sign of the argmax, never the size. The humanness_therapeutic row printing "None" is a separate schema artifact I can see directly: my local copies of these files store the plurality winner under the older key name `best_overall`, whereas the reader now looks for `most_winning_condition`, so any file that has not been regenerated under the new schema shows up as None even though the value exists.

**So what is wrong, and whose fault.** There are three separable problems. The experiment bug is the model filter: restricting c19 to the three tree models throws away exactly the scale-sensitive models (ridge) where feature-weighting and pruning could actually matter, and it does so needlessly — three of the five conditions (unweighted, feature_weighted, importance_pruned) never touch `sample_weight`, and the code at the TypeError fallback already handles models that cannot accept a sample weight. That filter lives in `tests/experiments/complexity/c19_importance_weighted_training.py`. The analysis-reader shortcomings are in `read_c19` in `tests/analysis/firstpass_notready.py`: it prints which condition won but never how much it won by, so a real effect and rounding noise look identical, and it silently falls over on the old `best_overall` key instead of falling back to it or recomputing the winner from the `condition_wins` counts it already has, which is why humanness_therapeutic shows None. The design question for you is whether this experiment is answerable in its current shape at all: with three tree models and metric gaps in the third decimal, "which weighting condition won" is close to a coin flip, and the one arm that clearly does something (feature-weighting on a linear model) is the arm that got filtered out. I would not treat any c19 row as evidence until the reader prints the winning margin and the model set includes at least one scale-sensitive model; the current table is not trustworthy, but the fix is straightforward and does not require re-running the server before we at least regenerate the stale humanness file.


## c21 — does bolting small extra features onto one representation help that representation

**What the experiment is asking.** Take a single base representation on its own — say an ESM protein embedding — and ask whether gluing on a handful of small, cheap, structurally-flavoured feature sets (things like amino-acid composition, BLOSUM features, a 167-dimensional fingerprint) makes that one representation predict better. This is deliberately not the full hybrid story: there is only ever one base representation, and the "augmentation" reps are the small side features the search is allowed to selectively keep and weight. For every base representation the experiment scores it alone, then scores it again with the augmentation features searched-and-selected on top, and records whether the augmented version beat the plain version. The hybrid idea "works" here if adding these small side features to a lone representation reliably improves it. The docstring itself warns this experiment is "known often degenerate," so the honest question is really whether it produces any trustworthy signal at all.

**What the table shows.** Each row is one dataset, and every dataset here is an antibody task, so the metric is Spearman rho where higher is better. The `state` column says whether the run is alive (`ok`), an `ERROR`, or a dead `all_skipped` run. The `improved` and `hurt` columns are raw counts, taken straight from the run's own summary, of how many individual tests came out better or worse with augmentation — where one "test" is a single combination of base representation, downstream model (random forest, k-nearest-neighbours, or xgboost), and augmentation condition. The `best_rel` column is the single largest relative improvement seen across all of those tests, expressed as a fraction of the base score: the reader computes it as the maximum, over every surviving test, of the sign-corrected delta divided by the absolute base score. A representative alive row is "abagym_Ang2  ok  19  26  +0.764", meaning 19 tests improved, 26 got worse, and the very best one improved by 0.764 of its base score. Two rows are worth quoting for contrast: "abagym_HER2  ok  10  14  +27.832" and "abcov_kd  ok  0  0  --". The last dataset, "humanness_therapeutic  ERROR  no_augmentation_reps", never ran because that dataset has no augmentation representations defined for it.

**What it is actually telling us, and why I do or do not trust it.** The improved-versus-hurt counts do not describe a working effect. On abagym_Ang2 augmentation helped 19 times and hurt 26 times; on abagym_VEGF it is 23 up against 22 down; on flab_polyreact_jain_cic it is 16 up against 20 down. That is a coin flip, and it is a coin flip made to look like more evidence than it is, because those dozens of "tests" are not independent — the same base representation reappears across three downstream models and several augmentation conditions, so a handful of genuinely distinct representations is being counted many times over. The `best_rel` column is where the "known often degenerate" warning bites hardest. That number is computed as delta divided by the absolute base score, and on these antibody datasets the base score is a Spearman rho that can sit very close to zero. When a representation is already near-useless (rho around, say, 0.01), even a trivial change in the score divided by that tiny denominator explodes. The +27.832 on abagym_HER2 is not a 2,700 percent improvement in any meaningful sense; it is almost certainly a division by a near-zero base rho, and the +3.425 on VEGF is the same story milder. Because `best_rel` is a maximum over every test in the run, it is guaranteed to surface the single most divide-by-zero-prone case in the whole file, so it is the least trustworthy number on the row by construction. The abcov_kd row is its own puzzle: it is labelled `ok` yet shows zero improved, zero hurt, and no best value, which means the run finished but produced no countable augmented tests at all — it should really read as dead, not alive. I also have to flag a data-freshness caveat honestly: the c21 result files I can read locally are the stale May versions where the per-test `aug_status` field does not exist yet, every row carries a null status, and the summaries read zero-improved, zero-hurt, not-a-number mean. The alive counts in this report therefore came from a newer re-run on the server that I cannot open here, so I can describe the mechanism behind +27.832 with confidence but cannot print the exact base rho behind it without the server file.

**So what is wrong, and whose fault.** There are three separate problems. First, an experiment-source issue in tests/experiments/complexity/c21_single_rep_augmentation.py: the `relative_improvement` figure is delta divided by the absolute base score with no floor on that denominator, so any dataset whose base Spearman rho lands near zero manufactures a giant percentage. On antibody tasks with weak base correlations this is not an edge case, it is the norm, which is exactly why the file's own docstring calls the experiment degenerate. Second, an analysis-reader shortcoming in read_c21 inside tests/analysis/firstpass_notready.py: it prints only the maximum of that unstable relative-improvement quantity, which deliberately picks out the most blown-up single test, while throwing away the mean delta and the per-condition breakdown that the run actually computed and saved; it also trusts the summary's improved-and-hurt counts without noting that they are inflated by counting the same few representations across three models and several conditions; and it prints abcov_kd as `ok` when a run with zero countable tests should be surfaced as dead. Third, a design question for you that no code change settles: a near-tie of wins against losses on a few antibody datasets, driven by base scores close to zero, may simply not be an answerable question in its current form, and if c21 is to stay it needs either a denominator floor and a raw-delta view, or an honest acknowledgement that it is a diagnostic rather than a result. This one is not fine as it stands — it is a real experiment bug (the unfloored denominator) compounded by a reader that showcases the worst symptom of it.


## c22 — which representation the winning hybrid actually leans on

**What the experiment is asking.** This one does not test whether the hybrid beats a single representation at all. It is purely descriptive. It takes the hybrid that the pool search already picked as the winner for a dataset, rebuilds that exact hybrid, trains two tree models on it (random forest and XGBoost), keeps whichever model scored better on the held-out fold, and then runs a SHAP explainability analysis on that model. SHAP hands back an importance number for every feature; the experiment maps each feature back to the source representation it came from and adds up the importance per representation. The question it answers is "of all the representations that got blended into the winning hybrid, which one is doing the most work, and how much of the total importance does it carry." There is no pass/fail here — nothing "works" or "fails," it is a breakdown of a hybrid we already committed to.

**What the table shows.** The report prints one row per dataset with four columns. The first is the dataset name. The second, "top rep (SHAP)," is the single representation that carries the largest total absolute SHAP importance inside that hybrid. The third, "shap%," is that top representation's share of the total absolute SHAP summed over every representation in the hybrid — so if the hybrid leaned entirely on one representation this would approach a hundred, and if importance were spread evenly across many representations it would be small. The fourth, "search," is the internal cross-validated score that the pool search recorded for this winning hybrid when it chose it; for these antibody datasets that is a Spearman correlation where higher is better, and it is the search's own estimate, not a fresh held-out comparison against any single-representation baseline. Two representative rows quoted verbatim: "abcov_kd                esm2_cdr3                9.2    0.457" and "abagym_VEGF             mutation_features       28.9    0.638".

**What it is actually telling us, and why I do or do not trust it.** The clearest real signal is that the "shap%" number is being driven as much by how many representations survived into the hybrid as by any genuine dominance. Look at the two extremes. For abcov_kd the top representation carries only 9.2 percent of the importance, which means the importance is smeared almost evenly across a couple of dozen representations, so naming a single "top rep" there is close to meaningless. My local result files echo this shape: abcov_kd spreads its SHAP over twenty-six representations with the leader at roughly seven to nine percent, essentially flat. At the other extreme a hybrid that only kept two representations will mechanically hand its "top rep" a large share; my local abagym_VEGF file, for instance, splits cleanly as aac about 63 percent and structural about 37 percent, so a high shap% there reflects a two-representation blueprint, not a strong preference. In other words the shap% column is not comparable across rows, because a low budget over few representations inflates it and a wide blend deflates it. On trust: I could reproduce the schema and the computation exactly, but I could not match the report's printed numbers to my local JSON files — the report lists esm2_cdr3 at 9.2 for abcov_kd and mutation_features at 28.9 for abagym_VEGF, whereas my local copies show esm2_entropy_top20 and the aac/structural split. The report was clearly generated from a newer, server-synced set of result files than the ones on this machine, so I trust the qualitative story (flat versus concentrated) but cannot verify each exact printed value locally. Two further reasons for caution: every dataset here is an antibody task, so this ran on one narrow domain only, and the sample sizes are tiny — abcov_kd has 141 rows, which means SHAP is being computed on validation folds of only about 28 antibodies each, so the per-representation importances are themselves noisy.

**So what is wrong, and whose fault.** I do not think there is an experiment bug to chase; the source file handles the awkward SHAP output shapes carefully and averages importances across folds properly. The real issues are one design question and one analysis shortcoming. The design question for you is what "shap%" is supposed to mean when it is confounded by blueprint width: a hybrid with two representations and a hybrid with twenty-six representations are being reported on the same axis, and the number is not comparable between them, so if you want this column to mean "concentration" it should probably be normalised against the number of representations in the blueprint, and that is a call for you, not something to change silently. The analysis shortcoming lives in the reader function read_c22 in tests/analysis/firstpass_notready.py: it prints only the single top representation and throws away the entire rest of the distribution it already has in hand, so you cannot see whether second place was a near tie or a distant afterthought, and it never prints how many representations the hybrid contained, which is exactly the context needed to read shap% honestly. The "search" column is also easy to misread as "how good the hybrid is" when it is really the search's own internal score with no single-representation baseline beside it, so at minimum it should be labelled as such. None of this is a crash or a corrupted number; it is a descriptive table that is under-labelled and printed from result files newer than the local copies.


## c23 — does matching the internal evaluator to the deployed model help?

**What the experiment is asking.** When KIRBy searches for a good hybrid, it uses an internal "evaluator" model to score candidate feature combinations before it hands the winning combination off to the real downstream model you actually intend to deploy. The question c23 asks is: should that internal evaluator be the same kind of model as the deployed one? For each of eleven downstream models (random forest, lightgbm, xgboost, ridge, knn, mlp, svm, gp, catboost, dnn, cnn) the experiment builds the hybrid three ways: with a matched evaluator that is the same family as the deployed model, with a slightly-off evaluator from a nearby family, and with a strongly-off evaluator from a very different family. It then measures how much better the deployed model does when the hybrid was chosen by the matched evaluator versus the two mismatched ones. If matching genuinely helps, the matched configuration should win, and the source file even predicts the effect should be biggest for neural nets. The hybrid "working" here does not mean beating a single representation; it means that spending the effort to match the evaluator to the deployed model buys you a measurably better hybrid.

**What the table shows.** The report prints one row per dataset with two numbers and a verdict. The first number, "medΔ B(slight)", is the difference in the deployed model's score between the matched evaluator and the slightly-off evaluator, where a positive value means the matched evaluator produced the better hybrid. The second, "medΔ C(strong)", is the same comparison against the strongly-off evaluator. Both numbers are a median taken across all eleven downstream models: the experiment computes one delta per model, and the reader collapses those eleven per-model deltas down to their median before printing. The final "matters?" column simply prints "yes" when the strongly-off median exceeds the tie threshold of 0.01, and "~" otherwise. Two representative rows read verbatim: "abagym_VEGF   +0.021   +0.020   yes" and "flab_polyreact_jain_cic   -0.029   -0.004   ~". Note that all eight datasets in the report are antibody regression tasks scored by Spearman rho, where higher is better, so a positive delta always means matching helped.

**What it is actually telling us, and why I do or do not trust it.** The medians are tiny and the datasets are small, so I do not trust the "yes" verdicts as real effects. Take abagym_VEGF, the clearest "yes" in the table. Its printed medians are +0.021 and +0.020, but underneath those single numbers the eleven per-model deltas for the slightly-off comparison run all the way from -0.104 for the dnn to +0.097 for the mlp, and the strongly-off deltas run from -0.070 to +0.034. In other words, on the very same dataset, matching the evaluator badly hurt the dnn while it clearly helped the mlp, and the median of +0.02 is a small survivor of a large two-sided spread. That directly contradicts the source file's stated conclusion that the effect should be strongest and most helpful for neural nets, because here the neural net is the model matching hurt the most. Every score behind these deltas is a Spearman rho computed on an antibody set of only a few hundred molecules, and I confirmed the sizes locally: VEGF has 418 samples, Ang2 has 397, and the rest are smaller still, with abcov_kd at 141, flab_polyreact_jain_bvp and flab_polyreact_jain_cic at 137, and abagym_HER2 at 146. A shift of 0.02 in Spearman rho at n=137 is comfortably inside ordinary cross-validation noise, and the reader shows no standard deviation or confidence interval to argue otherwise, even though each score in the JSON does carry a score_std that could have been used. So the honest reading is that six of eight datasets say the effect does not matter, two say it barely clears an arbitrary 0.01 line, and the per-model evidence underneath is contradictory rather than weakly positive. One more caveat: all eight rows are antibody datasets. c23 as written applies to any domain, but only antibody runs were produced and synced, so this table tells us nothing about whether evaluator matching matters for the molecular, reaction, tcga, or genomic domains.

**So what is wrong, and whose fault.** I do not see an experiment bug in the numbers; the deltas are computed correctly, with the sign flipped by domain direction so that positive always means matched-is-better, and I confirmed all eleven models produced finite deltas on every dataset. The real problems are one design question and two analysis shortcomings. The design question for you is whether this comparison is answerable at these sample sizes at all: a difference of 0.02 in Spearman rho on 137 to 418 antibodies is not distinguishable from noise, and the strongly two-sided per-model spread suggests there is no stable effect to find, so this may need larger datasets or a paired-across-folds significance test rather than a raw median. The first analysis shortcoming, in the reader function read_c23 in tests/analysis/firstpass_notready.py, is that it throws away almost everything the experiment computed: it collapses eleven per-model deltas into a single median and never shows the per-model values or their spread, so the one genuinely interesting fact here, that matching helps the mlp but hurts the dnn on the same dataset, is completely invisible. The second shortcoming, in the same reader, is that it never surfaces the score_std the experiment already saved, so a 0.02 median and a 0.002 median look equally solid on the page, and it also ignores the experiment's D (neural-net size mismatch) and E (quick default set) conditions entirely, printing only the ABC comparison. Those are reader-side fixes, not experiment-side. The experiment source at tests/experiments/complexity/c23_evaluator_model_matching.py is functioning as designed; the question is whether the design can ever produce a trustworthy signal on data this small.


## c24 — does a feature-selection blueprint learned on one fold still work on the others?

**What the experiment is asking.** When KIRBy builds a hybrid it discovers a "blueprint": which feature budget, which allocation method, which importance ranking, which internal evaluator, and ultimately which specific features to keep. The worry this experiment is built to answer is that this blueprint might be overfit to the exact rows it was tuned on, so it would fall apart on fresh data. To test that, the experiment splits each dataset into cross-validation folds, discovers a blueprint on each fold's training data, and then takes each fold's blueprint and re-applies it to every other fold's data. For every target fold it compares the score you get from that fold's own home-grown blueprint against the average score you get from the blueprints imported from the other folds. The hybrid's feature selection is "working" (generalising, not overfit) if the imported blueprints score about as well as the home-grown one, meaning the gap between them is close to zero. It also computes a separate Nogueira stability index, which measures how often the folds actually pick the same features as each other.

**What the table shows.** The report prints only three numbers per dataset. The first, mean_delta, is the average gap between the own-fold score and the imported-blueprint score, averaged across folds, signed so that a positive number means the fold's own native blueprint did better (a sign that selection is somewhat fold-specific) and a value near zero means blueprints transfer cleanly. The second, mean|delta|, is the same gap but with the sign stripped off first, so it reports the typical size of the transfer penalty regardless of direction. The third is just a word, either "transfers" or "penalty", which the reader stamps on purely by checking whether mean|delta| is below its tie threshold of 0.01. For example the report shows "abagym_HER2  +0.142  0.183  penalty", meaning HER2's own blueprint beat the imported ones by about 0.14 Spearman on average with a typical swing of 0.18, and "humanness_therapeutic  -0.001  0.006  transfers", meaning there the imported and home blueprints were essentially indistinguishable.

**What it is actually telling us, and why I do or do not trust it.** Two things make me cautious. First, every dataset in this table is an antibody regression task scored with Spearman rho, and these are small datasets with only a handful of cross-validation groups. Each delta is a difference of two Spearman correlations, each computed on one small held-out fold, and those correlations are themselves jumpy. A "penalty" of 0.14 to 0.18 on HER2, VEGF and Ang2 is well within what fold-to-fold noise alone produces on datasets this size, so I would not read those as real evidence that selection is overfit. Second, and more damning, the single number the report hides is the one that would tell the honest story. Behind mean|delta| of 0.183 for HER2 sits a max_abs_delta of 0.491 in the underlying JSON, meaning one fold's transfer gap was nearly half a Spearman unit. The reader prints the average and throws that spread away, so a wildly unstable fold looks like a modest average penalty. The report also completely drops the Nogueira stability index, which is arguably the experiment's headline defensive result: for HER2 that index is 0.993 with a 95 percent interval of roughly 0.992 to 0.994, meaning the folds selected almost identical feature sets every time. That is strong evidence the selection is NOT overfit, and it is invisible in the report. One row, flab_immunogenicity_marks, prints "--  --  penalty". That is a genuine blow-up, not missing data: in the JSON its fold-0 own-fold score came back as NaN (a Spearman on that fold that could not be computed, most likely because the predictions were near-constant), the NaN poisoned the fold-0 delta, and averaging a list that contains NaN yields NaN for both columns. The word "penalty" next to it is simply wrong. Finally, a note on provenance: my local copy has this dataset stored twice, once as a stale error file dated 2026-05-18 that predates the skip-instead-of-crash fix, and the report clearly reflects the newer server run, so I am reading the report's numbers rather than my incomplete local mirror.

**So what is wrong, and whose fault.** The experiment source itself is basically sound and its recent hardening is good — it now reduces the fold count when a dataset has too few groups and returns a clean skip rather than an error, which is why the wave stopped choking on these small antibody sets. The one real experiment-side gap is that a NaN own-fold score is allowed to propagate straight into the aggregate instead of being dropped or flagged; that is in tests/experiments/complexity/c24_blueprint_transfer.py, where the delta list is averaged without filtering non-finite fold scores. The larger problems are in the reader, read_c24 in tests/analysis/firstpass_notready.py. It prints only the mean and hides max_abs_delta, so it disguises a fold that transferred terribly as a mild average; it never surfaces the Nogueira stability index or the number of features selected, which is the most trustworthy signal this experiment produces; and its "transfers"/"penalty" label is decided by a raw threshold check that mislabels an all-NaN row as "penalty" instead of saying the run degenerated. There is also a design question for you underneath all of this: a transfer gap measured as the difference of two Spearman correlations over five tiny antibody folds may not be answerable at all, and if it is not, the right move is to lean on the stability index (which is far less noisy) as the primary readout and treat the delta as secondary color.

# SIMILARITY

## s01 — do plain distances in each representation line up with activity?

**What the experiment is asking.** This is the setup experiment for the whole similarity paper, and its stated conclusion is deliberately negative: standard distances in any single representation correlate only weakly with how much the activity actually differs. For each representation it builds the full table of pairwise distances between molecules (or antibodies, or tumours), and for each pair it also computes how much their measured property differs. It then asks, using a Spearman rank correlation, whether pairs that sit far apart in the representation also tend to differ a lot in activity. That correlation is called the Similarity-Activity Correlation, or SAC. A high positive SAC would mean the representation genuinely preserves the structure-activity relationship — near things behave alike, far things behave differently — which is what "the representation working" would look like. The experiment expects, and is trying to demonstrate, that this correlation is disappointingly small for every representation, which is the gap the hybrid is later supposed to close.

**What the table shows.** Each row is one dataset. The "best rep" column names the single representation that came out on top for that dataset, "SAC" is that representation's Spearman correlation between distance and activity difference, "sig?" is whether a label-shuffling permutation test said that correlation is above chance (the code shuffles the labels 200 times and checks how often a random shuffle beats the real number), and "viol" is the violation rate — the fraction of each point's five nearest neighbours whose activity actually differs by more than the typical amount, so a number near one-half means the nearest neighbours are essentially no more alike than random pairs. A representative good row is "flab_expression_koenig  ablang2  0.260  True  0.230", meaning the ablang2 representation reached a SAC of 0.260, which the permutation test called real, and only about 23 percent of nearest neighbours were violations. A representative bad row is "abagym_EGFR  esm2_midlayers  -0.122  True  0.353", where the "best" representation actually has a negative correlation.

**What it is actually telling us, and why I do or do not trust it.** The headline finding is honest and matches the experiment's whole reason for existing: the correlations are tiny. Most datasets land somewhere between about 0.05 and 0.26, and the violation rates hover between roughly 0.33 and 0.50, which for a regression task is close to the coin-flip value of one-half. In other words, for most datasets the single-representation distance barely knows anything about activity, which is exactly the weakness this paper wants to motivate. There are two clear exceptions, both classification tasks: "tcga_luad_vs_lusc  wsi_titan  0.471" and "tcga_brca_pam50  gene_geneformer  0.440", plus "humanness_therapeutic  igt5  0.289". Those are the datasets where separating two well-defined groups is genuinely easy, so the distance carries real signal. I would trust the ranking of the small numbers only loosely, because the "sig? True" flag is misleading about importance: the correlation is computed over 5000 sampled pairs, and with that many pairs even a correlation of 0.08 clears the permutation test comfortably, so "True" here means "not literally zero," not "meaningful." The thing I actively distrust is the "best rep" column itself. For five datasets the representation printed as best has a negative SAC — abagym_EGFR at -0.122, flab_polyreact_jain_bvp at -0.118, abagym_lysozyme at -0.096, ginkgo_aggregation at -0.069, and ginkgo_tm2 at -0.047. A negative SAC is not a good representation with a strong signal, it is a representation whose distances point the wrong way, and it should never be labelled the winner under a header that literally says "HIGHER = better." I confirmed against a real result file (abagym_EGFR, saved 2026-05-08) that esm2_midlayers really does sit at -0.122 and that the same file even carries a positive-signed alternative for other representations, so this is a reporting choice, not corrupted data.

**So what is wrong, and whose fault.** The experiment source itself looks sound; it is doing exactly the honest, deliberately-negative measurement it set out to do, and the small numbers are the point rather than a bug. The real problem is in the reader function read_s01 in tests/analysis/firstpass_notready.py. It picks the "best" representation by the largest absolute correlation (the line comparing abs(rho) to the running best), which is why a strongly negative anti-correlation can be crowned the winner directly beneath a header promising higher-is-better. For an experiment whose whole message is "positive correlation is scarce," the right thing to show is the best signed SAC per dataset, so a negative winner would correctly read as "no representation achieved even a positive correlation here." There is also a smaller cosmetic fault in the same reader: the dataset name is squeezed into a 26-character column with no guaranteed gap, so a long name like "flab_aggregation_jain_hicrt" collides with its representation and prints as "flab_aggregation_jain_hicrtsaprot" with no space, which is confusing to read. Finally, one design question for you rather than a bug: the saved files contain a second, differently-weighted version of the same correlation, and the reader ignores it entirely and shows only the plain version; if the weighted variant is the one you consider canonical, the reader is quietly showing the wrong column, and that is worth a decision before the write-up.


## s02 — does the hybrid make "similar molecules have similar activity" hold better than the single best representation

**What the experiment is asking.** This is the similarity-side version of the core KIRBy claim. Instead of training a model, it asks a geometry question: if I lay all the compounds (or antibodies) out in a representation's feature space and measure the distance between every pair, do pairs that sit close together also have close activity values? The score for that is SAC (similarity–activity correlation), a Spearman correlation between pairwise distance and pairwise activity difference, and higher is better. The experiment computes SAC for each single representation on its own, then computes SAC for the KIRBy hybrid (the feature-selected mix of many representations), and it also tries an importance-weighted version where features are scaled by how much a LightGBM model thinks they matter. The hybrid "works" here if its SAC comes out meaningfully above the SAC of the best single representation. The experiment's own docstring claims a "100%+" improvement, so the bar it set for itself is dramatic, not marginal.

**What the table shows.** Each row is one dataset. "best indiv rep" names the single representation that the reader decided was the strongest baseline, and "indiv" is that representation's SAC. "hybrid" is the hybrid's SAC. "lift" is hybrid minus indiv, and "win" is "yes" when the lift clears +0.01, "no" when it falls below -0.01, and "~" for anything inside that band. One representative win row reads verbatim `abagym_HER2                prot_t5_cdr          0.294   0.351  +0.058  yes`, and one representative loss row reads verbatim `ginkgo_colloidal          blosum               0.176   0.085  -0.091  no`. The genomic row is empty: `gb_human_enhancers_cohn   None                    --      --      --  ~`. The footer tallies the whole table as `hybrid distance beats best single rep: +12  ~2  -12  (27 datasets)`.

**What it is actually telling us, and why I do or do not trust it.** The headline is a coin flip: twelve wins, twelve losses, two ties, and one dataset that produced nothing, across twenty-seven datasets. That already contradicts the experiment's own "100%+ improvement" story, and the reason is a quiet but important choice inside the reader. The "indiv" baseline it prints is not the plain single representation — it is the higher of the plain SAC and the importance-weighted SAC of the best single representation, and weighting almost always lifts a single representation a lot. On abagym_HER2 the plain best representation only scores 0.0805, but its weighted version scores 0.294, and that 0.294 is what the table calls "indiv." So the reader is doing the honest thing the experiment itself refused to do: it makes the hybrid beat a *weighted* single representation, not a naked one. That is why the lift shrinks from the experiment's internal "+0.27 versus the plain baseline" down to the +0.058 the table shows. The "100%+" figure in the docstring is real only because the experiment compared a weighted hybrid against an unweighted single representation, which is not a fair fight.

There is a second, subtler distortion in the loss rows that makes them untrustworthy in a different direction. The "hybrid" column is the file's `best_sac`, and that value is floored at the plain best single representation. When the hybrid actually loses, `best_sac` falls back to that floor rather than reporting the hybrid's true (worse) number. On ginkgo_colloidal the real weighted hybrid scored only 0.066, but the table prints 0.085 (the plain blosum floor) as "hybrid," so the -0.091 loss shown is actually milder than the truth — the hybrid was worse than the row admits. In those loss rows the "hybrid" column is not even a hybrid; it is a single representation wearing the hybrid's label.

I also do not fully trust the sample this table is built from, for two reasons. First, there is not a single molecular dataset in it — no logd, esol, caco2, qm9, anything. I checked a molecular result that exists on the server (logd), and there the story is genuinely strong: maccs at 0.117 climbs to a hybrid 0.368, the true source of the "100%+" claim. That is exactly the evidence that would support the hypothesis, and it is entirely missing from this report, which shows only reaction, antibody, and genomic. So the domain where the hybrid clearly wins is absent, and the domain where it is a wash (antibody) is all we see. Second, these SAC values are small (mostly 0.08 to 0.5) and are Spearman correlations over 5,000 sampled pairs; lifts of +0.02 to +0.06 on top of a 0.2-to-0.3 baseline are modest and I would want the fold-to-fold spread before calling any single one real.

**So what is wrong, and whose fault.** The genomic empty row is a real gap to chase: the analyzed root contains a `gb_human_enhancers_cohn` file whose `best_individual_rep` is null, so the baseline never computed. I could not open that exact file locally (the report was generated from a fuller results directory than the one in my tree), so I can only say the SAC baseline failed for that dataset — plausibly the genomic representations did not load, or SAC degenerated on a large genomic set — and it needs the server file to confirm. That lives on the experiment side, in `tests/experiments/similarity/s02_hybrid_similarity.py`. The bigger issue is a methodology fault baked into the experiment source: its own headline delta, `sac_delta_from_best_rep`, subtracts the *unweighted* best representation from the *weighted* hybrid, which is the apples-to-oranges comparison that produced the inflated docstring claim. The reader partly repairs this by allowing the weighted single representation as the baseline, and that repair is why the honest tally is 12–12–2 rather than a landslide. But the reader has its own two shortcomings, both in `read_s02`: it labels `best_sac` as "hybrid" even when `best_sac` has silently fallen back to the plain single-representation floor, so loss rows understate the hybrid's deficit and mislabel a single rep as a hybrid; and it prints only the single winning number, hiding the four things a reader needs — the plain hybrid SAC, the weighted hybrid SAC, the plain baseline, and the weighted baseline — so you cannot see how much of any "win" is the hybrid versus how much is just the weighting trick. The design question for you is whether SAC-versus-best-rep is even the comparison you want to headline: if weighting a single representation captures most of the gain, the interesting quantity is weighted-hybrid minus weighted-best-rep, computed the same way on both sides, and reported per domain — with the molecular datasets actually present, since they are the only place this claim currently holds.


## s03 — feature concentration (is the signal denser after selection?)

**What the experiment is asking.** This is not a win-or-lose experiment; it is a "why does the hybrid work at all" diagnostic. The idea is that when the hybrid picks a small subset of dimensions out of a big representation, those chosen dimensions ought to carry more of the actual signal per dimension than the representation as a whole. To measure that, the experiment estimates the mutual information (how much the features tell you about the label) for the full representation and for the selected subset, then divides them out on a per-dimension basis. The headline number is the "MI density ratio": the mutual-information-per-dimension of the selected features divided by the mutual-information-per-dimension of the full representation. A ratio above one means selection concentrated the signal — the few dimensions the hybrid kept are individually richer than the average dimension. That would be the mechanism-level evidence that feature selection is doing real work, not just shuffling dimensions around.

**What the table shows.** The report prints, per dataset, three things: "#cells" is how many usable density-ratio numbers were collected across the sweep of downstream models and feature budgets crossed with each representation; "med ratio" is the median of those numbers; and "ratio range" is the smallest and largest. The reader gathers every cell it can find, keeps only the finite ones, and reports the median and the min/max — it deliberately prints no mean, in keeping with the no-averaging rule. The problem is that every single row is empty. Two representative lines, quoted verbatim: "abagym_EGFR                     0         --                  --" and "gb_human_enhancers_cohn         0         --                  --". Every one of the roughly twenty-six datasets shows zero cells and a double-dash for both the median and the range. There is nothing to interpret in the numbers because there are no numbers.

**What it is actually telling us, and why I do or do not trust it.** I traced this all the way to the stored result files, and the emptiness is real and has two overlapping causes. First, a schema mismatch. The current experiment code stores its results as a two-level structure: an outer dictionary keyed by a model-and-budget pair, whose value is a dictionary of per-representation cells. The reader is written for exactly that two-level shape — it loops over the outer model-budget entries, then loops over the representations inside each one, and only counts a cell when it finds a dictionary carrying a finite "mi_density_ratio". But the actual result files on disk are the older, flat shape: the top level is keyed directly by representation name, and the value is that representation's result dictionary. So the reader's inner loop ends up walking over field names like "mi_full" whose values are plain numbers, not dictionaries, and it skips every one of them. That alone guarantees zero cells for every dataset. Second, and worse, even if the schema matched, the underlying data is degenerate. In every local file, each representation only ever recorded two fields, "mi_full" and "effective_rank_full", and the "mi_density_ratio" was never written at all. The selected-features branch — the part that computes the selected, random, and PCA-matched mutual information and the density ratio — never executed, which means the fitted hybrid was absent or none of the representations were found in its selection. On top of that, "mi_full" is exactly zero for every representation in every dataset, which is its own alarm: the mutual-information estimator reported no detectable dependence anywhere. So the ratio the experiment exists to produce was never computed, and the one input it did record is flat zero. The files are dated early-to-mid May, before the model-and-budget sweep rewrite, so this is stale pre-rewrite output, not a fresh run. I want to be honest that the report you are holding lists a few datasets I do not have locally (for instance the genomic gb_human_enhancers_cohn and ginkgo_aggregation), so that copy was likely generated against a server results tree; but every dataset in it, local or not, shows the identical zero-cells signature, so the diagnosis holds across the board.

**So what is wrong, and whose fault.** There are three distinct problems here and they belong to different people. The analysis-reader problem is that it is coded against a schema the stored files do not use; it silently skips the old flat layout and prints zeros rather than warning that it recognised nothing, so a reader cannot tell "no data" from "data in a shape I do not understand." That is a shortcoming in the reader function for this experiment in the analysis script — at minimum it should detect the old flat layout, or print a note that it found files but zero parseable cells. The experiment problem is more serious and lives in the experiment source for s03: the runs that produced these files never populated the density ratio at all and recorded a mutual information of exactly zero everywhere, which points at either the fitted hybrid not being handed through so the selected-features branch was skipped, or the mutual-information estimator flooring to zero on these antibody representations. That needs a fresh run of the current code with the selection actually reaching the density-ratio branch before anyone can say whether the mechanism claim holds. The design question for you is whether s03 belongs in this preliminary report at all in its current state: it is a mechanism diagnostic on antibody, genomic, and tcga datasets, not a molecular win/loss count, and until it is re-run against the new schema it can only ever print dashes. My recommendation is to re-run s03 on current code, confirm the density ratio is being written, and only then wire it into the report; the reader also needs a one-line hardening so that "files present but nothing parseable" is stated out loud instead of masquerading as a clean zero.


## s04 — activity cliffs, does the hybrid predict the hard compounds better

**What the experiment is asking.** An activity cliff is a pair of molecules that look almost identical by their chemical fingerprint but have very different measured activity. These are the compounds a model is most likely to get wrong, because it wants to give near-identical inputs near-identical predictions. This experiment first picks out the cliff compounds using a fixed, representation-independent rule (ECFP4 Tanimoto similarity above 0.55 combined with a large jump in the label), and then asks a narrow question: on those cliff compounds specifically, does a nearest-neighbour predictor built on the feature-selected hybrid make a smaller error than the same predictor built on the single best representation? Because it uses the ECFP4 fingerprint to even define what a cliff is, the experiment only makes sense for small-molecule (molecular) datasets, and the code says so out loud. For the hybrid to "work" here, its error on cliff compounds (RMSE for a regression dataset) should come in lower than the best individual representation's error on the same compounds.

**What the table shows.** The table is meant to have four columns: the dataset name, a state column, the hybrid's error on cliff compounds ("hyb cliff"), and the best single representation's error on cliff compounds ("best rep cliff"). The best-rep number is not a single stored value; the reader loops over every representation in the file, reads each one's cliff error, and keeps the best one, meaning the smallest error for a lower-is-better dataset or the largest score for a classification dataset. The problem is that in this report every single row is in the skip state, so both number columns are blank. Every dataset listed is either an antibody, reaction, or nucleotide task, and each one is stamped as out of scope. Two representative rows, quoted verbatim: "abagym_EGFR               skip: molecular-only expe" and "gb_human_enhancers_cohn   skip: nucleotide domain:". Under the header the report even announces this itself: "Non-molecular / no-ecfp4 datasets are skipped by design."

**What it is actually telling us, and why I do or do not trust it.** Taken at face value the table says nothing at all, because not one molecular dataset appears in it. That is not a bug in the science, it is a data-plumbing accident. I confirmed against the source that the experiment deliberately writes a skip stub for any non-molecular dataset, so the twenty-nine skip rows are all correct and expected. The real issue is that a genuine molecular result does exist on disk and simply never made it into this table. There is a file for the "logd" dataset, but it lives in a separate results tree (the server-synced folder) rather than the one this report was generated from, and the reader only ever reads one folder per experiment. When I open that logd file by hand it is exactly the kind of answer this experiment is supposed to surface: on the cliff compounds the hybrid's error is 0.700 while the best single representation (pdv) is at 0.748, so the hybrid is meaningfully better on the hardest compounds, which is the headline this experiment was built to produce. Note one honest caveat even inside that file: a plain random-forest baseline on pdv reaches 0.631 on the same cliffs, beating both the hybrid and the best-rep nearest-neighbour, so the hybrid wins the nearest-neighbour contest but is not the best predictor overall. All of the other datasets we care about for this question (caco2, herg, drd2, qm9, and so on) are simply absent from the report entirely, so I cannot say whether the effect holds up; that needs the server results to be present in the folder the report reads.

**So what is wrong, and whose fault.** The experiment itself is behaving correctly and I would not touch it: the molecular-only guard is intentional, the skip stubs are honest, and the one molecular file that exists produces a sensible, on-target answer. The fault is entirely on the analysis side, and it is specific. The reader locates an experiment's output by basename and keeps only the first matching directory it happens to walk, so when the same experiment has results in two trees (a local folder full of skips and a server folder holding the actual molecular runs) it silently reads the skip-only folder and drops the real data. That is the thing to fix in the analysis reader, in how it resolves the experiment directory, not in the experiment file. There is also a smaller design question for you underneath it: this report was clearly run against a results root that had no molecular s04 results in it at all, so the more basic answer is that the molecular results were never synced into the folder being analysed. Until the molecular datasets are actually present in the directory the reader chooses, the s04 section will keep printing a wall of skips even though the experiment ran fine and, on the one dataset we can see, the hybrid is winning on the compounds that matter most.


## s05 — kNN prediction in the hybrid space versus the best single representation

**What the experiment is asking.** This is one of the core claims of the whole project, phrased as a nearest-neighbour test. If the hybrid really is a better feature space than any one representation, then a plain k-nearest-neighbours predictor built in the hybrid space should predict the label better than the same kNN predictor built in the single best representation's space. The experiment runs a distance-aware hybrid search, then for a sweep of feature budgets it evaluates hybrid kNN under cross-validation, and separately evaluates a kNN in every individual representation. The hybrid "works" here if its kNN prediction beats the strongest single-representation kNN, and it is a per-dataset win or loss counted individually, never averaged, because the metrics differ by domain: reaction regression uses RMSE where lower is better, and antibody regression uses a rank/fit score (Spearman rho or R2) where higher is better. The experiment sign-corrects every delta itself so that a positive number always means the hybrid improved, regardless of which direction the raw metric runs.

**What the table shows.** Each row is one dataset. The "best rep kNN" column is the score of the best single representation's kNN. The "hyb kNN" column is the hybrid's kNN score at one deliberately pre-chosen setting. The "Δ(signed)" column is the hybrid minus the best rep after sign correction, so positive is a hybrid win, and the "win" column marks yes, no, or a tilde for a near-tie inside a small threshold. It is worth being precise about which hybrid number is shown: the reader deliberately reads the pre-registered "fixed reference" cell, meaning the budget nearest 100, the unweighted hybrid, at the larger k value, chosen in advance and not cherry-picked. It explicitly refuses to use the experiment's other stored number, the post-hoc maximum over every budget, condition, and k, because that one is optimistically inflated by multiple comparisons. Representative rows read verbatim: "buchwald_hartwig  16.938  15.415  +1.523  yes" and "abagym_HER2  0.332  -0.001  -0.332  no". The block ends with the counted tally, "hybrid kNN beats best single-rep kNN: +4  ~2  -9  (15 datasets)".

**What it is actually telling us, and why I do or do not trust it.** Read honestly, this section is a loss for the hybrid: four wins, two ties, nine losses across fifteen datasets. The single win with real magnitude is buchwald_hartwig, and even there both models are poor, because the reaction kNN sits at RMSE 16.9 versus 15.4, so the hybrid is only less bad, not good. Every other delta is tiny, on the order of a few hundredths of a rho, which for a Spearman correlation estimated over five folds is comfortably inside the noise band. Two of these datasets are essentially coin-flips already flagged as ties. One value is genuinely degenerate and worth staring at: abagym_HER2's hybrid cell is -0.001, meaning the pre-registered budget-100 unweighted hybrid produced essentially zero rank correlation while the best single rep managed 0.332. That is the honest fixed cell collapsing to noise, not a computed win being thrown away, but it drags the tally. I checked the actual result JSONs and I could confirm the schema and the scale but not reproduce the exact printed numbers, because every s05 JSON in the local tree predates the summary/fixed-reference schema and carries an empty summary block. Buchwald's local file, for example, gives best-rep RMSE 16.921 from the onehot_components rep at k=10 against the report's 16.938, which is consistent with the report having been generated from a slightly newer server snapshot that populated the summary. So the report file itself is trustworthy and self-consistent; it simply was not produced from the copies sitting in this checkout. One more thing the table does not say out loud: the whole section only covers one reaction dataset and fourteen antibody datasets. There are no molecular, tcga, or genomic rows, so this "core claim" is being judged almost entirely on antibody rho deltas that are near zero.

**So what is wrong, and whose fault.** I do not see an experiment bug in the computation. The kNN neighbour count is clamped to the training size, the weighted and unweighted conditions are both genuinely applied, and the sign correction is handled in the experiment source at the point where the delta is formed, so the reader can trust the sign. The near-zero HER2 hybrid is a real result of the pre-registration discipline, not a divide-by-zero or a crash. The most important issue is a design question for you about a stacked comparison, and it lives in the experiment source `tests/experiments/similarity/s05_knn_prediction.py`. The baseline is not a fixed cell: the "best rep" is chosen as the best over all representations after each representation is already allowed to pick its own best k in-sample. So the baseline gets a double grid-search advantage, over reps and over k, while the hybrid is pinned to a single pre-registered budget, k, and unweighted setting. That asymmetry systematically flatters the baseline and can turn genuine hybrid parity into a printed loss, so at least part of the nine losses may be this handicap rather than a real deficit. I would either give the hybrid an equally pre-registered single-rep baseline, or report both sides at their post-hoc maxima symmetrically, and label clearly which is which. The analysis reader in `tests/analysis/firstpass_notready.py` has a smaller, defensible shortcoming: it collapses the entire budget sweep, both k values, and the weighted condition down to the one honest fixed cell, so a reader cannot see whether a larger budget would have rescued a dataset like HER2, or whether the importance-weighted variant ever mattered. That collapse is the correct anti-cherry-picking choice for the headline, but it would help to also print the post-hoc-max delta beside the fixed one so the ceiling and the honest number sit side by side. Finally, the empty-summary local JSONs are a housekeeping problem worth fixing so the reader can be re-run against this checkout without silently dropping every s05 row.


## s06 — applicability domain: does distance-to-training predict when the model is wrong?

**What the experiment is asking.** When you deploy a model, a useful safety check is: if a new example sits far away from everything the model was trained on, you should trust its prediction less. This experiment tests whether that "distance to the training set" actually tracks how wrong the model is. It measures the distance from each held-out example to its five nearest training neighbours, measures the model's error on that example, and computes the rank correlation (Spearman rho) between the two. A high positive correlation means far-away examples really do get bigger errors, so the distance is a usable "applicability domain" flag. The hybrid would be "working" here if measuring distance in the hybrid's feature space flags unreliable predictions better than measuring it in the plain stacked-together (concat) feature space does — that is, if the hybrid column beats the concat column.

**What the table shows.** There are three number columns per dataset. The "concat" column is the Spearman correlation between distance-in-concat-space and the model's error. The "hybrid" column is the same correlation but with distance measured in the hybrid space. The delta column is hybrid minus concat, and because higher correlation is better, a positive delta means the hybrid's distances are the better reliability flag. One important detail the header states but is easy to miss: the errors used here come from a "neutral" model — a random forest trained on the concat features, not on the hybrid. That is deliberate, so that a hybrid distance advantage cannot be an artifact of the hybrid model marking its own homework. Every number is pooled across all cross-validation folds at k equals 5 neighbours. Representative rows, quoted verbatim: "abagym_VEGF  0.020  0.174  +0.153" is a case where the hybrid clearly helps, and "ginkgo_heparin  -0.055  -0.615  -0.560" is a case where the hybrid distance is strongly, wrongly anti-correlated with error.

**What it is actually telling us, and why I do or do not trust it.** The headline honest reading is that this signal is weak and does not point in a consistent direction. Look at the spread: the best absolute correlation anywhere is "flab_immunogenicity_marks  0.391  0.413  +0.022", and even there both numbers are only moderate and the hybrid barely moves the needle. Most rows hover near zero — "flab_polyreact_jain_bvp  0.147  0.151  +0.004", "abagym_Ang2  -0.043  -0.045  -0.002". The deltas scatter to both sides: several small hybrid wins (abagym_VEGF +0.153, flab_aggregation_jain_hicrt +0.142, flab_aggregation_jain +0.100) sit next to several hybrid losses ("abcov_kd  0.135  -0.081  -0.216", where the hybrid actually flips the sign, and "ginkgo_titer  0.188  0.003  -0.184"). Unlike some other experiments, this is not a tiny-sample problem — each rho is computed over every validation point across all folds, which is hundreds of examples, so these near-zero values are genuinely near zero, not noise from five data points. The experiment's own docstring says exactly this: as of 2026-06-03 the regression correlation is "near zero and sign-inconsistent," and it calls that a real negative finding rather than a bug. I believe that. The one row I actively distrust is ginkgo_heparin at hybrid -0.615: a strong negative correlation means that in the hybrid space, being farther from training goes with lower error, which is backwards for an applicability domain. Ginkgo is a small antibody dataset (roughly 94 to 242 examples), so per-fold hybrid feature selection can easily overfit and produce a pathological geometry; I would treat that -0.560 delta as a degenerate artifact, not a finding. One row, "gb_human_enhancers_cohn  --  --  --", is blank because that genomic dataset's result file has no usable neutral-model correlation stored — most likely its folds were dropped during the per-fold hybrid build, leaving the correlation empty. I cannot confirm the exact cause from my local copy because that particular file did not sync down; it needs the server data.

**So what is wrong, and whose fault.** Mostly this is a genuine, cleanly-reported negative result, and I would not "fix" it into looking positive. There are three things to separate out. First, a real design question for you that sits in the experiment itself, in tests/experiments/similarity/s06_applicability_domain.py: the correlation is computed on distances and errors pooled across folds without re-standardizing per fold, and Spearman is rank-based, so if one fold happens to have systematically larger distances and also larger errors it can inject a between-fold correlation that is not really about applicability domain. On small datasets like the Ginkgo and abagym ones this could be part of what is driving the sign instability, and it is worth deciding whether to standardize distances and errors within each fold before pooling. Second, an analysis-reader shortcoming in read_s06 in tests/analysis/firstpass_notready.py: the reader compares hybrid against concat, but the actual KIRBy question the project cares about is hybrid versus the best single representation, and the per-representation correlations are all sitting in the JSON (23 to 26 reps per dataset) and get thrown away, along with the importance-weighted-hybrid variant. So the table cannot answer "does the hybrid beat the best rep at flagging unreliable predictions," only "does it beat concat." Third, a smaller reader robustness gap: read_s06 prefers the neutral-model numbers but silently falls back to the tautological hybrid-model numbers if a file is missing the neutral block, which would mix two different meanings into one column without any marker. None of these change the bottom line, which is that for these representations distance-to-training is a weak and inconsistent reliability signal, and the hybrid does not reliably improve it.


## s07 — noise bridge: does the hybrid mistake fewer real activity cliffs for "noise"?

**What the experiment is asking.** Automatic noise detectors work by looking at each compound's nearest neighbours: if a compound sits among neighbours whose measured values are very different from its own, the detector flags it as probable noise. The problem is that a genuine activity cliff — two nearly identical molecules or antibody sequences with genuinely very different activity — looks exactly like noise to that kind of detector, even though it is real signal. This experiment first builds a list of ground-truth activity cliffs using a representation-independent rule (edit distance on the heavy-chain sequence for antibodies, ECFP4 Tanimoto similarity for small molecules), so the cliff list does not depend on any embedding. It then runs the neighbour-based noise detector in two feature spaces — the hybrid's feature space, and the space of each individual representation — and asks what fraction of the compounds the detector flags as "noise" are actually those ground-truth cliffs. That fraction is called the cliff-contamination rate, and lower is better: a good feature space should separate the true cliffs from the ordinary noisy points so that fewer real cliffs get swept up in the noise flag. The hybrid "works" here if its contamination rate is lower than the best single representation's, meaning it protects real cliffs from being thrown away.

**What the table shows.** Each row is one dataset. The "best rep" column is the contamination rate of the single individual representation that scored lowest — that is, the best-case baseline, the rep among all of them that let through the fewest real cliffs. The "hybrid" column is the hybrid's own contamination rate. "Δ(neg=win)" is hybrid minus best rep, and because lower is better a negative delta would mean the hybrid improved on the baseline. The "win" column applies a tie band of 0.01, so anything within that band prints "~" for a tie, a delta more negative than that prints "yes", and a positive delta prints "no". A representative bad row is "ginkgo_acsins  0.120  0.520  +0.400  no", where the best single rep let 12 percent of its noise flags be real cliffs but the hybrid let 52 percent, a large loss. A representative saturated row is "abagym_Ang2  1.000  1.000  +0.000  ~", where every noise flag in both spaces is a real cliff. Rows like "buchwald_hartwig  --  --  --  ~" print dashes because no usable number exists at all.

**What it is actually telling us, and why I do or do not trust it.** Read down the win column and there is not a single "yes" in the whole table — the hybrid never wins here, it either ties or loses. That result is much less damning than it looks, because two separate degeneracies rig the comparison against the hybrid. The first is how the baseline is chosen: the code sorts every individual representation by contamination rate and takes the very lowest as "best rep", so the hybrid is being asked to beat the single luckiest rep out of dozens, on a metric that is mostly noise. The second, and worse, is what a zero actually means. The contamination rate is defined as the number of real cliffs among the noise flags divided by the total number of noise flags, and the code returns 0.0 whenever nothing at all was flagged as noise. So a representation that detects no noise whatsoever scores a perfect 0.000, and it will always be picked as "best rep". That is exactly what the zero rows are: "abcov_kd  0.000  0.143  +0.143  no" almost certainly means the winning baseline rep flagged nothing, so it scored zero by default, while the hybrid did flag fourteen points, two of which were cliffs, and got punished for actually doing the job. Comparing a detector that fires against one that never fires is not a fair fight. At the other extreme the abagym mutational-scan datasets are saturated at 1.000 in both columns, because on those datasets nearly every pair of sequences is similar-but-different so almost everything qualifies as a cliff; there the metric carries no information for anybody. The genuinely informative middle rows — the flab and ginkgo antibody sets — all show the hybrid losing by margins like +0.071 to +0.400, but several of them rest on tiny cliff counts (I confirmed from the stored files that ginkgo_acsins has only two ground-truth cliffs and abcov_kd only ten), so a single flag landing on or off a cliff swings the rate by tenths. The dashed rows are honest absences: buchwald_hartwig is a reaction dataset with neither heavy-chain sequences nor ECFP4 fingerprints, so no ground-truth cliff source applies and the experiment correctly skips it, and gb_human_enhancers_cohn is genomic for the same reason; the three dashed ginkgo antibody rows most likely found zero ground-truth cliffs at the auto-selected similarity percentile, though I would need the server-side JSON to say whether it was zero cliffs or a failed hybrid arm, because both land as a non-finite delta. One caveat on provenance: the copies of these result files in the local tree are an older schema (they store the rate under `best_rep_fp_rate` and never populated the newer summary field the reader reads), so the exact numbers printed in the report came from a newer server-synced set I cannot open directly; I verified the mechanism from the source and confirmed the local top-three rep values match the report's printed rates.

**So what is wrong, and whose fault.** The core defect is in the experiment source, `tests/experiments/similarity/s07_noise_bridge.py`. The contamination rate returning 0.0 for an empty noise flag set (in the `_knn_noise_fp_rate` helper) is a divide-by-empty artifact that lets a do-nothing representation win the baseline slot, and picking "best rep" as the strict minimum over all reps then guarantees the hybrid is measured against that artifact. Those two together, not the hybrid, are why the win column is empty. I would treat a zero-noise-flagged rep as undefined rather than perfect, and I would compare the hybrid against a more honest baseline than the single best-of-many rep. There is also a real design question for you, separate from the bug: on many of these antibody datasets the ground-truth cliff count is in the single digits, and on the abagym scans it saturates near everything, so the metric has almost no dynamic range on either end — it may only be answerable on datasets with a moderate, non-trivial cliff prevalence, and it might be worth restricting the experiment to those. The analysis reader in `firstpass_notready.py` is comparatively innocent here — it faithfully prints both rates and the oriented delta and does not hide any max or median behind a single number — but it inherits the unfairness by reporting a win/loss verdict against a baseline that can be a degenerate zero, and it gives no hint of how many ground-truth cliffs or noise flags sit behind each rate, so a 0.400 built on two cliffs looks identical in weight to one built on hundreds. Surfacing the cliff count and the noise-flag count alongside each row would make the thin rows visibly thin.


## s08 — optimal dimension: does similarity want a different feature budget than prediction?

**What the experiment is asking.** When we build a hybrid, we choose a feature budget — how many columns from the pool of representations to keep. This experiment asks a simple question: is the budget that gives the best *prediction* accuracy the same as the budget that gives the best *similarity* structure? "Similarity structure" here means SAC, the correlation between how close two molecules look in the hybrid feature space and how close their activity labels actually are — a high SAC means the distances are meaningful, which is what you want for anything nearest-neighbour-like. The worry motivating the experiment is the curse of dimensionality: distances can degrade as you add features even while a random forest keeps improving, so similarity might peak at a *smaller* budget than prediction does. The hybrid "works" in the sense this experiment cares about if there is a coherent, believable sweet-spot budget, and it is interesting if the prediction-optimal budget and the similarity-optimal budget genuinely disagree. It is a null (boring) result if they land on the same budget or if the disagreement is just noise.

**What the table shows.** The report prints one row per dataset with four numbers. `best_rf_bud` is the budget at which the random-forest prediction score was best (lowest error for molecular and reaction datasets, highest R2 or Spearman for antibody, highest AUROC/F1 for classification). `best_sac_bud` is the budget at which the similarity-activity correlation SAC was highest. `#dims` is `n_distinct_dims`, the number of genuinely different feature widths that were actually evaluated across the budget grid — this matters because requested budgets get capped at the size of the feature pool, so several requested budgets can collapse to the same real dimension. `optima_differ` says whether the random-forest-optimal budget and the SAC-optimal budget came out different, but the experiment deliberately refuses to answer that (prints it as suppressed) unless at least four distinct dimensions were seen. Representative rows, quoted verbatim: `abagym_EGFR   50   25   6  True` means prediction peaked at budget 50 and similarity at budget 25 across six distinct dimensions, so the optima differ; `flab_aggregation_jain   50   50   4  False` means both peaked at the same budget of 50; and `ginkgo_titer   500   500   2  None (untrustworthy)` means both landed at 500 but only two distinct dimensions were ever evaluated, so the comparison is refused as unreliable.

**What it is actually telling us, and why I do or do not trust it.** First, an honesty caveat about my own inspection: every s08 result JSON I have locally is stale. All of them carry the old budget grid of 50/500/1000/2000 and have no `n_distinct_dims` field at all, whereas the report clearly used a newer run whose budgets are all drawn from the corrected 10/25/50/100/250/500 grid and which populates `#dims`. So the report was generated against fresher server data that I cannot fully see; I verified the mechanics from the experiment source and from the stale JSON schema, not from the exact numbers printed. Now to the numbers themselves. The seven rows near the bottom that show `#dims` as `--` (ginkgo_colloidal, ginkgo_heparin, ginkgo_hic, ginkgo_pr_cho, humanness_therapeutic, tz_her2_binary, tz_her2_multiclass) are almost certainly the leftover stale files that predate the distinct-dimension diagnostic — those rows still print an `optima_differ` of True or False, but with no distinct-dimension count behind them that verdict is exactly the kind of unguarded claim the newer code was written to suppress, so I would not trust those seven at all. Among the rows that do have a count, most sit at exactly four, which is the bare minimum the experiment is willing to call trustworthy; four distinct dimensions is a very thin basis for declaring an optimum, because the "optimum" is just the argmax (or argmin) of a five-fold cross-validated mean over a handful of budgets, and on these small antibody and reaction datasets those means differ by tiny amounts that reshuffle under noise. So even the "trustworthy" rows are really saying "we picked the best of four-to-six noisy points," which is a weak signal. The one genuinely useful safeguard is working: `ginkgo_titer` with only two distinct dimensions is correctly flagged untrustworthy and its verdict suppressed, which is the behaviour we want. There is also a hidden model choice the reader does not reveal, discussed next, which makes the printed `optima_differ` verdict shakier than it looks.

**So what is wrong, and whose fault.** There are three separable things. The clearest problem is a data-freshness one, not a code one: the seven `--` rows are stale JSONs sitting in the results tree from before the distinct-dimension diagnostic existed, and the reader silently mixes them in beside fresh rows, so the table reads as one clean run when it is actually two schemas stitched together. Those datasets need to be re-run and re-synced from the server before anyone reads their verdicts. The second issue is an analysis-reader shortcoming in `read_s08` inside `tests/analysis/firstpass_notready.py`: the experiment actually computes an optimal budget for six downstream models — random forest, xgboost, ridge, svm, mlp and lightgbm — and stores them all under `best_model_budgets`, but the reader prints only the random-forest one and calls it "the" prediction optimum. That matters because the whole `optima_differ` headline is defined against the random-forest budget specifically, so if random forest is the noisy outlier while the other five models agree with each other (and my one readable local case, abagym_Ang2, shows exactly that pattern — random forest at 500 while all five others agree at 50), the table will announce a prediction-versus-similarity disagreement that is really just random forest being erratic. The reader hides the other five budgets, the SAC value itself, and the number of distinct dimensions behind a single flag. The third is a design question for you, not a bug: an argmax over four-to-six cross-validated means on datasets of a few hundred samples may simply not be able to resolve a "sweet-spot budget" at all, and the current four-distinct-dimensions gate is a blunt pass/fail rather than a real confidence statement. If you want this experiment to say something durable, the honest fix is on the experiment side (report the spread of the per-model optima and how far apart the top budgets' scores actually are, so a one-column argmax is not asked to carry the whole conclusion) plus a reader change to stop reducing six models to random forest alone. As it stands I would treat s08's disagreement verdicts as suggestive at best and not quote any of the `--` rows.


## s09 — cross-dataset roll-up of the similarity story (the summary of s02 through s08)

**What the experiment is asking.** s09 is not really an experiment in its own right — it is a bookkeeper that gathers the results of six earlier similarity experiments (s02 hybrid similarity, s04 activity cliffs, s05 kNN prediction, s06 applicability domain, s07 noise bridge, s08 optimal dimension) and asks one question across every dataset at once: does the hybrid consistently beat the best single representation on all of these similarity-flavoured measures, or does the story fall apart when you line the datasets up side by side? For each dataset it computes a handful of deltas — how much the hybrid improved the structure-activity correlation, how much it cut the error on activity cliffs, how much it improved kNN prediction, how much it improved the distance-versus-error correlation, how much it reduced noise contamination, and the ratio of optimal feature budgets between two downstream models. It would count as the hybrid "working" here if those deltas came out positive for most of the datasets, ideally with a Wilcoxon test saying the pattern is unlikely to be chance.

**What the table shows.** In this report there is no table. The entire s09 block reads, verbatim: "[s09]  cross-dataset summary — per-dataset deltas (combined file; NO mean headline)" followed by a single line, "(no s09 file)". Had the file existed, the reader would have printed one row per dataset with four columns — sac_delta (change in structure-activity correlation), knn_delta (change in kNN score), ad_delta (change in the applicability-domain distance-error correlation), and cliff_red% (percent reduction in error on activity cliffs) — each written with a plus or minus sign so that positive always means the hybrid did better. It would have deliberately ignored the mean and Wilcoxon numbers that s09 itself computes, honouring the locked "no averaging across datasets" rule, and shown only the per-dataset values. None of that got printed because the reader looked for a results directory named "s09_cross_dataset_summary", found nothing, and bailed out at the "(no s09 file)" guard.

**What it is actually telling us, and why I do or do not trust it.** The empty block is not a blown-up number or a degenerate calculation — it is simply that s09 was never produced by this run. I confirmed that directly on disk: there is no "s09_cross_dataset_summary" directory anywhere under the results tree, not in the synced server results, not in the local results, and not in either of the two smoke-test result folders — even though every one of those folders does contain the s02 through s08 inputs that s09 would consume, and the smoke folders even contain s10 through s13. So the inputs exist and the downstream experiments exist; only the aggregator is missing. The reason is structural. s09 is unique among the similarity experiments in that it cannot run per-dataset — it needs every dataset's results loaded together in one process. In the launcher it is a separate mode called "full_cross" (experiment 9), invoked as a one-off job over all four molecular datasets at once, and that job was simply never part of the per-dataset run plan that produced everything else in this report. There is a second, quieter wrinkle: when experiment 9 is run through the main similarity runner it does not even write a "s09_cross_dataset_summary" directory — it tucks its output inside a combined results file under a key called "exp9_cross_dataset". The only thing that writes the directory the reader is hunting for is the standalone s09 module, and that standalone module was never scheduled. So even if someone had run the cross-dataset step through the main runner, this reader would still have printed "(no s09 file)". I am confident in this diagnosis because it is verifiable from the code and the filesystem without needing the server; the only thing I cannot see is the server-side job history, but the absence of the directory in the synced results is decisive enough.

**So what is wrong, and whose fault.** There is no experiment bug here in the sense of a wrong number — s09's arithmetic is actually careful, with explicit metric-direction handling, guards against divide-by-zero on the cliff and noise reductions, and logged reasons when a dataset is dropped. The real problem is an orchestration gap plus a naming mismatch, split across two places. The orchestration gap is that the run plan never fired the cross-dataset job, so s09 has no output at all; that is a scheduling decision for you, not a code fix — someone has to decide to run the "full_cross" step after the per-dataset similarity jobs finish, and to run it over the full dataset list rather than the hard-coded default of logd, caco2, herg_ki and qm9. The naming mismatch is a genuine defect worth fixing: the main runner stores its cross-dataset result under the key "exp9_cross_dataset" inside a combined file, while the reader and the standalone module both expect a directory called "s09_cross_dataset_summary", so these two paths can never meet. That should be reconciled either in the similarity runner (so experiment 9 writes the same directory name the standalone module and the reader agree on) or by pointing the reader at the combined-file key as a fallback. Finally, a small honesty gripe about the reader: "(no s09 file)" is technically true but unhelpful — it cannot distinguish "the aggregator was never run" from "the aggregator ran and produced nothing", and given that s09 is a known dependent step, the reader would do the user a favour by saying so explicitly rather than leaving a bare parenthetical.


## s10 — does re-weighting the hybrid's features by importance help the downstream model?

**What the experiment is asking.** Once we have built a hybrid feature set, we have an importance score for every feature (how much a LightGBM model leaned on it). The idea in s10 is: instead of feeding all those features to a downstream model with equal footing, multiply each feature column by the square root of its importance, so that features the model cared about get stretched out and useless ones get squashed toward zero. That re-weighting changes distances between points, which is exactly what distance-sensitive models care about. s10 runs four such downstream models on the hybrid feature set — a nearest-neighbour regressor, a Gaussian process, a support-vector regressor, and a "q-RASAR"-style model that bolts on four extra similarity descriptors (the average and spread of neighbours' labels, and the nearest and mean distances). For each, it compares the weighted version against the unweighted version and reports the difference. The hybrid is "working" here only in the narrow sense that weighting its features makes the downstream model better; a positive number means the weighting helped, a negative number means it hurt.

**What the table shows.** There is one row per dataset and four columns, and every printed number is the *hybrid* delta for one of the four downstream tasks — the per-representation results the experiment also computes are not shown at all. The column `knnΔ` is the weighted-minus-unweighted difference for the nearest-neighbour regressor; importantly the reader silently prints the k=10 setting only (it tries k10, then k5, then k20 and stops at the first it finds), so k=5 and k=20 are computed and thrown away. `gpΔ` and `svrΔ` are the weighted-minus-standard differences for the Gaussian process and the support-vector regressor. `qrasarΔ` is a different comparison: it is the weighted-similarity model against the plain base model (`delta_w`), so it bundles together *two* changes at once — adding the four similarity descriptors and weighting the distances — rather than isolating the weighting. Every number is a mean across the five cross-validation folds, and all deltas have already been sign-flipped so that positive means improvement regardless of whether the dataset's metric is error-based or correlation-based. Representative rows, quoted verbatim: "abagym_Ang2               +0.004  +0.064  +0.056   -0.030" and "buchwald_hartwig          -0.030  +1.065  +0.283   +0.368". Classification datasets show dashes in the Gaussian-process and support-vector columns because those two tasks are regression-only, for example "humanness_therapeutic     +0.004      --      --   +0.010".

**What it is actually telling us, and why I do or do not trust it.** The honest read is that importance-weighting the hybrid's features does almost nothing useful, and this matches the experiment's own docstring, which states weighting is "neutral-to-negative downstream." Across the antibody rows the deltas are tiny and their signs are all over the place: abagym_Ang2 is slightly positive on three of four tasks, abagym_HER2 ("-0.097  +0.076  -0.036   -0.060") is mostly negative, abcov_kd ("-0.070  -0.105  -0.015   -0.002") is negative on all four. These are correlation-scale metrics (R2 or Spearman rho) living between zero and one, so a swing of a few hundredths is exactly the size of noise you get from a five-fold mean, and there is no consistent direction to lean on. The one row that looks dramatic, buchwald_hartwig with a Gaussian-process delta of +1.065 and a support-vector delta of +0.283, is a trap: buchwald is a reaction-yield dataset scored in RMSE units where the error is around 14, so those numbers are in a completely different scale from the antibody rows and cannot be compared down the column or across to them. Worse, the Gaussian process on this dataset is wildly unstable — the older local copy of this same experiment shows the weighted Gaussian process making RMSE explode from 14.2 to 27.3, a catastrophic blow-up, whereas the server run in this report shows it helping by 1.065; a single fold-averaged number hides that this model can swing by units in either direction. I would not trust any single buchwald cell. The genomic row "gb_human_enhancers_cohn       --      --      --       --" is all dashes: the per-representation baselines ran but no hybrid blueprint was ever built for it (the pooled similarity search tends to fail or return nothing on nucleotide sequence embeddings), so every hybrid delta is simply missing. I cannot confirm that particular file's internals because it is not synced locally — the local s10 results are stale, pre-dating the sign-orientation fix (they lack the `deltas_oriented` and `hybrid_status` flags), so the exact numbers in this report exist only on the server.

**So what is wrong, and whose fault.** Nothing here is an outright experiment bug; the four tasks compute what they claim and the sign-orientation is applied correctly. The problems are interpretation and reader design. The biggest reader shortcoming is that the four columns mix metric units across rows — RMSE for buchwald, correlations for the antibody datasets — so the table invites exactly the wrong comparison, reading buchwald's +1.065 as a huge win next to abcov's -0.105; the reader in firstpass_notready.py should at minimum print the metric name per row or refuse to place error-scaled and correlation-scaled rows in the same untagged column. Second, the `knnΔ` column silently reports only k=10 and discards k=5 and k=20, and all four columns discard every per-representation delta the experiment computed, so a real effect that showed up only at a different k or on a specific representation would be invisible. Third, the `qrasarΔ` column reports weighted-versus-base (`delta_w`), which conflates adding the similarity descriptors with weighting them; the cleaner quantity for answering "does weighting help" is `delta_w_vs_uw`, which the experiment already computes and the reader throws away. There is also a design question for you that sits above all of this: s10 does not test the hybrid against the best single representation at all — it tests weighted-hybrid against unweighted-hybrid — so this table cannot be read as a hybrid-versus-rep win under the counts rule, and given that the deltas are dominated by fold noise on correlation-scale antibody data, it is worth deciding whether the weighting question is answerable at this sample size before investing more in it.


## s11 — Bayesian optimization: is a compact hybrid a better search space for library screening?

**What the experiment is asking.** This experiment reframes the hybrid not as a fixed feature set for one prediction, but as the search space for an active-learning loop. The setup imitates screening a compound library: you label a tiny random seed set (5 percent), hide the rest as an unlabelled pool, fit a Gaussian-process surrogate on what you know, use it to pick the single most promising unlabelled compound, reveal that one label, and repeat. The score is how quickly the best value found so far climbs, summarised as the area under the best-so-far curve. The stated hypothesis is that in very high dimensions all pairwise distances concentrate to nearly the same number, so the Gaussian process becomes flat and its acquisition rule collapses to random picking. A compact KIRBy hybrid (around 50 features) is supposed to dodge that and find good compounds in fewer labelled experiments. The hybrid "works" here if its best-so-far curve rises faster than the same loop run on raw 2048-dimensional fingerprints, on PCA, on a random projection, and on pure random acquisition.

**What the table shows.** For s11 the report does not print any performance numbers at all. It prints one row per dataset with a single "state" column that is either a skip reason or the word "RAN" followed by the list of condition names that were attempted. The overwhelming majority of rows are skips, for example "abagym_Ang2  skipped: domain=antibody" and, for the one nucleotide dataset, "gb_human_enhancers_cohn  skipped: nucleotide domain: similarity premise unreliable for sequence embeddings (exp=s11)". Exactly one dataset in this report ran: "buchwald_hartwig  RAN: conditions=['ecfp4_raw', 'tanimoto_ecfp4', 'best_single', 'pca_50d', 'hybrid_50d', 'hybrid_50d_refit', 'random_50d', 'random_acq', 'hybrid_ngboost', 'hybrid_bnn', 'hybrid_gauche_gp']". Note what that "RAN" line does and does not contain: it confirms all eleven search-space conditions executed, but it reports nothing about which one found good compounds fastest. There is no area-under-curve, no hybrid-versus-baseline comparison, no win or loss.

**What it is actually telling us, and why I do or do not trust it.** The wall of skips is mostly correct and by design, not a failure. The experiment source refuses any domain that is not molecular or reaction, refuses classification (because best-so-far saturates to the top label the instant one active compound is picked, so every condition ties at a meaningless score), refuses datasets under 200 rows, and refuses anything without at least twenty distinct groups for an honest group-aware seed/pool split. Every antibody row is caught by the domain rule, and the nucleotide row is pre-empted even earlier by the harness. So far so reasonable. The real problem is what is missing and what is invisible. First, the molecular datasets where this hypothesis is most testable — caco2, herg, logd, esol, drd2 and the rest — do not appear in the s11 block at all, which means no s11 result files existed for them under the results tree this report was read from; the single reaction dataset buchwald_hartwig is the only thing that produced output. Second, even for that one dataset the report is silent on the outcome, because the reader only lists condition names. I cannot judge whether the compact hybrid searched more efficiently than raw fingerprints, because the number that would answer that was never printed. Third, I checked the only fully-populated s11 result I have locally, a smoke run on herg, and every single condition tied at an area-under-curve of exactly 8.0 with the best-so-far curve pinned at 1.0 from the first step. That smoke run used only 200 rows and a budget of 8 iterations on a near-binary label, so it is the exact saturation degeneracy the source warns about — not evidence about the real experiment, but a clear illustration that on small or saturated data every condition collapses to the same score and the comparison carries no signal. Whether the real buchwald_hartwig run avoided that, I genuinely cannot tell from local data; it needs the server result file.

**So what is wrong, and whose fault.** There is no clear experiment bug in the skip logic; the gating is defensible and the source is careful about the saturation and no-random-split hazards. The dominant issue is the analysis reader. The read_s11 function in the analysis script is a coverage stub: for a dataset that ran it prints only the condition names and throws away every metric the experiment computed — the per-condition area-under-curve, the iterations-to-top-1-percent and top-5-percent counters, the count of Gaussian-process fit failures, and the "this curve secretly degenerated to random" flag that the source deliberately stores. That means the central claim of the experiment is completely unreadable from this report even when the experiment succeeds. The fix belongs in the reader, not the experiment: it should print, for each ran dataset, the hybrid's area-under-curve against the raw-fingerprint, PCA, random-projection and random-acquisition baselines, and surface the degenerate-random and Gaussian-process-failure flags so a saturated or collapsed run is visibly marked rather than shown as a bare "RAN". The second issue is a data-coverage one for you, not a code fault: the molecular datasets that are the whole point of a library-screening argument have not been run or synced here, so the only evidence in front of us is one reaction dataset whose result we cannot see. Before this experiment can support any conclusion, the molecular runs need to exist and the reader needs to actually report their curves.


## s12 — cross-domain activity cliffs

**What the experiment is asking.** An "activity cliff" is a pair of molecules (or antibodies, or cells) that look almost identical in feature space but have very different measured labels — the kind of pair that trips up any model, because it has to predict two very different answers from two nearly-identical inputs. The classic cliff test (s04) only works for small molecules, because it relies on chemical fingerprints and Tanimoto similarity. s12 is the generic version: it defines "similar" using ordinary Euclidean distance on the concatenated representations, so it can run on antibody, TCGA, and reaction datasets too. It flags a pair as a cliff when the two members are structurally close and their labels differ by more than two times the typical spread of the labels. Then, on just those cliff points, it asks the KIRBy question: does the feature-selected hybrid predict cliff cases better than the single best representation does? The hybrid "works" here if, on the hard cliff subset, it beats the best individual representation.

**What the table shows.** The report prints one row per dataset with three fields. The "state" column is either "ok" or a skip note. The "best model Δ" column is a single signed number, direction-corrected so that a plus sign always means the hybrid did better on the cliff subset than the best single representation did. That number is measured in the dataset's own metric — Spearman rho or R2 for antibody (higher is better), an error like RMSE for reaction (lower is better), F1 or AUROC for classification. Two representative rows read verbatim: "buchwald_hartwig          ok                         +2.522" and "abagym_HER2               ok                         -0.243". A handful of rows show no number at all, for example "ginkgo_hic                ok                             --", and one genomic dataset is skipped outright: "gb_human_enhancers_cohn   skip: nucleotide do".

**What it is actually telling us, and why I do or do not trust it.** The headline is that this number is a cherry-pick and I do not trust it as printed. Under the hood each dataset's result carries a separate cliff-delta for all six downstream models (I confirmed this in a local file: for abagym_Ang2 the six values run rf -0.049, xgboost -0.137, ridge -0.027, svm -0.041, mlp -0.223, lightgbm -0.141). The reader keeps only the single most favorable model and throws the other five away, so "best model Δ" is the best case out of six, not a typical result. Even after that generous selection the column is mostly negative — abagym_HER2 -0.243, flab_polyreact_jain_cic -0.304, flab_aggregation_jain -0.178, and so on — which means that on the hard cliff cases the hybrid is losing to the best single representation even in its best light. Worse, the numbers rest on almost nothing. In the local abagym_Ang2 file there are only 22 cliff compounds out of 397, spread across five folds, and the metric is only computed on a fold's cliff members when there are at least two of them — so each fold's cliff score is a Spearman correlation over roughly four or five points, which swings wildly by chance. The one big positive, buchwald_hartwig +2.522, is the clearest warning sign: that is a huge error swing on a reaction dataset, almost certainly a saturated or near-degenerate value computed on a tiny cliff handful, not a real hybrid win. The empty "--" rows (ginkgo_hic, ginkgo_colloidal, ginkgo_pr_cho, the tz_her2 pair) are datasets where no cliff-delta was produced — either no cliffs were found or the hybrid blueprint search returned nothing. The genomic skip is correct and expected: this cliff notion does not transfer to nucleotide data, and the experiment says so.

One important caveat about verification. The result JSONs I have locally are stale. They date from May, use the old absolute similarity cutoff (sim_threshold 0.1) and the old schema that stored a key literally named "error" set to "no_cliffs_found" — and under that old cutoff most datasets, including buchwald_hartwig, found zero cliffs. The report in prelimResults clearly reflects a newer server run that uses the distribution-relative percentile sweep (the code now auto-selects a percentile aimed at a 10 percent cliff prevalence), because that run actually finds cliffs and prints deltas where my local copy shows none. So I can explain exactly how every column is built and why it is fragile, but I cannot reproduce the specific server numbers locally; confirming the buchwald +2.522 outlier and the exact cliff counts behind each row needs the server results tree.

**So what is wrong, and whose fault.** There is a real experiment fragility, an analysis-reader shortcoming, and a design question. The experiment fragility is the tiny cliff sample: computing a rank correlation or error on four-or-five cliff points per fold produces numbers that are dominated by noise, and the percentile sweep guarantees only that some pairs get labeled cliffs, not that there are enough of them per fold to measure anything stably. That is inherent to the method in the experiment source, not a coding bug — the code behaves as intended. The analysis-reader shortcoming is squarely in read_s12 in firstpass_notready.py: it reduces six per-model deltas to the single most favorable one via a max, so the table systematically flatters the hybrid, and it never prints the cliff count (n_cliff_compounds is right there in cliff_info) so a delta resting on 4 points looks identical to one resting on 400. I would have the reader show the median or full spread across the six models and print the cliff count next to each delta, so an outlier like buchwald +2.522 on a near-empty cliff set is visibly untrustworthy. There is also a minor stale-schema mismatch: the old "error": "no_cliffs_found" files are not recognized as skips by the reader (it only checks for the newer "skipped" flag), so they fall through and render as "ok --" rather than as an honest "no cliffs" note; a fresh server rerun makes this moot. The design question for you is whether a per-fold cliff subset this small can answer the hybrid question at all, or whether cliff performance should be pooled across folds before scoring rather than averaged fold-by-fold.


## s13 — does the hybrid space cluster and retrieve better?

**What the experiment is asking.** The idea is that if the hybrid distance really is a better way to measure how similar two molecules or antibodies are, then two things should follow. First, if you cluster the points in hybrid space, the members of each cluster should have more similar activity labels than clusters built in any single representation's space — that is "clustering coherence." Second, if you pick any point and pull its nearest neighbours in hybrid space, those neighbours should have activity values close to the query point's — that is "retrieval." The experiment builds several spaces for each dataset (every single representation on its own, a PCA-compressed version of everything concatenated, and the selected hybrid), scores each one on both coherence and retrieval, and asks whether the hybrid beats the best single representation on each axis. The hybrid "works" here if it wins both, and the experiment explicitly flags when the two axes disagree.

**What the table shows.** The report prints one row per dataset with three columns. "clust win" is a boolean straight out of the file that says whether the hybrid's clustering coherence was higher than the best single representation's coherence (higher is better for coherence). "retr win" is a boolean saying whether the hybrid's mean neighbour-activity gap was smaller than the best single representation's (lower is better for retrieval). "agree?" says whether those two booleans point the same way — both wins or both losses. A representative row reads "abagym_EGFR   False   True   False", meaning on that antibody dataset the hybrid lost on clustering, won on retrieval, and so the two axes disagreed. One genomic dataset reads "gb_human_enhancers_cohn   (no hybrid/summary)", meaning the file has no summary block at all. The block ends with the tallies "hybrid wins clustering: 11/24   retrieval: 22/24".

**What it is actually telling us, and why I do or do not trust it.** The headline pattern is that the hybrid almost always wins retrieval (22 of 24) but only wins clustering about half the time (11 of 24). I do not trust the retrieval number as a real-world result, and the experiment's own source code says why: the hybrid's features are selected using every sample's label, whereas the PCA and single-representation baselines are unsupervised. A comment in the source states plainly that this gives the hybrid a tautological advantage on these in-sample metrics, so a near-clean retrieval win is closer to "the label-selected space organises the labels it was fitted on" than to any claim about unseen molecules. On top of that, the win test has no tolerance band — it is a strict inequality. In the local copy of the abagym_EGFR result the hybrid's retrieval gap is 0.2141 against the best single representation's 0.2134, a difference of seven ten-thousandths, and that razor-thin margin is reported as a clean win or loss with no hint that it was a coin toss. The bar the hybrid has to clear is also the single best of roughly twenty-six representations on each axis, and the "best" coherence for each space is itself a maximum taken over three cluster counts (three, five, and ten), so both sides are quietly cherry-picking the most flattering cluster count before the comparison. There is also a schema problem visible in the "agree?" column: several rows (the ginkgo, humanness, and trastuzumab datasets) show "None" rather than True or False, because those older files predate the "metrics_agree" field and the reader simply prints whatever it finds. Finally, the local result files disagree with the report — locally abagym_EGFR shows a retrieval loss while the report shows a win — which tells me the report was generated against a newer server run I cannot fully reconcile without the server data.

**So what is wrong, and whose fault.** There is one genuine experiment gap: the "no hybrid/summary" row for the genomic enhancer dataset means the hybrid step failed there and produced no summary, and that is worth chasing in the experiment source, since a silently missing summary is indistinguishable from a dataset that simply was not run. The larger issue is a design question for you, not a bug: comparing a supervised, label-selected hybrid against unsupervised baselines on an in-sample metric is close to unfair by construction, and the experiment author already wrote that warning into the file — so the retrieval win count should probably not be presented as evidence at all until the comparison is made fair (for example, selecting on a held-out split). The reader in firstpass_notready.py has real shortcomings that make this worse: it throws away every actual number the file contains — the coherence values, the retrieval gaps, the size of each margin, and which representation was the one to beat — and prints only three booleans, so a seven-ten-thousandths loss and a large decisive loss look identical, and it inherits the no-tolerance win test rather than showing a margin the reader could judge. It also prints the raw "None" from the missing-field files without explaining that it means "old schema," which reads as a data error rather than schema drift. The clustering count of 11 of 24 is the more honest of the two numbers because coherence is not helped nearly as much by the supervised-selection advantage, and a genuinely mixed result there is believable — but I would not report either count without also showing the per-dataset margins so a colleague can see how many of these are ties.

## n01 — activity-cliff framework, does the hybrid predict cliffs as evenly as single reps

**What the experiment is asking.** An "activity cliff" is a pair of molecules (or antibodies) that look almost identical structurally but have very different measured activity. Models usually do worse on these because the structure barely changes while the label jumps. The experiment first finds the cliff compounds using a reference that has nothing to do with any learned representation — ECFP4 Tanimoto similarity for molecules, edit distance for antibodies, or Euclidean distance on the concatenated features as a fallback — so that no representation is being judged against cliffs derived from its own embedding. Then, for each downstream model, it measures the prediction error separately on the cliff compounds and on the non-cliff compounds and takes the difference, which it calls the gap. A gap near zero means the model handles cliffs about as well as everything else. The hypothesis is that the feature-selected hybrid should have a smaller cliff-versus-non-cliff gap than any single representation, meaning the hybrid smooths out the cliffs. That is what would count as the hybrid "working" here.

**What the table shows.** For every dataset the report prints one row per downstream model (rf, xgboost, ridge, svm, mlp, lightgbm). The "hyb gap" column is the hybrid's cliff-minus-non-cliff error, sign-normalized so that for a lower-is-better metric it is cliff error minus non-cliff error and for a higher-is-better metric it is the other way around; the header tells us smaller is meant to be better. The "best rep gap" column is the gap of the single representation whose gap is closest to zero — the experiment sorts the per-rep gaps by absolute value and reports the top one. The "hyb smaller?" column is the reader's verdict on whether the hybrid beat that best single rep. A representative real row is "abcov_kd  ridge  0.054  0.023  no", meaning the hybrid's gap of 0.054 is worse than the best rep's 0.023. Another is "buchwald_hartwig  ridge  2.060  -0.464  no", where the reaction-scale errors are large and the best rep's gap is actually negative. Some datasets show only dashes, for example every model row of "abagym_Ang2" reads "--  --" with a blank verdict, and "ginkgo_hic" collapses to the single stub line "(stub: too_few_cliff_compounds)".

**What it is actually telling us, and why I do or do not trust it.** I do not trust the "hyb smaller?" column, and the reason is concrete. The experiment defines the "best rep gap" as the rep whose gap is closest to zero — it literally sorts the reps by the absolute value of the gap. But the reader then decides whether the hybrid won by comparing the two numbers with a plain signed less-than: the hybrid is called smaller if its signed gap is below the signed rep gap. Those two rules disagree whenever a gap is negative. I checked every "yes" verdict in this block: there are 36 of them, and in 34 the hybrid's gap is actually larger in magnitude than the rep it supposedly beat. Take "flab_immunogenicity_marks  rf  -0.206  0.035  yes": the reader says the hybrid won because minus 0.206 is less than 0.035, but a gap of minus 0.206 is further from zero than 0.035, so by the experiment's own "closest to zero is best" definition the hybrid is worse. The same thing happens at "ginkgo_colloidal  mlp  -0.428  -0.009  yes", where the hybrid's gap is nearly fifty times bigger in magnitude yet is scored a win. So almost all the apparent hybrid victories here are an artifact of the reader rewarding large negative gaps, and a large negative gap usually just means the handful of cliff compounds happened to be predicted more easily than the rest that fold — a small-sample fluke, not the hybrid smoothing anything. On top of that the gaps themselves are fragile: the cliff error is averaged only over folds that had more than one cliff compound in the held-out set, so on the small antibody and reaction datasets each cliff score rests on one or two folds and a few compounds. The dashed rows and the ginkgo_hic stub are separate and better understood. The stub means the cliff detector could not find enough structurally-similar-but-active pairs to form a cliff set at all. The all-dashes rows, which I confirmed against the local humanness_therapeutic result file, mean the hybrid did run but not a single representation produced a finite cliff gap — the cliff subsets were too small to score — so the experiment never built the comparison record and the reader has nothing to print. I want to be clear that the exact numbers in this report come from newer server-side results than anything on disk here; my local copies of buchwald_hartwig and ginkgo_hic are the older absolute-threshold version that found zero cliffs, so I verified the schema and the failure modes locally but cannot re-derive the server numbers without the synced data.

**So what is wrong, and whose fault.** There are three separate problems. The headline one is an analysis-reader bug in read_n01 in tests/analysis/firstpass_notready.py: it forms the win verdict with a raw signed comparison of the hybrid gap against a rep gap that was selected by absolute value, so a hybrid with a big negative gap is falsely credited as the winner, and that mislabels 34 of the 36 "yes" rows in this section. The verdict needs to compare the two gaps on the same footing the experiment used to pick the rep, namely closeness to zero. The reader also throws away the second and third entries of the top-three-smallest-gap list and never prints how many cliff compounds or folds sit behind each number, so a reader cannot see how thin the evidence is. The second problem is an experiment-level fragility in tests/experiments/noise/n01_activity_cliff_framework.py: the cliff and non-cliff errors are means over only the folds that happened to contain more than one cliff, which on these small antibody and reaction sets is a very noisy estimate and is what produces the wild negative gaps in the first place; it would be worth recording the cliff sample count alongside each gap so degenerate cases can be filtered. The third is a design question for you rather than a bug: n01 describes itself as a molecular experiment, yet the bulk of the rows here are antibody (abagym, flab, ginkgo) and reaction (buchwald), where cliff sets are tiny and the whole cliff-versus-non-cliff gap is dominated by which few compounds landed in a fold. It is worth deciding whether this experiment should report on the non-molecular datasets at all, or whether they should be marked as out of scope the way the header already implies.


## n02 — reliability-weighted training: does down-weighting noisy samples help?

**What the experiment is asking.** The idea is that some training rows have unreliable labels, and we can spot them geometrically. For each sample the experiment looks at its nearest neighbours in a feature space where the features have been re-scaled by how important they are, and asks whether the sample's label agrees with its neighbours' labels. A sample that disagrees with everyone around it is treated as probably noisy and gets a smaller weight when the model is trained. The experiment runs this five ways: an individual representation trained normally, that same representation trained with reliability weights, the hybrid trained normally, the hybrid trained with reliability weights, and the hybrid trained with a "cliff-aware" variant that tries to tell genuine activity cliffs apart from noise. The headline question written into the experiment is which benefits more from this trick, the plain base representations or the hybrid. For the weighting to count as "working" on the hybrid, turning the weights on should move the score in the good direction by a margin bigger than run-to-run noise.

**What the table shows.** The report prints one row per dataset and per model (only random forest, xgboost and lightgbm, because those are the three models that accept per-sample weights). The single number is the hybrid delta: the weighted hybrid score minus the unweighted hybrid score, already flipped so that a plus sign always means weighting helped, regardless of whether the dataset's metric is an error you want low or a correlation you want high. The last column turns that number into a verdict using a fixed cutoff of 0.01: "yes" if the delta beats plus 0.01, "no" if it is worse than minus 0.01, and a tilde for anything in between, meaning too small to call. A representative block is abagym_HER2, where random forest reads "-0.024  no", xgboost reads "+0.078  yes", and lightgbm reads "-0.081  no". Another is humanness_therapeutic, where all three models read "+/-0.002" and are all marked with a tilde.

**What it is actually telling us, and why I do or do not trust it.** The dominant pattern is that the three models disagree with each other on the same dataset, which is the tell-tale sign of noise rather than a real effect. On abagym_HER2 one model loses by 0.024, the next gains by 0.078, the third loses by 0.081 — all three verdicts differ, on the same data, from the same weighting idea. abagym_VEGF and flab_polyreact_jain_bvp show the same three-way split. Where the models do agree, it is usually because the task is saturated and nothing moves: humanness_therapeutic sits at roughly 0.001 to 0.002 across all three models because, as the underlying result files show, that AUROC is already up around 0.95 to 0.96, so there is no headroom for reweighting to matter. Each printed delta is itself an average over the cross-validation folds (five folds in the files I inspected), so the reader is not hiding any max or median trickery here — it simply reads the stored delta — but a mean of five folds on metrics this small is easily swamped by fold-to-fold variation. There is also a scale problem that makes the "yes/no" column untrustworthy across domains. buchwald_hartwig is a reaction dataset scored in RMSE units of about 15, so its xgboost entry of "+0.057  yes" is a 0.4 percent change on the error, which is noise, yet it clears the same 0.01 cutoff used for Spearman and AUROC numbers that live between 0 and 1 where 0.057 is a genuinely meaningful move. The same fixed cutoff is being applied to quantities on completely different scales. The most important thing the table does not tell us, though, is the experiment's own headline question: whether base reps or the hybrid benefit more. The result files clearly contain that comparison — a per-representation block over twenty-one reps and a per-model top-three-versus-hybrid summary — but the report only ever prints the hybrid column, so the base-versus-hybrid contrast the experiment was built to answer is completely absent from what we see. One caution: the local result files I read are from a different run than the report (for example buchwald random forest is a smaller delta locally than the "-0.168" printed in the report), so the schema is confirmed but the exact numbers in the report come from the server run.

**So what is wrong, and whose fault.** The experiment code itself looks sound and is not the problem: it guards the divide-by-range in the reliability score, threads the classification-versus-regression flag through correctly, and stores far more than it shows. The real gap is in the reader function read_n02 in tests/analysis/firstpass_notready.py. First and most serious, it prints only the hybrid delta and silently drops the per_rep and per_model_top3 data, so it does not answer the "base or hybrid more" question that is the entire point of n02 — that comparison should be surfaced, at minimum as a base-side delta next to the hybrid delta. Second, the fixed 0.01 tie threshold is applied identically to RMSE-scale reaction datasets and to correlation-scale antibody datasets, which mislabels trivially small reaction changes as wins or losses; the verdict should be relative to the metric's scale, or the reaction rows should not share a cutoff with the bounded-metric rows. Third, the reader never prints the fold count or spread behind each delta, so a reader cannot see how thin these averages are. Underneath the reader issues there is also a genuine design question for you: with deltas this small and this inconsistent across three models, reliability weighting may simply have no reliable effect on these datasets, and the honest reading is "no signal" rather than the scattering of yes/no verdicts the table currently shows.


## n06 — real replicate disagreement as ground-truth noise

**What the experiment is asking.** Every other noise experiment injects fake noise so we know the right answer by construction. n06 is the one that uses noise nature actually gave us. In the BindingDB binding-affinity dataset the same drug-and-target pair is often measured many separate times, in different labs, on different days, with different assays. When those repeat measurements of the identical pair disagree, that disagreement is genuine assay noise, not something we manufactured. n06 groups the rows by drug-and-target, computes the spread (standard deviation, in pKd units) of the labels inside each repeated group, and calls that spread the true noise level for those rows. Then it runs each of our ten noise-estimator methods and asks: does the estimator's guess about which samples are noisy line up with which samples really do sit in a disagreeing replicate group? Agreement is measured by a Spearman rank correlation, computed only over the rows that actually have a repeat measurement. The experiment "works" if some estimator's noise score correlates positively and meaningfully with the real replicate spread, and it separately checks whether doing the estimating in the hybrid feature space beats doing it in the plain concatenated feature space.

**What the table shows.** In this report there is no table. The entire n06 block reads:

```
[n06]  BindingDB ground truth — do noise scores agree with real replicate disagreement?
  (no n06 files)
```

Had results been present, the reader function would have printed four columns per dataset: the dataset name, the best estimator, the feature space that best estimator lived in (either "concat" or "hybrid"), and its best correlation. Those three "best" values are not something the reader computes on the fly. The experiment itself scans every estimator in every space, keeps the single highest Spearman correlation, and writes that winner into a small summary block; the reader simply prints whatever is in that summary. So the printed "best corr" is already a maximum taken over roughly twenty estimator-times-space combinations, and the report would show only that winner, never the spread of the other nineteen or how many replicate samples were behind it.

**What it is actually telling us, and why I do or do not trust it.** The line "(no n06 files)" is not a computed result, it is the reader giving up at the front door. The reader asks for a results directory named n06_bindingdb_ground_truth, finds none anywhere under the results tree, and prints that message immediately. I confirmed the directory genuinely does not exist locally, in either the working results folder or the copy synced from the server, and that there is no n06 JSON file of any kind on this machine. This is not a stale-schema problem, a divide-by-zero, or a saturated number. It is simple absence: the experiment has not been run, or was run on the server and never copied back. Two supporting facts. First, n06 is a single-dataset experiment that only applies to BindingDB affinity data, so unlike the other noise experiments it would never have produced the long per-dataset list of rows you see elsewhere in the report; at most it would have produced one row. Second, its sibling experiments in the same noise family did land results here, for instance n07 has a buchwald_hartwig file present, which proves the directory-finding plumbing works and that n06 is specifically the one with nothing to find. The underlying data it needs does exist and is loadable, since a BindingDB baseline file sits in the phase-5 baselines folder, and the experiment's own notes state that roughly 3,487 pairs with disagreeing replicates were verified over about 9,700 rows. So there is every reason to expect real ground truth if the job is actually launched. I cannot show you a single number here because there is not one to show.

**So what is wrong, and whose fault.** Nothing here is a bug in the experiment code and nothing here is a bug in the reader. The experiment source in tests/experiments/noise/n06_bindingdb_ground_truth.py is careful and was clearly rewritten after an earlier audit that had mistakenly reused the cold-target grouping as if it were a replicate id; the current version builds replicate groups the right way and refuses to fall back to the wrong grouping. The reader behaves correctly too; "(no n06 files)" is the honest thing to print when the folder is empty. The only real issue is operational: this experiment was never run, or its output was never synced down from the cluster, so there is simply nothing to analyze. The action is not a code change, it is to run n06 on the BindingDB dataset and copy the result back, after which this section can be revisited. One smaller thing worth flagging as a design question for you, for when the data does arrive: because n06 covers a single dataset and its printed answer is one maximum correlation over about twenty estimator-and-space combinations, a lone winning number will be easy to over-read. It would be worth having the reader also surface how many replicate samples backed that correlation and how the runner-up estimators scored, so a fluke best-of-twenty does not get mistaken for a robust finding. That is a reader enhancement, not a correctness fix, and it only matters once the experiment has actually been run.


## n07 — noise remediation: which cleanup strategy best repairs the damage from noisy labels

**What the experiment is asking.** Take a dataset, deliberately corrupt a slice of the training labels (for regression it jitters ten percent of the labels with Gaussian noise scaled to the label range; for classification it randomly flips ten percent of the classes), and then try four different cleanup strategies to undo the damage: remove the samples flagged as noisy, downweight them, smooth their labels toward their neighbours, or replace their labels with a nearest-neighbour average. Two reference points anchor the comparison: a clean model that never saw any noise, and a "noisy baseline" that saw the corruption and did nothing about it. The headline number is "recovery percent," defined as how much of the clean-versus-noisy performance gap a strategy claws back. A recovery of one hundred percent means the strategy fully restored clean performance; zero means it did nothing; negative means it made things worse than just leaving the noise alone. The hybrid is "working" here only in the sense that we run all of this inside the hybrid feature space and ask which cleanup strategy wins.

**What the table shows.** The report prints three things per dataset: the dataset name, the "best hybrid strat" (the name of the winning cleanup strategy), and the "best recovery%" (how much of the gap that winner recovered, higher being better). For example, the report reads "abagym_HER2  remove  4736.8", meaning the remove strategy was named the winner and the best recovery number was four thousand seven hundred thirty-seven percent. Another row reads "buchwald_hartwig  label_smooth  350.9", naming label smoothing as the winner with a best recovery of three hundred fifty-one percent. The six datasets covered are all antibody or reaction tasks (abagym, flab, ginkgo, buchwald), which is expected because the noise suite only runs on that subset.

**What it is actually telling us, and why I do or do not trust it.** I do not trust these numbers, and the reason is structural, not cosmetic. Recovery percent is a fraction whose denominator is the clean-to-noisy gap, and on these datasets that gap is tiny. I opened the one local result JSON, buchwald_hartwig, and the clean RMSE was 14.35 while the noisy RMSE was 14.58 — the injected noise moved the error by only about a fifth of a unit. When you divide a strategy's change by a gap that small, any ordinary fold-to-fold wobble gets amplified into hundreds or thousands of percent. That is exactly what we see: abagym_HER2 at 4736.8 and, most tellingly, flab_aggregation_jain at 243782.1 percent are not "the cleanup worked spectacularly," they are "the denominator was almost zero." A recovery of two hundred thousand percent is a divide-by-near-nothing artifact, full stop. The experiment does guard against a literally zero gap, but the threshold it uses is one part in ten billion, which is far too permissive — a gap of a tenth of a unit sails through the guard and still explodes.

There is a second, separate problem hiding in how the reader builds these two columns, and it means the two columns do not even describe the same thing. The "best recovery%" number is the single largest value the reader can find scanning across all six downstream models and all four strategies in the per-model recovery table. The "best hybrid strat" name, however, comes from a completely different field that only reflects the legacy random-forest hybrid. On buchwald_hartwig the printed recovery of 350.9 actually came from the ridge model using knn_smooth (the JSON shows ridge/knn_smooth at 350.88), but the strategy the report names is label_smooth, which is the random-forest winner. So the row literally pairs one model-and-strategy's number with a different strategy's name. A reader would reasonably assume "label_smooth recovered 350.9 percent," and that is not what happened.

Underneath the blow-ups the real signal is also weak and inconsistent. In the same buchwald JSON, the four strategies swing from helpful to harmful depending on which downstream model you look at: knn_smooth is plus 350 percent under ridge but minus 249 percent under the MLP; remove is plus 315 under ridge but minus 474 under the SVM. There is no stable "this cleanup strategy works" story here — the sign of the effect flips with the model. To confirm this pattern holds on the other five datasets I would need the server JSONs, since only buchwald is present locally.

**So what is wrong, and whose fault.** There are three distinct issues. First, an experiment design flaw: recovery percent is the wrong headline when the clean-to-noisy gap is small, because it is a ratio that detonates near zero, and the near-zero guard in n07_remediation.py is set far too loose to catch it. This is worth a conversation with you about what the right summary is — a bounded quantity like the raw error difference, or a recovery that is only reported when the gap is large enough to be meaningful, would be far more honest than an unbounded percentage. Second, an analysis-reader bug in read_n07: it prints a recovery number harvested as a global maximum over all six models while printing a strategy name drawn from the random-forest-only field, so the number and the name can disagree, as they do on buchwald_hartwig. That is a straightforward mismatch to fix in the reader — either report the model and strategy that actually produced the maximum, or restrict the maximum to the same source the name comes from. Third, a design question about interpretation: because the strategies flip sign across downstream models, collapsing everything to a single "best" cell throws away the fact that there is no consistent winner, and you should decide whether this experiment is meant to name one strategy at all or simply report the per-model spread. None of these are fatal to the pipeline running, but as printed the n07 table is not trustworthy and its most eye-catching numbers are artifacts.


## n09 — does the hybrid re-order the noisy-label method leaderboard

**What the experiment is asking.** There is a family of "learning with noisy labels" methods — twelve of them here, with names like contrast_to_divide, early_learning, and evidential_kernel — that are designed to train a model that survives when the training labels are wrong. This experiment takes each dataset, deliberately corrupts the training labels with synthetic noise at five increasing levels, and asks a purely relative question: when you swap the base representation for the hybrid representation, does the ranking of these twelve methods change, and do more methods get better or worse from the swap? It is explicit in its own docstring that it is not measuring absolute robustness of any method; it only cares whether feeding the methods a hybrid feature mix re-orders who comes out on top and how many methods the hybrid helps versus hurts. The hybrid "works" here, loosely, if swapping it in improves more methods than it harms.

**What the table shows.** The report prints three things per dataset. "ranking_changed" is a True/False flag that is True when the top-three list of methods under the base representation is not identical to the top-three list under the hybrid; note this is an order-sensitive comparison of the top three, so even swapping second and third place flips it to True. "hyb improves" is the count of methods, out of twelve, whose hybrid score beats their base score. "hyb harms" is the count that got worse. Both counts are measured only at the single highest noise level, sigma equals 1.0, and they are plain mean-versus-mean comparisons with no significance test. Two representative rows quoted verbatim: "abagym_EGFR  True  12  0" (every one of the twelve methods improved with the hybrid, none was harmed) and "flab_aggregation_jain  True  3  9" (the hybrid helped three methods and hurt nine).

**What it is actually telling us, and why I do or do not trust it.** The pattern in the report splits cleanly: the two abagym antibody datasets show a total sweep in the hybrid's favour, twelve improves and zero harms each, while the two flab datasets show the opposite, three improves and nine harms, and ginkgo_aggregation is four and eight. Buchwald sits in the middle at nine and three. So there is no consistent verdict — on some datasets the hybrid helps everything, on others it hurts most things. My bigger worry is the operating point. That "highest sigma" is 1.0, and in this experiment sigma is a fraction of the label range, so at sigma equals 1.0 the injected Gaussian noise has a standard deviation equal to the entire spread of the labels. That is catastrophic corruption, and the local buchwald result confirms the saturation: the best method's error climbs from a clean 15.71 to somewhere between 18.92 and 26.63 across the twelve methods at that noise level. Comparing methods when the labels are essentially destroyed, by raw mean with no significance test, is close to reading tea leaves — a count of twelve-to-zero versus three-to-nine can swing on fold noise. I also do not fully trust the "ranking_changed" column: it is True for all six datasets, which is exactly what you would expect from an order-sensitive top-three equality check that trips on the tiniest reshuffle, so it is carrying almost no information. One caveat I must be honest about: the only n09 JSON I have locally, buchwald_hartwig.json dated 26 May, is a stale pre-fix run in which the entire hybrid arm failed — its clean_hybrid is NaN, its top-three hybrid list is empty, and its improve/harm counts are both zero — yet it still records ranking_changed as True purely because an empty list differs from a populated one. The report's numbers (buchwald showing nine and three, all counts summing to twelve) clearly come from newer server runs where the hybrid arm actually ran, so I cannot re-derive the exact report figures from local data; confirming them needs the server JSONs.

**So what is wrong, and whose fault.** Three separate things. First, an experiment-design concern in n09_lnl_survey.py: it headlines the improve/harm counts at sigma equals 1.0, where the labels are corrupted by noise as wide as the whole label range, and it counts by bare mean comparison with no significance or tie handling. That is the least informative noise level to summarise on, and it is a question for you whether the headline should instead be a moderate sigma or a count aggregated across sigmas. Second, the ranking_changed flag in that same file is defined as order-sensitive inequality of the top-three lists, which makes it fire almost unconditionally and, worse, fire spuriously True whenever the hybrid arm is empty or NaN; it should at minimum guard against an empty hybrid list before declaring the ranking changed. Third, an analysis-reader shortcoming in read_n09: it distills an experiment that computed six conditions, five noise levels, a weighted-hybrid arm, full retention curves, and explicit top-three lists down to three scalars, all pinned to the worst noise level, and it never surfaces the sigma being used, the weighted-hybrid comparison, or whether the hybrid arm even populated. A reader glancing at "True 12 0" has no way to know it is the sigma-1.0 slice or that a NaN hybrid would have printed the same True. I would widen the reader to show the counts across sigmas and to flag empty or NaN hybrid arms explicitly, and I would raise the sigma-1.0 headline choice and the top-three equality definition with you as design calls before trusting any of these rows.


## n11 — the noise-cleanup bake-off (best recovery config per noise level)

**What the experiment is asking.** Take a dataset, deliberately corrupt its labels with a known amount of noise, and then try to undo the damage. The experiment runs a big grid of "cleanup recipes": every combination of a noise-score estimator (roughly a dozen ways of guessing which points are the noisy ones), a remediation method (down-weight the suspect points, or smooth their labels toward a local average), a strength dial called alpha, a distance metric, and a representation to measure the noise in. For each recipe it trains a random forest on the noised-and-then-cleaned data and asks: how much of the performance you lost to the noise did this recipe win back? That is the "recovery" number, expressed as a percentage of the clean-minus-noisy gap. A recipe that recovers 100 percent has restored the model all the way back to its clean-data performance. The hypothesis that would count as "cleanup works" is that some estimator-and-remediation recipe reliably pulls recovery well above zero across noise levels. Note that the hybrid representation is present in the grid but is explicitly flagged as oracle-biased and not to be trusted, because the hybrid was designed while looking at the clean labels; the honest claim is about the estimator-and-remediation recovery, not about hybrid-versus-base.

**What the table shows.** The report prints, for each dataset and each of the two noise levels (sigma 0.3 and sigma 0.6, meaning noise scaled to 30 percent and 60 percent of the label range), a single winning recipe and its recovery percentage. The "best config" cell packs three things separated by slashes: the representation the noise was scored in, the estimator that did the scoring, and the remediation method plus its alpha strength. The final column, recov%, is how much of the clean-to-noisy gap that one winning recipe recovered. A representative sane row is "buchwald_hartwig  0.3  reactant_ecfp4/quantile_regression/co  58.3", meaning at the lower noise level the best recipe on the Buchwald-Hartwig reaction dataset recovered 58.3 percent of the lost performance. A representative broken row is "ginkgo_aggregation  0.6  esm2_entropy_top20/activity_cliff_awa  2827.0", claiming a recovery of 2827 percent.

**What it is actually telling us, and why I do or do not trust it.** The first thing to understand is that recov% is not a typical recipe's recovery — it is the maximum over the entire grid. For Buchwald-Hartwig that grid held 4,788 recipes per noise level (I confirmed this in the local result file), and the experiment sorts all of them by recovery and prints only the champion. Picking the single best out of nearly five thousand noisy measurements is a textbook winner's curse: even if cleanup did nothing on average, the luckiest recipe would still look impressive. So the printed number systematically overstates how well cleanup works, and it tells you nothing about whether cleanup works in general. The honest signal the experiment actually computed and then the reader threw away is the fraction of recipes that recovered anything at all: in the local Buchwald file that is 93.2 percent of recipes positive at sigma 0.3 but only 59.6 percent at sigma 0.6, which is a real and interesting story the table never shows.

The Buchwald numbers themselves (58.3 and 72.5 percent) are believable because that dataset has a healthy clean-to-noisy gap — I checked the local file and the gap is 2.90 RMSE units at sigma 0.3 and 8.89 at sigma 0.6, so dividing by it gives sensible percentages. The antibody rows are where it falls apart. The recovery percentage is a ratio whose denominator is the clean-minus-noisy gap. When the injected noise barely hurt the model, that gap is tiny, and dividing by a tiny number makes recovery explode. The ginkgo_aggregation value of 2827.0 percent, and its 271.7 percent at the other noise level, and flab_aggregation_jain's 116.4 percent, are not real recoveries — they are division artifacts from a near-zero gap. Worse, because the reported cell is the maximum over the grid, the experiment is actively hunting for whichever recipe divided by the smallest gap, so it surfaces exactly the most inflated artifact it can find. I only have the Buchwald file locally; the four antibody and reaction rows come from server-synced results I cannot open here, so I am inferring their tiny-gap cause from the mechanism rather than reading their gap fields directly, but the Buchwald file confirms both the 4,788-config max and the exact printed numbers, so the mechanism is not in doubt. One more red flag: any recovery above 100 percent means the cleaned model supposedly beat the never-noised model, which is a sign of noise in the measurement, not of a good cleanup.

**So what is wrong, and whose fault.** There are three separate problems. First, an experiment bug: the guard against dividing by the gap only triggers when the gap is almost exactly zero (below one part in ten billion), so any small-but-nonzero gap sails through and produces absurd percentages like 2827. The fix belongs in the experiment source, in the recovery calculation inside run() and again in the summary builder, and should require the gap to be a meaningful fraction of the clean score before a recovery ratio is even reported, and should clip or flag the rest. Second, and relatedly, choosing the winner as the single argmax over thousands of recipes is a design choice that guarantees an unrepresentative number; a median recovery, or the fraction of positive recipes, would be far more honest, and that also lives in the summary builder in the experiment source. Third, analysis-reader shortcomings in read_n11: it prints only the champion and discards the fraction-positive, the total count, and the clean and noisy scores that would immediately expose a tiny gap; it truncates the config description at 37 characters, which literally cuts off the remediation method and the alpha strength so you cannot even read what the winning recipe was ("reactant_ecfp4/quantile_regression/co" is the whole cell); and it never marks when the winning space is the oracle-biased hybrid, even though the header tells the reader to ignore that arm. Finally there is a scope question for you: the experiment's own docstring says it is molecular-only, yet the table is showing a reaction dataset and three antibody datasets, so either that scope note is stale or these runs are out of the declared scope, and that is worth a decision rather than a silent acceptance.


## n12 — does weighting the distance by feature importance help clean up noisy labels

**What the experiment is asking.** This is a narrow ablation about one trick inside noise cleanup. When you try to spot mislabelled training points, one common method is to look at each point's nearest neighbours: if a point's label disagrees with its neighbours, it is probably noisy, and you down-weight it before training. Those "nearest neighbours" are found by measuring distance in feature space. The question here is whether stretching the features by how important they are — scaling each feature by the square root of its importance before you measure distance, so that informative features count more toward "who is my neighbour" — makes that neighbour-based cleanup work better. It asks this twice: once when the feature space is a single base representation (for a molecular set that would be ECFP4, but on these datasets it falls back to whatever rep is available), and once when the feature space is the hybrid. So "the hybrid working" here is not really the point; the point is whether importance-weighting the distance helps at all, and whether the hybrid already bakes in that benefit so the weighting becomes redundant.

**What the table shows.** Each dataset appears twice, once for each noise level (sigma 0.3 and 0.6, meaning noise added at 30 percent and 60 percent of the label range). The three result columns are plain true/false flags. `helps_base` is true when importance-weighting the distance gave a higher average "recovery" than the unweighted distance on the base representation, where recovery means how much of the damage the added noise did was clawed back. `helps_hybrid` is the same comparison on the hybrid, and it is true if either of two ways of weighting the hybrid beat the unweighted hybrid. `already_wt` is true when the unweighted hybrid and the importance-weighted hybrid land within two recovery points of each other, i.e. the weighting made no real difference because the hybrid effectively did it already. The report itself prints a warning above the table: "Boolean flags (NOT significance tests — spread often overlaps)." Two representative rows, quoted verbatim: "abagym_HER2         0.3             True          True       False" and "buchwald_hartwig    0.3            False          True        True".

**What it is actually telling us, and why I do or do not trust it.** I do not trust these flags to mean much, and the experiment's own authors say the same in the source. Look at abagym_HER2 across its two noise levels: at 0.3 it reads True, True, False, and at 0.6 it reads True, False, True. The hybrid-weighting verdict flips from "helps" to "does not help" and the "already weighted" verdict flips from false to true, just by turning the noise up. A real effect would not reverse itself between two noise levels on the same dataset. That is the fingerprint of noise being reported as signal. The deeper reason is that every one of these booleans is a single greater-than comparison between two averages, and each average is taken over up to eighteen underlying numbers (three noise estimators, three neighbour counts of 5/10/20, and two importance methods), all collapsed into one mean per condition. The experiment does compute the spread of those numbers — a standard deviation and a min/max range per condition — precisely so a small gap can be read against its own noise floor, but none of that reaches this table. There is also a divide-by-small-number hazard: recovery is the change in error divided by the clean-versus-noisy gap, so on any dataset where the added noise barely hurt, that gap is tiny and the recovery percentage explodes; the code guards only against an exactly-zero gap, not a near-zero one. Finally, the one n12 result file present locally, buchwald_hartwig.json dated 2026-05-29, is degenerate: both sigmas have an empty per_importance_method block and every summary flag is false, meaning that on that older run every estimator failed and produced no scores at all. The report in front of us has populated true/false values, so it must be reading a newer server run that has not been synced down here — I cannot verify the actual recovery numbers behind these flags against local data.

**So what is wrong, and whose fault.** Three separate things, and the honest summary is that the experiment is more careful than the report makes it look. First, a real scope mismatch that is a design question for you: the source file states at the top that n12 is molecular-only, additive-Gaussian-noise-only, yet the table is populated entirely with antibody sets (abagym_HER2, the two flab sets, ginkgo_aggregation) and a reaction set (buchwald_hartwig), and none of the molecular sets it was written for. The feature-importance-weighting idea was built around a molecular fingerprint base rep, and it is silently falling back to some other representation on these datasets — worth deciding whether n12 should run on them at all. Second, the experiment carries an oracle leak it openly admits in a comment: the hybrid's blueprint is chosen from clean labels and only rebuilt under noise per fold, so the hybrid conditions are a best-case, not a fair leak-free baseline; that caveat never surfaces in the report. Third, and most fixable, is the reader: read_n12 in the analysis script prints only the three booleans and throws away everything that would let you judge them — best_k, best_importance_method, and especially the per-condition recovery mean, standard deviation, and range that the experiment went to the trouble of computing. The result is a table that looks like five crisp verdicts when the underlying reality is a set of overlapping distributions. The reader also has a cosmetic width bug: the dataset column is twenty characters wide but "flab_aggregation_jain" is twenty-one, so its name jams straight into the sigma value with no gap ("flab_aggregation_jain0.3"). I would fix the reader to print each condition's mean recovery next to its spread and stop reducing the whole thing to booleans; the experiment logic itself does not need changing, only the decision about which datasets it belongs on.


## n13 — does the hybrid advantage survive when you change the shape of the injected noise

**What the experiment is asking.** This is a sensitivity study, not a robustness benchmark. It takes clean labels and deliberately corrupts them with several different *shapes* of synthetic noise — Gaussian bumps on every point, uniform bumps, heavy-tailed (Student-t) bumps that occasionally throw a huge outlier, and a "partial" mode that badly corrupts only a fraction of the points. For each noise shape it trains a whole family of noise-robust learning methods on two feature sets: the plain base representation, and the feature-selected hybrid. The hypothesis is that the hybrid keeps its edge no matter which noise shape you use — in other words, whatever advantage the hybrid has is not an accident of one particular kind of noise. The hybrid "works" here if, for most noise shapes, the hybrid-trained methods on average score better than the same methods trained on the base representation, and ideally if the best method stays the same as you swap noise shapes.

**What the table shows.** Each row is one dataset. The "persists" column is a single true/false verdict: the experiment computes, for every noise shape, the fraction of noise strengths at which the hybrid beat the base rep, then averages those per-shape fractions, and prints True if that average is above one half. The "gauss_transfers" column asks a stricter yes/no question: is the single best-scoring noise-robust method under Gaussian noise *also* the single best method under every other noise shape? It is an exact-match test — one method swap anywhere makes it False. The last column, "win rate by noise type," lists for each noise shape the fraction of strength levels (there are three) where the hybrid won, so every number is really a count out of three and can only ever be 0.00, 0.33, 0.67, or 1.00. One representative row reads "buchwald_hartwig  True  False  gaussian=1.00 uniform=1.00 multiplicative=1.00 heavy_tailed=1.00 partial=1.00", and a contrasting one reads "flab_aggregation_jain  False  True  gaussian=0.00 uniform=0.33 multiplicative=0.00 heavy_tailed=0.00 partial=0.67".

**What it is actually telling us, and why I do or do not trust it.** The first thing that jumps out is the word "multiplicative" in every row. The current experiment source no longer sweeps a multiplicative noise shape at all — it was deliberately removed because scaling a label by its own value is not a meaningful noise model when the target has an arbitrary origin, and the code now sweeps only gaussian, uniform, heavy_tailed, and partial. So the report was produced from an older version of the results that still carried the dropped shape. I confirmed this against the one local result file, tests/results/noise/n13_noise_distributions/buchwald_hartwig.json, dated 31 May, whose stored noise_types list literally begins gaussian, uniform, multiplicative, heavy_tailed, partial. That local file is itself stale and does not even match the report's numbers (it records gaussian at 0.67, the report says 1.00), so the report's figures came from a separate, also-outdated server run. Everything in this block therefore predates the current code and should not be read as the experiment as it now stands. Beyond the staleness, the coverage is tiny: only four datasets appear, and they mix a reaction task where lower error is better (buchwald_hartwig) with antibody tasks where higher correlation is better (abagym_HER2, the two flab rows). Even taken at face value the signal is thin, because each "win rate" is a count out of three, so a single flipped strength level moves a cell by a third. The abagym_HER2 row runs the full gamut, 0.33 to 1.00 depending on the shape, which is exactly what noise looks like at this resolution. And the "persists" verdict hides a lot: it is the average of those per-shape fractions squashed down to one boolean, so flab_pk_jain_fcrnrt (average four-fifths) and a barely-over-half dataset would both just read True.

**So what is wrong, and whose fault.** The headline problem is stale data, and it is not really the reader's fault — the reader faithfully prints whatever keys are in the JSON, including the retired multiplicative shape. The fix is operational: rerun n13 on the server with the current source and re-sync, at which point multiplicative disappears and the partial track is correctly labelled as a corrupted-fraction sweep rather than a strength sweep. There are two genuine reader shortcomings, both in read_n13 in tests/analysis/firstpass_notready.py. First, it prints the win-rate fractions but never prints the denominator behind them, so the reader of the report cannot see that each is a count out of three; showing the raw wins-out-of-total would make the coarseness obvious. Second, the "hybrid win" test buried inside the experiment averages the metric across all twelve noise-robust methods for the base rep and again for the hybrid and compares those two means, so one badly-behaved method can swing the verdict; the reader surfaces none of that and shows neither the per-method spread nor the fact that "persists" is a mean-of-means collapsed to a boolean. The design questions for you sit in the experiment source, tests/experiments/noise/n13_noise_distributions.py: whether a win rate that can only take four values across three strengths is a strong enough instrument, whether averaging over twelve heterogeneous methods is the right definition of "hybrid advantage," and whether "gaussian_rank_transfers" as an exact single-best-method match is too brittle to be informative (it will read False almost any time two methods are close). None of these are bugs; they are honest limits of a four-dataset, three-strength sensitivity probe. The experiment logic itself looks sound and carefully guarded — the only thing actually wrong today is that we are looking at pre-schema-change output.
