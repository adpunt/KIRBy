# pool-not-in-hybrid-eval-key

**title:** The hybrid_evals key names the chosen top-k representations but not the pool they were chosen from, and the pool sets the budget split inside that subset

**area:** hybrid_evals/ cache layer and the per-fold evaluation path (_evaluate_hybrid_config)

**class:** A-wrong-answer

**severity as reported:** large

**location:** src/kirby/find_best_hybrid.py:732 (_hybrid_eval_cache_path), :885 (_make_hybrid_eval_meta), :4136-4176 (probe), :5231-5238 (rep_sets), :7679-7683 (_screen_reps); src/kirby/hybrid.py:851-854 (_sanitize_baseline_scores), :1098-1101 (top_k weights), :5471-5478 (auto-demote)

## scenario as reported
One process, `test_rep_subsets=True`, a 10-representation pool, allocation `top_3`, metric rmse. Config 1 runs over rep_set 'all'. The 10 allocation scores are -RMSE, so all negative; `_sanitize_baseline_scores` subtracts the pool minimum (the worst representation J), the top_k scheme keeps each of A/B/C weighted by its own shifted score, and the largest-remainder split gives A/B/C 176/167/157 features. It writes hybrid_evals/<ds>/<hex(A,B,C + widths)>__top_3__<imp>__<ev>__b500__f0of5_42__rf__none.pkl. Config 2 runs over rep_set 'no_J' — the same nine remaining representations, J dropped. Its top 3 is still A/B/C, the widths of A/B/C are unchanged, and allocation/importance/evaluator/budget/fold/n_folds/seed/model/labels_hash/train_idx_hash/val_idx_hash/aug fields/step_size/candidate_ranking/greedy_tolerance/metric_name/task_type/objective are all identical — so it lands on that same filename and the meta matches on every key. It is served config 1's fold score. But with J gone the minimum is now K, the shift is smaller, the weights become s_A-s_K / s_B-s_K / s_C-s_K, and the split it would have computed is 182/167/152 — a different feature matrix and a different number. `rep_subset` is a CONFIG_COL in result_cache.py:75-77, so the two are filed as two separate rows in result_db, one of them holding the other's numbers. Same collision across runs whenever `screen_threshold` differs (it is in the search meta at find_best_hybrid.py:637-638 and in no hybrid_evals key), and with augmentation on it bites every leave-one-out subset rather than only the one that drops the minimum, because hybrid.py:5474 demotes the zero-allocated base representations into the augmentation pool and that set is pool-dependent while `aug_names` in the meta records only the caller's original augmentation dict.

## evidence as reported
hybrid.py:851-854 `min_val = min(finite.values()); shift = -min_val if min_val < 0 else 0.0; return {rn: (s + shift ...)}` — the shift is taken over every representation in `rep_dict_train`, which is the whole pool, not the top k. hybrid.py:1098-1101 `sorted_reps = sorted(baseline_scores.items(), key=lambda x: x[1], reverse=True); top_names = {name for name,_ in sorted_reps[:k]}; return {name: (score if name in top_names else 0.0) ...}` — the surviving weight is the shifted SCORE, so its magnitude, not just its membership, decides the split. hybrid.py:1343-1344 `baseline_scores = {rn: precomputed_scores.get(rn, float('nan')) for rn in rep_dict_train}` restricts the score vector to the pool actually passed in. find_best_hybrid.py:4127-4136 `_subset_widths = {n: int(base_reps[n].shape[1]) for n in _predicted_subset ...}; _subset_hex = _subset_name_hex(_predicted_subset, _subset_widths)` — only the k predicted names reach the hash. _make_hybrid_eval_meta (find_best_hybrid.py:885-955) has no pool, no tier, no rep_subset and no screen_threshold key. find_best_hybrid.py:5234-5238 builds the leave-one-out pools; find_best_hybrid.py:7740-7742 states the cross-pool sharing is deliberate ("so general-tier and top-tier runs share the identical-subset computation").

## fix as proposed
Put the pool in the identity. Cheapest correct version: add the full sorted (name, width) list of `base_reps` — not just the predicted k — to `_make_hybrid_eval_meta`, and hash it into `_subset_name_hex`'s filename component. That separates 'all' from every 'no_X', separates screened from unscreened pools, and separates the auto-demote candidate sets. Alternatively thread `tier` through, since result_cache.py:42-45 already declares tier the thing that fixes the rep pool — but tier is free text and is not set by every caller, so the pool list is the safer key. Either way this invalidates every existing hybrid_evals file, so it needs a wipe (hybrid_evals is already in tests/slurm_scripts/wipe_allocation_caches.sh:102).
